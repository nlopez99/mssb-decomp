# Match functions

Your **claim** is one unit that already has a source file. Turn as many of its functions as you can into C that compiles to the original instructions with the same relocations. `python3 tools/match.py` gives the **verdict**, and only its `match` counts. The measure is matched bytes per hour, so take cheap functions first and let expensive ones go at the time box.

## Steps

1. **Survey.** Run `date +%s` and keep the number. Run `python3 tools/match.py <unit> --all`; if the checkout has no `objdiff.json`, it is not built, so stop and report that. Read `docs/matching-notes.md`, the index of lessons by symptom. Put the source file in the order **Source conventions** requires, and define first the data in the unit's own ranges that the target reaches through a pool base, since functions that read it score low until it exists; data each function names with its own `lis`/`addi` changes no score and can wait until the functions are done. Where the target pools that data, some boundaries between objects show only once functions are written (an offset folded into one `addi`); split those `symbols.txt` entries as they turn up. Order the functions that do not match: `reloc`, then `partial` above 95%, then `missing` and `stub` functions from smallest to largest, then the remaining `partial` ones. A `partial` with a comment above it saying what still differs has already used an earlier session's time box, so it goes last, whatever its score. Move each inlined function ahead of the function that inlines it: a function with no callers in the assembly whose body appears inside another one is inlined there, and its caller cannot match until it does. The exception is a copy the original wrote out in place: when the function itself matches and its copy differs from the target only in register numbers, write the copy in the caller (`fn_3_8C07C` in `m_sound.c`). A callee that is still an empty stub counts the same way, since the stub gets inlined into its caller: `match.py <unit>` names those stubs after each function (`waits on ...`), so put them first, and check that listing again as functions get bodies. Any body stops the inlining, so a rough draft of a waited-on stub lets its callers match; the stub itself then waits for its own place in the order. Among waited-on stubs, draft first the one whose callers add the most bytes. A large function built mostly from inlined copies of functions that already match is cheap once they do, so take it then, ahead of register-only polishing. Done when you have that list. (`match.py` exits 1 while anything differs, so don't chain it with `&&`.)

2. **Match each function in list order.**
   1. Run `python3 tools/match.py <unit> <function> --m2c` for the target assembly and an m2c draft. The draft is typed only for globals the source's includes declare, so add the includes it needs (usually `game/UnknownHomes_Game.h`) first. Its types are still guesses. A long draft is cut at `--max-lines`, and the whole draft is saved under `build/m2c/<function>.c`. Take parameter types from the callers' register setup, from how the function's entry uses each register, and from SDK prototypes in `include/Dolphin/`. `s32` is `long`, not `int`: MWCC treats them as different types, so an unexplained register difference can come from using one where the original used the other. `grep -rn "<function>" build/GYQE01 --include='*.s'` finds both calls and pointers to it in data.
   2. Write the function in its position (see **Source conventions**) and run `python3 tools/match.py <unit> <function>`. Each run rebuilds one object in under a second. If the header still declares the function `void(void)`, give it the real prototype in the same edit, or the build fails with a redeclaration error. A small function given a body can now be inlined into callers that already matched, which then show as `missing`: after writing a callee, check its callers in `match.py <unit>`, and write the callee's own same-file callees first. `-C 0` shows only the differing lines; raise the 200-line cap with `--max-lines` for long functions, since `--full` prints every line.
   3. Find the diff's symptom in `docs/matching-notes.md` and read the notes file it points to, change one thing, and run it again.

   Done when the verdict is `match`, or when the **time box** runs out: 20 runs without a new best score for that function; each new best restarts the count. A run is one attempt: a single compile and compare, one scripted batch of variants (such as every declaration order), or one permuter session, and runs that change a callee count toward the function whose score you are chasing. When only register numbers still differ, first try a scripted batch of declaration orders and `int`/`s32` swaps (see the notes on `--source`), which solved most such cases; then spend part of the box on `python3 tools/permute.py <unit> <function>`: start the command it prints in the background, check it a few minutes later with `python3 tools/permute.py <function> --best` (foreground `sleep` is blocked), which prints its best result so far and the source change behind it, and stop it with `python3 tools/permute.py <function> --stop`, which also stops its workers and leaves other runs alone (macOS has no `timeout`). One session per function is usually enough: when the first finds nothing a programmer would write, a second rarely does. The permuter works on a copy made at setup, so rerun `permute.py` after changing the source. Check the function's body in that change before trusting the score. It compiles the function alone, so skip it when the difference lies in code inlined into or from another function (vary that by hand), and when its setup reports that its copy compiles differently from the build. Compiling a scratch copy with other flags, compiler versions or pragmas is allowed as evidence for an escalation, and counts toward the box.

3. **Keep or restore.** At a time box, keep the **best candidate** only if its score beats what the file had, and put a comment of at most three lines above it saying what still differs. Otherwise restore the previous code. When a function teaches something the notes lack, add it under its symptom, in `docs/matching-notes.md` or the notes file that symptom points to (symptom, cause, fix, example).

4. **Verify and commit.** Run `python3 tools/match.py <unit> --all`, `python3 tools/check_symbols.py`, `python3 tools/check_prototypes.py` and `python3 tools/regress.py`. All three checks must pass (by exit code: `check_prototypes.py` also lists other units' known disagreements) before you commit, and the last must end in `regress: OK`. In a worktree made by `tools/worktree.py` it compares with the branch the worktree started from, not with your earlier commits, so giving up a match from earlier in the session for a larger one passes; name such trades in the report. For the same reason it misses a partial that dropped since your last commit: run `python3 tools/regress.py --base HEAD` as well. Report only your unit's lines of its gained list. Commit with a message that names the matched functions, or says what else changed.

5. **Report.** Stop every background job you started (permuter runs, scripts): one left running keeps editing the worktree after you finish. Then your final message gives:
   - the unit, elapsed seconds since step 1 (per unit when the claim has several), code bytes matched before and after (the `code X/Y bytes` line of `match.py <unit>`), and section scores before and after;
   - each function you worked on, with its size and its status and score before and after;
   - each best candidate's remaining difference;
   - lessons added to the notes;
   - every **escalation**.

## Claim

Change only the unit's source file, its header under `include/`, the lines of `config/GYQE01/<module>/symbols.txt` that fall inside the unit's ranges in that module's `splits.txt`, and the notes (`docs/matching-notes.md` and `docs/matching-notes/`). You may change a shared declaration, such as a prototype, a field type or a new field in a shared header, when the evidence requires it. When other units use a shared struct's current fields and the evidence shows another layout over the same bytes (per-player blocks where the header has flat fields), add that layout as an anonymous `union` member over them, so both sets of names compile. If you change a shared declaration, run `match.py` on the units that use the changed fields or prototype (`regress.py` covers the rest, since it rebuilds every unit) and list the change in the report. Likewise, a `symbols.txt` entry outside your ranges that the evidence shows is wrong (separate objects lumped into one symbol, a wrong size) may be fixed in its own commit, once `regress.py` passes with it. List that change in the report too.

Report these as an escalation with the evidence, and leave them unchanged: `splits.txt`, compiler flags or versions in `configure.py`, other units' source files, and any difference you trace to something outside the claim. Two cases keep you moving while you escalate:
- Data that only your unit uses but that lies outside its ranges in `splits.txt` gets an `extern` declaration, plus an escalation proposing the split range and any wrong `symbols.txt` entries in it; propose a range only if it is contiguous with the unit's other data and fits the link order. If the target reaches several objects from one base register (`addi rX,base,K` before an element offset, or offsets past a symbol's size), no `extern` can match. If `symbols.txt` lumps objects you need to name, split those entries first in their own commit (see above). Tune the function in a scratch copy of the source that declares the data as statics, compiled with `python3 tools/match.py <unit> <function> --source <copy>`; commit the `extern` version, and put the copy's result in the escalation. When the data is too large to define within the session, the offsets past the symbol's size from one base are evidence enough for the escalation. Functions just outside the unit's `.text` range that use its data may belong to it too: escalate them with the evidence. When such a function is inlined into one of yours, write it in your file as `static inline` under its `.text` line, so your object gains no extra function, and keep its prototype out of the header until the split moves; then it becomes a plain function with a prototype.
- A function or global that another unit's header declares wrongly (typically a `void(void)` placeholder matching that unit's stub, or a struct where the data is an array) gets a correct `extern` declaration in your source file when fixing the header would break that unit's source. Do not include that header. Escalate with the declaration and its evidence. `check_prototypes.py` fails when that declaration and the header differ in the number of parameters or in the kind (integer, float or pointer) of a parameter or the return value; against a `void(void)` placeholder, or for a main-DOL function, it only lists the difference. Then fix the header and the owner's definition in their own commit if the owner keeps its score with them (a stub, which may gain a `return 0;`, or a parameter it never reads; check with `match.py` on that unit), and otherwise call through the header's form and escalate.
- Your own header declares one of your functions in a form other units depend on: they were matched against it, or they declare the function locally in a form your corrected prototype contradicts while including your header (a redeclaration error that only a full `ninja` build shows, so run `ninja` after editing your header). Keep the header's form, put the correct prototype at the top of your source file, try the other unit's fix in a scratch copy, and escalate with the result.

A pragma or a section score is also an escalation: if a pragma gives a large gain, report the gain, and keep the pragma out of the source. Section scores (`.rodata`, `.data`, `.bss`) do not need to reach 100% for functions to `match`. Report them, and leave a unit's `Matching`/`NonMatching` flag in `configure.py` alone.

## Source conventions

- Each function sits under its `// .text:0x... size:0x... mapped:0x...` line. For a function new to the file, compute `mapped` from a neighbour: the offset between `.text` and `mapped` is constant within a file. In a module whose sources have no `mapped:` value yet (`menus`, `challenge`), leave it out.
- Units built with `-inline deferred` (every `game`, `menus` and `challenge` unit, and main-DOL units whose `configure.py` entry adds it) list functions in **reverse address order**, highest first: MWCC generates them last to first. `python3 tools/reverse_functions.py <source file>` converts a file still in address order; if it refuses, reorder by hand. Other units list functions in address order.
- Data in the unit's own ranges is defined in the source with the original's values, which the unit's assembly file lists; split any `symbols.txt` entry there, in `.bss` too, that lumps several objects; a split-off object that no code reads keeps the binding of the entry it came from. Initialized `.data` objects are laid out in declaration order, so declare them in address order. Keep each object's binding from `symbols.txt` (`scope:local` is `static`), except that data the target reaches from one pool base must be `static`; mark those entries `scope:local`. All-zero data needs an explicit `= { 0 }` to stay in `.data`. `jumptable_*` objects come from `switch` statements, not hand-written data. Size each `symbols.txt` entry to its object; alignment padding before the next unit stays unnamed (dtk lists it as a `gap_*` symbol), and needs no definition. Unknown struct fields in initialized data are filler arrays of the data's word width (`s32 _10[10]` for `data:4byte`), so the original values fit.
- Prototypes go in the unit's header in address order. Functions and data from other units that no header declares get `extern` declarations at the top of the source file. A global without a header gets a local `extern struct { ... } name;` with only the fields the unit uses, at their offsets. A type only this unit uses is defined in its source file; a prototype in the header that needs it uses a forward `struct` declaration, so give the type a tag (`typedef struct Foo { ... } Foo;`): an anonymous `typedef struct` cannot be declared ahead.
- Use the `symbols.txt` name for every symbol. Rename one only with evidence, such as an SDK function or a string that names it, and then rename it in `symbols.txt` and in every user (`tools/check_symbols.py` finds them). Unknown struct fields are `_XX` with `/* 0xXX */` offset comments.
- Prefer SDK enum names (`GX_TF_RGBA8`) over bare numbers where they compile to the same code, and match the surrounding style. Comments explain what the code cannot: a compiler constraint or a remaining mismatch.

## Integrity

- Call a function matched only when the verdict is `match`, in comments, commits and the report alike.
- Write C a programmer plausibly wrote. Inline asm, casts or pragmas whose only purpose is to steer the compiler, and permuter output pasted verbatim do not count as progress.
- Never change what is measured (compiler flags, splits or objdiff settings) to raise a score.

## Lookups

- Units and their paths: `objdiff.json` (`name`, `metadata.source_path`).
- Symbols and sizes: `config/GYQE01/symbols.txt` for the main DOL; `config/GYQE01/{game,menus,challenge}/symbols.txt` for the RELs. A build rewrites these files (dtk adds `data:` tags), so edit an entry by pattern rather than by its exact old text, and check the result with `grep`; run `ninja` after the edit, since `match.py` rebuilds only the unit's own object and compares against the target objects the last full build split.
- Assembly of whole units: `build/GYQE01/<module>/asm/<module>/<unit>.s`; main-DOL code with no source: `build/GYQE01/asm/auto_*.s`.
- The objects being compared: `target_path` and `base_path` in `objdiff.json`. `build/binutils/powerpc-eabi-objdump -t <object>` lists their symbols, which shows section layout, pool symbols (`...rodata.0`) and weak objects. `ninja -t commands <base_path>` prints the exact compile command for scratch experiments.
- SDK declarations: `include/Dolphin/` (GX enums in `GX/GXEnum.h`, `OSPanic` and `OSErrorLine` in `os.h`); `memset` comes from `"string.h"`.
