# Matching notes

Lessons from matched functions, indexed by the **symptom** `tools/match.py` shows. Find the symptom below, try its causes in order, and add a lesson where that symptom lives when a function teaches you something new (symptom, cause, fix, example). The three large symptom catalogs have their own files; read the one your diff shows.

## `reloc`: a reference points somewhere else

objdiff's report scores these 100% because it ignores relocation targets; the unit cannot link until they are fixed.

- **Placeholder shadows a named symbol.** The source declares its own `extern ... lbl_3_data_XXXX` for an address that `symbols.txt` already names. Look the address up in `config/GYQE01/**/symbols.txt`, use the existing header declaration, delete the placeholder. Example: `calculateHorizontalPower` read `hitTrajOptions` through `lbl_3_data_5B34`.
- **Source is ahead of `symbols.txt`.** The source uses a good name that `symbols.txt` still calls `lbl_...`. Rename it in `symbols.txt` after checking the source type's size equals the symbol's `size:`, then fix every other use of the old name (`tools/check_symbols.py` lists them). Example: `gameInitOptions` and `aILevel` for `setInMemBatterConstants`.
- **Wrong callee or global.** The call or load goes to a different symbol with the same shape. Treat it as a source bug, not a naming issue.
- **`sym+0xNNNN@ha` / `sym+0xNNNN@l` in the target.** MWCC never folds a constant offset into a relocation: `&arr[k]`, `arr + k` and struct members all compile to `addi rX,rX,sym@l; addi rX,rX,k`. So the original referenced a separate object that `symbols.txt` lacks. Split that object out of the lumped `symbols.txt` entry in its own commit (the skill allows this once `regress.py` passes), then declare an `extern` under the new name with the size the code implies. Example: rep_1330's `lbl_8034E9A0+0x4C28` and `+0x4E44`, main-DOL objects at 0x803535C8 and 0x803537E4.
- **`...bss.0` or `...data.0` with offsets in the base.** MWCC addresses a file's statics from one base symbol plus literal offsets (`addi r4,r5,160`, `lwz r3,8(r31)`), so the target's offsets give the layout, and `symbols.txt` often lumps several statics into one symbol. Declare one static per object, in reverse address order (MWCC lays them out in reverse declaration order), including statics nothing in the file reads, and split the symbol in `symbols.txt` to match. One static struct does not reproduce this: it recomputes its base in each branch, while the pool base is computed once. Example: kinoko's `lbl_3_bss_BA00` to `BAA0`. The target may name the base after the file's first object instead (`addi r30,r6,lbl_1_bss_6BD8@l` then `addi r3,r30,992`): those objects are statics too, and the base's `...bss.0` pairs with that name without a relocation difference. In the challenge module every `.data` and `.bss` object of `rep_7730.c` turned out static (`fn_1_21180`, `fn_1_22F4C`, `fn_1_25C68`), and offsets folded into one `addi` from the base showed separate objects lumped in `symbols.txt` (`lbl_1_bss_6FA8`, `lbl_1_bss_43F38`, `lbl_1_data_10468` to `10498`).
- **A pooled `.bss` offset that lands inside a `symbols.txt` entry** (`lbz r0,12018(r6)` from the base `lbl_1_bss_3070`, where 0x2EF2 lies inside dtk's 0x2D51-byte `lbl_1_bss_3218`): a separate static starts there. A field of a static struct is addressed through the struct's own offset first (`addi r5,r6,424; lbz r0,11594(r5)`), never as one displacement from the pool base. List every offset each function reaches from the base with a script over the unit's assembly (base register from `addi rX,rY,base@l`, then each `d(rX)`) and split the entries at those addresses; an array is reached with `addi` to its start. Example: `rep_0610.c` (challenge module), whose 0x3980-byte `.bss` became 50 statics this way and scores 99.87%.
- **One data symbol plus offsets past its size in the target** (`addi r31,r5,lbl_3_data_285A8@l` then `addi r6,r31,0x360`, while the base loads each symbol with its own `lis`/`addi`): the target reaches several objects from one pool base, so they are statics of this file. Initialized `.data` statics are laid out in declaration order (unlike `.bss` above), so declare them in address order. An offset folded into one `addi` means a separate static; `arr[1]` compiles to `addi` of the array start, then the element offset. Extern declarations cannot reproduce this: if the data lies outside the unit's `splits.txt` ranges, keep externs under the `symbols.txt` names and escalate the `.data` range, with a scratch copy that defines the statics as evidence. MWCC pooled a function's accesses when it touched three of these statics and named each when it touched two. A zero-filled static needs an explicit initializer (`static u8 flags[9] = { 0 };`) to stay in `.data`; without one MWCC moves it to `.bss`. Objects the code names on their own can keep their global binding between pooled statics: the layout still follows declaration order (`lbl_3_data_18180` in `rep_2390.c`). Examples: `fn_3_168704` and `fn_3_168DFC` in `rep_3F60.c` (matched once its `.data` was defined there), `fn_3_15BAA0` in `rep_3AE8.c` (matched once its five statics were defined there), `fn_3_C11CC` and `fn_3_C1770` in `rep_1F58.c`. What an extern lacks is the definition, not the binding: `rep_28A8.c`'s `fn_3_DA834`, `fn_3_D9EA0` and `fn_3_DD3FC` reach 0x188E8 to 0x18C48 from one base and matched (apart from the base's name) with every object there defined in the file, all global or mostly static alike; the base is then the section symbol `...data.0`. dtk also names fields inside a static when initialized data points at them (a menu table whose entries hold `&settings._0C`), and lumps what follows each field into that symbol; fold those entries back into the object's own (`lbl_1_data_10908`, three 0x50-byte emitter settings, in challenge `rep_7A28.c`), and generate long initializers from the assembly with a script. objdiff's `.data` score does not catch a wrong value there when the unit's relocations to `.rodata` strings already differ (the weak `dolsqrtf2` constants shift them by 0x10): a mistyped `106000` for `105999` showed only in the link trial, and comparing `objdump -s -j .data` of both objects finds it.
- **A large `.data` range to define before its pooled functions can match:** generate the statics from the unit's assembly with a script (bytes, relocations, `char*` entries as string literals, which `-str readonly` puts in `.rodata`), using the source's existing types where the code already names an object, and compare `objdump -s -j .data` and `-r` of both objects. Challenge `rep_0610.c`'s 56 KB at 0x1DC0 to 0xF588 came out byte-identical and kept all 72 matched functions, although some of them name three statics with their own `lis`/`addi` (`fn_1_D8A0`). Parse a copy of the assembly taken before editing `symbols.txt`: the next build re-splits it, prints byte objects as `.string`/`.ascii`, and adds `gap_` objects, and an object the script then reads as all zeros moves to `.bss` and shifts every pooled `.bss` offset.
- **100% but `reloc`, with a local array's initializer as the only symbol difference** (`@192` against `lbl_3_rodata_214`): dtk sized the `.rodata` symbol with the alignment padding after it, 0x10 for a 14-byte `s16[7]`. Size the `symbols.txt` entry to the object (0xE). Examples: `lbl_3_rodata_214`, `2F4` and `374` for `fn_3_5518` and `fn_3_4A38` in `rep_1C0.c`.

## `...rodata.0` in the base, constants one by one in the target

The base shows `lis rX,...rodata.0@ha; addi` and then `lfs f0,100(rX)`, while the target names each constant (`lfs f0,lbl_3_rodata_418C@l(r4)`). MWCC pools a function's `.rodata` references once it touches enough of them (three float constants alone stayed separate in `fn_3_16D810`; adding a `GXColor` initializer pooled all four).

- **Cause: the original's `.rodata` began with weak objects, which turns pooling off for that section** (observed: with weak objects first nothing in `.rodata` is pooled, while `.bss` statics still are). `game/UnknownHomes_Game.h` defines `SQRT2_LINKAGE extern` before including `math.h`, so `dolsqrtf2` becomes an `extern inline` whose static locals are emitted as weak `_half$localstatic` and `_three$localstatic` even when unused; plain `#include "math.h"` emits nothing. The target's `.rodata` does not show them, presumably because the linker kept one weak copy for the whole module.
- **Fix, only when the base shows `...rodata.0`:** include `game/UnknownHomes_Game.h` above `header_rep_data.h`, as `game_batter.c` does. The `.rodata` section score loses those 0x10 bytes; the code matches. Example: `rep_4138.c`, where this matched `fn_3_16D810` and `fn_3_16DB6C`. The challenge module behaves the same: `rep_7730.c` names every constant one by one only with this include order. `-pool off` also matches such functions but breaks pooled `.bss`, and GC/1.3.2 to 2.7 behave identically, so the include order is the explanation, not the flags.
- The same include matched `fn_3_16B5B4` in `kinoko.c`, which pooled once an inlined callee added string literals.
- **When nothing needs unpooled constants, include `header_rep_data.h` first.** That puts `repHeaderData` at offset 0 as in the target and scores `.rodata` higher (92% against 86% in `rep_F80.c`); every function matched with either order.

## `.rodata` below 100% with every function matched

- **Literal constants in the reverse of the target's order:** the source lists functions in address order. With `-inline deferred` MWCC generates functions last to first (objdiff's `reverse_fn_order` hides this for `.text`) and creates each function's constants as it goes, so REL source lists functions from the highest address down; `tools/reverse_functions.py` converts a file. Example: rep_940 `.rodata` 83% to 93%.
- **Avoid them when the unit needs nothing from `game/UnknownHomes_Game.h`:** include only what it uses (`Dolphin/vec.h`, `static/UnknownHomes_Static.h`); `.rodata` then scores 100%. Example: `rep_3C80.c`, 92.31% to 100%.
- **A constant of one expression created after the others** (`0.5f` first in the base's `@` numbering and in `.rodata`, last of `512.0f`, `100.0f`, `1280.0f`, `0.5f`, `256.0f` in the target): the source halved with `/ 2.0f`, which MWCC turns into `* 0.5f` after the front end has created the other constants. Write repeated subexpressions in place too (`(100.0f + task->_24) / 100.0f` twice, CSE'd), since a local computed first creates its constants first. Example: `fn_3_C1C18` in `rep_1FD8.c` (93.57% to 95.95%).
- **The weak `dolsqrtf2` constants** (0x10 bytes, from `game/UnknownHomes_Game.h`) stay as a difference; the linker keeps one copy for the whole module, rep_0's: that target's `.rodata` begins with `_half` and `_three`, so `rep_0.c` includes `game/UnknownHomes_Game.h` above `header_rep_data.h` and scores 100%. In `menus` and `challenge` the kept copy is at `.rodata` 0x0, named weak in `symbols.txt` and owned by `rep_0010`, so a unit with the include links anyway; the 0x10 bytes only lower its `.rodata` score (menus `rep_0B08` links at 97.62%). The explanation above is incomplete: in `rep_10E8`'s target, `_half` and `_three` are local objects in the middle of `.rodata` (0x1140, 0x1148), yet its constants are unpooled and the include order still matched. Menus `rep_0B08` is another such case: its target keeps `0.5` and `3.0` as plain constants at 0xB78 and names every constant, and only `game/UnknownHomes_Game.h` above `header_rep_data.h` unpooled them (`fn_2_698EC`); `.rodata` scores 97.62% with all 138 functions matched.
- **A local array's initializer symbol larger than the copy the function makes** (dtk lumps the unreferenced bytes after it into one symbol, here `lbl_3_rodata_224` at 0xD0 bytes where the code copies 0x38): the function declared more initialized local arrays than it reads. MWCC drops the copies of unused locals but keeps their `.rodata` initializers, in declaration order and 4-aligned. Declare them with the original's element types and sizes between the used ones; size each used array's `symbols.txt` entry to its object (an `s16[7]` is 0xE). Example: `fn_3_4A38` in `rep_1C0.c` (`.rodata` 29% to 98%).

## `.data` or `.bss` below 100% with every object defined

- **An all-zero object in the target's `.data`:** define it with an explicit initializer, `static T x = { 0 };`, which MWCC keeps in `.data`; without one it goes to `.bss`. Example: `lbl_3_data_28928` in `kinoko.c`. A scalar does not stay there even with `= { 0 }` (`u8 x = { 0 };` went to `.bss`), and a one-element array is 4-aligned: an unreferenced zero byte right after a `u8` in `.data` belongs to it, `u8 lbl_1_data_FBC[2] = { 1, 0 };` (challenge `rep_0250.c`, where dtk had split it off as `lbl_1_data_FBD`).
- **A trailing `gap_..._data` symbol, or a last object larger than its type:** the linker padded the section up to the next unit's alignment (8 for `.data`, 32 for kinoko's `.bss`). Leave it; no source object belongs there. To confirm, `objdump -s -j .data` of both objects differs only in trailing zeros the base lacks. Examples: `rep_3F60.c` scores `.data` 99.78% (4 bytes at 0x28924); `rep_3E58.c` scores `.data` 98.73% (4-byte `gap_04_000285A4_data` after the jump table) and `.bss` 50% (`lbl_3_bss_B9E0` is an `s8` with size 0x20 in `symbols.txt`). A `switch` jump table needs no definition: MWCC emits it as `@NNN` and objdiff pairs it with `jumptable_...`.
- **Jump tables scored unmatched though their entries name the same labels** (`objdump -r -j .data` shows identical `fn+0xNN` relocations in both objects): objdiff 3.4 evidently compares a data relocation's target by address, so every table after a function whose size differs counts as unmatched, its own function's table included. Compare the functions' sizes in `objdump -t` of both objects; `.data` rises only when every function up to the last `switch` has the target's size. Example: `rep_36D8.c` `.data` stays at 2.38% (only `lbl_3_data_265F0`) because `fn_3_13C7BC` and `fn_3_140CE0` are each 4 bytes longer than the target, though `fn_3_141A30`'s table is identical.
- **A `gap_*` symbol between two objects** (3 bytes after a `u8`, before a 4-aligned object): alignment padding inside the file; objdiff counts it as unmatched, so the section stays below 100%. Leave it. Example: `rep_4138.c` `.bss` 88.46% from `gap_05_0000D6E1_bss` and `gap_05_0000D6ED_bss`.
- **An object larger than everything the code touches, ending at the unit's end on no alignment boundary:** the tail is a separate unreferenced object, not padding. Check a `memset` or loop bound for the real size, split the `symbols.txt` entry, and declare the tail too (MWCC keeps unreferenced statics). Example: `lbl_3_bss_D6F0` was 0x24, but `memset` clears 0x18; the last 0xC became `lbl_3_bss_D708` (`rep_4138.c`, `.bss` 66.67% to 88.46%). Likewise the 8 bytes `3, 0` after `rep_2308`'s four 0x28-byte draw entries became `lbl_3_data_17DB8`.
- **A pooled static landing one byte off its target offset after an unreferenced gap:** MWCC aligns a `u8` array of four or more bytes to 4, so a gap that starts at an odd offset cannot be one array. Declare a `u8` for the odd byte and the array after it. Example: `lbl_3_bss_AE53` and `lbl_3_bss_AE54[0x27]` in `sta_c6.c`, which put `lbl_3_bss_AE7B` at 0x2B for `fn_3_E7424`. Arrays of two and three `u8` were 4-aligned too: `rep_1FD8.c`'s unreferenced bytes 0x9DE1 to 0x9DE3 and 0x9DE5 to 0x9DE6 (around the `u8` statics 0x9DE0, 0x9DE4 and 0x9DE7) fit only as single `u8` statics, which put the pooled `lbl_3_bss_9DE8` at 0x68 for `fn_3_C3C2C`.

## Linking: the hash check fails after flipping a unit to `Matching`

Compare the built module with the original (`build/GYQE01/game/game.rel` against `orig/GYQE01/files/game.rel`): each section's bytes, its length, and the relocations decoded per source offset. Map the first differing offset to a symbol with `symbols.txt` and to a unit with `splits.txt`. A section length that differs, or every relocation into `.bss` past some address moving by 0x20, points at a size or alignment error in the first unit before that address.

- **Two float constants swapped in `.rodata`:** MWCC creates a function's constants in the order its code is generated before scheduling, so the final load order does not show it. A term kept in its own variable is generated as its own statement, ahead of the expression that uses it. Fix by folding the term into the expression or splitting it out, whichever puts the target's first constant first, and recheck the function. Examples: `fn_3_14A4` in `rep_140.c` (linear term folded into the return made 3.0f precede 2.0f), `fn_3_15C024` in `rep_3AE8.c` (scaling the call's result by 0.00005f in a second statement made the call's 1.0f and 100.0f come first).
- **A unit's `.data` starting 4 bytes off an 8-byte boundary:** MWCC aligns every `.data` and `.bss` section to at least 8, so the linker places the object 4 bytes later and everything after it moves. If those 4 bytes are zero and follow the previous unit's last object, they are padding: start the unit's first object 4 bytes later in `symbols.txt` and drop the zeros from its definition. Example: `rep_1770.c`'s `lbl_3_data_F4A4` became `lbl_3_data_F4A8` (0x28 bytes). The section score stays below 100% until `splits.txt` starts the range there.
- **A unit's `.data` range starting with zero bytes before a 32-aligned object** (dtk's `pad_..._data` symbol at the range start, and `reloc` on the pool base: the target's `lbl_X` at `.data+0x10` against the base's `...data.0` at `.data+0`): an object of the file is `ATTRIBUTE_ALIGN(32)` (a `GXSetArray` colour table), so the whole section is 32-aligned and the linker padded up to it from the previous unit's end. Define the objects from the first named one; the function stays `reloc` until `splits.txt` starts the range at the aligned address. Example: challenge `rep_00B0`, whose `.data` range starts at 0x1F0 and whose first object is at 0x200 (`fn_1_19AC`).
- **`.bss` shorter than the unit's range:** padding to the next 8-byte boundary is at most 4 bytes, so more than that between the last object and the next unit is an unreferenced static of this unit; so is a byte before a `u8` that the target puts at offset 1. Declare them (in reverse address order, like the other `.bss` statics) and split `symbols.txt`. Examples: `lbl_3_bss_B9BC` (0x24) in `rep_3D50.c`; `lbl_3_bss_1900` and `lbl_3_bss_9944` (0xC) in `rep_1D58.c`. A struct of bytes does not fill such a tail from an odd address either: MWCC 4-aligns it like a byte array, so a 0x13-byte struct for menus `rep_0DE0`'s `lbl_2_bss_B2A5` landed at 0xB2A8. The tail there was a separate 0x10-byte object at 0xB2A8 after the one-byte `B2A5`; with it the unit linked. The 4-byte bound holds only after 4-aligned objects: menus `rep_0A08`'s `.bss` is one `u16` (`lbl_2_bss_9E08`, read and written with `sth` only) in an 8-byte range, and it linked with that alone, the 6 bytes after it being padding (`.bss` scores 66.67%).

## Unit boundaries: evidence for a `splits.txt` proposal

- **One object per `repHeaderData`.** Every game object starts its `.rodata` with its own copy of `header_rep_data.h`'s 0x50-byte `repHeaderData`, and units are named after where that copy sits. The module has 92 copies and 92 units, so code outside every unit's range is the tail or head of a neighbouring unit, not an object of its own. A unit with no code yet (`rep_A78`, `rep_D68`) is still one object.
- **Jump tables close an object's `.data`, and each object's `.data` starts on an 8-byte boundary.** Zero padding before an 8-aligned run of tables marks a boundary (`0x10A30` after `fn_3_B482C`'s table). Proven with test files compiled with the game's flags.
- **One base register reaching several objects proves they share a file; one group of readers does not.** The block 0x8110–0xD5B8 holds tables read only by single units' functions, yet lies outside those units' `.data` (rep_1770, rep_16B8, rep_3A48, rep_3448).
- **A run of jump tables holds an object boundary only where a table starts 8-aligned.** A table starting 4 off 8 belongs to the previous table's object, so one table that sits in a known unit pulls every later function whose table follows it at 4 off 8 into that unit: menus `rep_0AB0`'s tables at 0x29970 to 0x2A1E4 made its code run to 0x68260, far past its `.rodata` readers. The same check settles lumped data: a symbol 4 off 8 that only one unit reads puts that unit's object start at or before the 8-aligned address below it (`lbl_2_bss_AE0` split at 0x1220 for menus `rep_0568`'s 0x1224).
- **`.bss` past the objects' statics holds commons.** In menus, `.bss` from 0xB644 holds globals aligned per symbol, not per object (0x1010C and 0x10164 sit 4 off 8 yet belong to different units), so the 8-byte rule applies only below 0xB644; a common read by one unit's functions alone is still evidence that ties a neighbouring function to it (0x1A8240 and menus `fn_2_5853C`).
- **An object among units with only `repHeaderData` has no observable owner.** Every copy of `repHeaderData` is identical, so when a run of such units holds fewer objects than units, which unit owns each object cannot be read from the binary; moving it within its run changes nothing in the build. Bound the object by evidence and name the convention in the commit (menus `rep_0C50`, `0CA0`, `0CF0` took the three objects between `rep_0B08` and `rep_0DE0`).
- **A pool base below the unit's `.data` range:** rep_16B8's `fn_3_96CA4` and `fn_3_91FC4` reach `lbl_3_data_BE50`, `BF18`, `BF2C`, `EE5C`, `F1FC`, `F20C` and `F430` from the base `lbl_3_data_8D88` (offsets 0x30C8 to 0x66A8), so one object's `.data` starts at 0x8D88 and runs past 0xF430, across rep_1610's 0xD5B8 range; a copy of `rep_16B8.c` defining 0x8D88–0xBF6C before its own data matched `fn_3_96CA4` apart from the base's name. Yet `fn_3_9894C` names `D648`, `D7E8` and `D860` one by one, unexplained.

- **A small function at the start of a unit's `.text` that its callers there call with `bl`, while MWCC inlines it into them from the same file:** it is the previous unit's last function. Challenge `fn_1_4DD8` (0xC0, the first function in `rep_0138`'s range, which fills the collision table `rep_00B0` reads) is inlined into `fn_1_717C` and, through it, `fn_1_6848`; no statement count kept it out. Moving it into `rep_00B0.c` (its `.text` now ends at 0x4E98) matched `fn_1_717C` and took `fn_1_6848` from 86% to 98.88%; `rep_00B0` still matches and links.
- **A function inlined into one of the unit's functions belongs to its object, even outside its `.text` range.** Menus `rep_04B0`'s `fn_2_14220` inlines `fn_2_13BA4` and `fn_2_13CA0` from the unassigned 0x13BA4–0x13D70 (written as `static inline` in `rep_04B0.c`); a scratch copy defining them as plain functions compiled both byte-identical to the originals.
- **A small same-file callee that the target calls with `bl` puts the caller in another file.** Under `-inline auto` MWCC inlines a function of a few statements into every caller in its file, so a tail whose calls to a unit's tiny functions stay `bl` is not that unit's. rep_8C8's head 0x1E154-0x1E3EC calls `fn_3_20A60`, `fn_3_20AB0` and `fn_3_20AE0` (7-8 stores each); written in `rep_8C8.c` those get inlined, while with their bodies outside the file `fn_3_1E154`, `fn_3_1E178` and `fn_3_1E328` all match, also in a scratch copy of `rep_868.c`. A call into a large function (`fn_3_20224`) proves nothing either way.
- **A `.bss` or `.data` range that starts 4 off 8 cannot link:** MWCC aligns each section to 8, so the object lands 4 bytes later. rep_2390's `.bss` at 0x9FDC built at 0x9FE0 and failed the hash; starting it at 0x9FD8, with sta_c0's unreferenced `lbl_3_bss_9FCC` cut to 0xC and an unreferenced 4-byte static at 0x9FD8, linked.
- **Copies of the menus debug tables do not count objects.** The 0x2C4-byte block of debug menu labels that starts with "BAT FIRST" appears in many menus units, and one object can hold two: `rep_04B0`'s `.data` has copies at 0x19E8 and 0x1E28, while `fn_2_16460` and `fn_2_16724` share `.rodata` constants (one object). Nothing reads the block; `rep_0318.c` names its nine objects.

## Before committing

- Run `tools/match.py` on every function that uses a type, prototype or symbol you changed, not only the one you were fixing.
- Run `python3 tools/regress.py`; it fails on any dropped objdiff score or lost strict match. Its summary goes in the pull request.

## Tool pitfalls

- Install m2c from https://github.com/matt-kempster/m2c. The PyPI package named `m2c` is an unrelated project.
- `match.py --m2c` prepares the unit's context for m2c (preprocesses it and strips inline asm); the draft is typed only for globals the source's includes declare, so a placeholder file including only `header_rep_data.h` gives `?` types until you add `game/UnknownHomes_Game.h` and the like.
- `match.py` reports a function you have written as `missing` when objdiff cannot pair it, for example after a callee's empty stub was inlined into it; give the callee a body first. If the callee has a body and is still inlined where the target calls it, see "A callee inlined in the base but called with `bl` in the target" in [`structure.md`](matching-notes/structure.md).
- `match.py <unit>` does not build the unit's type context (`build/GYQE01/src/<path>.ctx`); `match.py <unit> <function> --m2c` without `--no-build` does (or `ninja` that `.ctx` path). Build it once before batching `--m2c --no-build`, or every draft says it ran without type context.
- decomp-permuter's own `import.py` breaks on this project; `tools/permute.py` explains why in its header and replaces it.
- `tools/permute.py` fails to compile its view when the source has `sizeof(T) + (x)`: pycparser reads it as `sizeof((T) +(x))`, a cast. Parenthesize the product, `(20 * sizeof(T)) + (...)`, which compiles the same.
- The same happens with `sizeof(T) * 2` (read as `sizeof((T)(*2))`). Put the constant first, `(count - k) * (2 * sizeof(Vec))`; check the score afterwards, since `(count - k) * 2 * sizeof(Vec)` does not fold to one `mulli` (`fn_3_67EF0` in `rep_EA0.c`).
- A scripted batch that edits the source with a plain string replace also edits every other function holding the same text, which sibling functions in one unit often do; require each pattern to occur once (`fn_3_D60C0`'s variant changed `fn_3_D5E80` and `fn_3_D5C8C` in `sta_c2.c` until `regress.py` caught it). Find the function by its definition line, not by the first `name(`: in a file in reverse address order that is often a caller, and a batch edited `fn_2_478F4` in place of `fn_2_47540` (menus `rep_08E8.c`).
- `match.py --m2c` gives no draft for a `switch` whose jump-table address is formed outside the dispatch loop ("Unable to determine jump table"). Run m2c on a copy of the assembly with the table's `lis`/`addi` moved next to the `bctr` (`fn_3_FDB30` in `rep_3090.c`).
- For scripted batches of variants, `match.py <unit> <function> --source <copy>` compiles the copy into a temporary directory (about 0.2 s) and scores it there, leaving the source and the build directory alone, so a batch can run in the background while you edit and run `match.py` on the real source. Repeat `--source` with a header copy to vary a prototype as well: a `.h` file replaces the header of the same name under `include/` for that run. Where two modules have a header of that name (`rep_0010.h` in `menus` and `challenge`), name the one it replaces, `copy.h=include/challenge/rep_0010.h`. A batch running in the background reads the live headers otherwise, so pass it a copy of the unit's header taken when it starts: an edit to the header mid-batch failed every later variant of a 720-variant batch (`rep_E08.c`). Copy the whole file: a copy holding only the declarations and the one function allocated `fn_3_DF608` (`rep_28A8.c`) differently from the full build, while the whole-file copy agreed with it and also showed which callers inline what.
- A permuter output can beat the base with the target function's body unchanged: the output drops the file's other functions, and inlining and allocation then differ. Diff only the target function's body before trusting a score (`fn_3_67620` in `rep_EA0.c`: 245 against 390, same body).
- m2c drafts an extra parameter (`arg4`) when a local is read on some path before it is set: the register it reads is whatever the caller left. Check the callers' argument setup before adding the parameter; `fn_3_4197C` (`rep_AC8.c`) keeps the nearest fielder's index uninitialised, and its callers set only `r3`.
- `tools/permute.py` fails with a syntax error on `va_arg(args, s32)`, because pycparser cannot parse MWCC's `_var_arg_typeof`. For the permuter run only, write `*(s32*)__va_arg(args, 1)` (the same code), and restore `va_arg` afterwards.
