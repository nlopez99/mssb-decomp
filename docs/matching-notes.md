# Matching notes

Lessons from matched functions, indexed by the **symptom** `tools/match.py` shows. Find the symptom, try its causes in order, and add a lesson here when a function teaches you something new (symptom, cause, fix, example).

## `reloc`: a reference points somewhere else

objdiff's report scores these 100% because it ignores relocation targets; the unit cannot link until they are fixed.

- **Placeholder shadows a named symbol.** The source declares its own `extern ... lbl_3_data_XXXX` for an address that `symbols.txt` already names. Look the address up in `config/GYQE01/**/symbols.txt`, use the existing header declaration, delete the placeholder. Example: `calculateHorizontalPower` read `hitTrajOptions` through `lbl_3_data_5B34`.
- **Source is ahead of `symbols.txt`.** The source uses a good name that `symbols.txt` still calls `lbl_...`. Rename it in `symbols.txt` after checking the source type's size equals the symbol's `size:`, then fix every other use of the old name (`tools/check_symbols.py` lists them). Example: `gameInitOptions` and `aILevel` for `setInMemBatterConstants`.
- **Wrong callee or global.** The call or load goes to a different symbol with the same shape. Treat it as a source bug, not a naming issue.
- **`sym+0xNNNN@ha` / `sym+0xNNNN@l` in the target.** MWCC never folds a constant offset into a relocation: `&arr[k]`, `arr + k` and struct members all compile to `addi rX,rX,sym@l; addi rX,rX,k`. So the original referenced a separate object that `symbols.txt` lacks. Split that object out of the lumped `symbols.txt` entry in its own commit (the skill allows this once `regress.py` passes), then declare an `extern` under the new name with the size the code implies. Example: rep_1330's `lbl_8034E9A0+0x4C28` and `+0x4E44`, main-DOL objects at 0x803535C8 and 0x803537E4.
- **`...bss.0` or `...data.0` with offsets in the base.** MWCC addresses a file's statics from one base symbol plus literal offsets (`addi r4,r5,160`, `lwz r3,8(r31)`), so the target's offsets give the layout, and `symbols.txt` often lumps several statics into one symbol. Declare one static per object, in reverse address order (MWCC lays them out in reverse declaration order), including statics nothing in the file reads, and split the symbol in `symbols.txt` to match. One static struct does not reproduce this: it recomputes its base in each branch, while the pool base is computed once. Example: kinoko's `lbl_3_bss_BA00` to `BAA0`.
- **One data symbol plus offsets past its size in the target** (`addi r31,r5,lbl_3_data_285A8@l` then `addi r6,r31,0x360`, while the base loads each symbol with its own `lis`/`addi`): the target reaches several objects from one pool base, so they are statics of this file. Initialized `.data` statics are laid out in declaration order (unlike `.bss` above), so declare them in address order. An offset folded into one `addi` means a separate static; `arr[1]` compiles to `addi` of the array start, then the element offset. Extern declarations cannot reproduce this: if the data lies outside the unit's `splits.txt` ranges, keep externs under the `symbols.txt` names and escalate the `.data` range, with a scratch copy that defines the statics as evidence. MWCC pooled a function's accesses when it touched three of these statics and named each when it touched two. A zero-filled static needs an explicit initializer (`static u8 flags[9] = { 0 };`) to stay in `.data`; without one MWCC moves it to `.bss`. Objects the code names on their own can keep their global binding between pooled statics: the layout still follows declaration order (`lbl_3_data_18180` in `rep_2390.c`). Examples: `fn_3_168704` and `fn_3_168DFC` in `rep_3F60.c` (matched once its `.data` was defined there), `fn_3_15BAA0` in `rep_3AE8.c` (matched once its five statics were defined there), `fn_3_C11CC` and `fn_3_C1770` in `rep_1F58.c`. What an extern lacks is the definition, not the binding: `rep_28A8.c`'s `fn_3_DA834`, `fn_3_D9EA0` and `fn_3_DD3FC` reach 0x188E8 to 0x18C48 from one base and matched (apart from the base's name) with every object there defined in the file, all global or mostly static alike; the base is then the section symbol `...data.0`.
- **100% but `reloc`, with a local array's initializer as the only symbol difference** (`@192` against `lbl_3_rodata_214`): dtk sized the `.rodata` symbol with the alignment padding after it, 0x10 for a 14-byte `s16[7]`. Size the `symbols.txt` entry to the object (0xE). Examples: `lbl_3_rodata_214`, `2F4` and `374` for `fn_3_5518` and `fn_3_4A38` in `rep_1C0.c`.

## Registers only: same instructions, different register numbers

- **Shared across functions.** When several functions show the same unexplained allocation while identically written ones match, look at what they share before tweaking each: a prototype's parameter or return type changes the compiler's internal conversions and so its allocation, with identical instructions. Example: `minigame_checkIfAIInputIs_Algorithmic_Or_ControllerBased(u8)` should take `s8` (callers pass `s8 characterIndex[]`); that fixed three functions.
- **`int` against `s32` in a prototype.** `s32` is `long`, so MWCC converts between it and `int` even though the code is the same, and the conversion moves allocation. `fn_3_28E4` (`rep_140.c`) had `count` and a saved address swapped (r29/r30) until the callee `fn_3_1B24` took `int count`; the permuter pointed there with casts on that one argument. Recheck the callee: its second loop then tested `cmpwi r8,1; ble` against the target's `li r12,1; cmpw r12,r8; bge` until its counter became `s32 i`, and `fn_3_155C` needed `int` for both.
- **Declaration order.** The order locals are declared in affects which register each gets, volatile or callee-saved; try moving the variable that lands in the wrong register above its neighbour. Example: `inputs` declared before the `BOOL` flag. Search the orders again after any other fix: `fn_3_15FB84`'s `n` and `player` (r9 and r11 swapped) matched only once declared `n`, `marker`, `offset`, `player`, though an earlier search over the same four, made on an earlier version of the function, found nothing. Moving one declaration at a time can stall where swapping two distant ones still helps: `fn_3_FA58C` (`sta_c4.c`) gained nothing from any single move at 99.49% but reached 99.59% with `slot` and `indices` exchanged, so script every pairwise swap too.
- **Statement order of independent loads.** Which register a shared base (`addi r10,r3,sym@l`) gets depends on where its first use sits among the statements that read through it. Example: `fn_3_CABF0` in `rep_2308.c` matched once `model = &bss._010->_C4;` moved above the six local-array fills, written as `ids[i]`, `anims[i]` pairs in the target's store order.
- **Volatile registers differ in a function's setup code** (`lbz r0,30(r27)` against `lbz r4,30(r27)` for the same field): the statement order of independent setup assignments decides them. Script every order of the first few assignments, crossed with a few declaration orders; that is a dozen runs. Example: `fn_3_168A6C` matched only as `model`, then `anim`, then `animData` assigned, with `animData` declared first. The same order decides how the whole entry block is scheduled: `fn_3_15FB84` went from 86% to 97.7% when a float local was computed after the first of three stores instead of before them.
- **A value loaded once.** Holding a repeated load in its own local (with the type of the expression, usually `int`, not the field's `u8`) changes allocation. Example: `slapContactSize` in `calculateBuntHorizontalAngle`; `u8 status = g_GameLogic.gameStatus;` tested by an `if` and a later `switch` in `fn_3_E1478`.
- **Operands swapped in an add** (`add r31,r31,r0` versus `add r31,r0,r3`): split the expression, e.g. `value = tex[i]; value += step * 2;`. Example: `fn_3_16943C`.
- **An `add` of a float-to-int conversion and a table value with the conversion second** (`lwz r0,12(r1); add r0,r10,r0` where the target has `add r0,r0,r10`): MWCC puts the loaded value first for both `(int)(d * t) + lo` and `lo + (int)(d * t)`. Hold the converted value in an `int` local, and the difference before it too: `range = hi - lo; offset = range * t; z = offset + lo;`. The `range` local also fixed where the index of `t` was loaded. Example: `fn_3_20224` in `rep_8C8.c` (`range` found by the permuter).
- **A derived value written to a new register** (`subf r3,r4,r6; subf. r3,r0,r3` where the base reuses the variable's register, `subf r6,r4,r6`): the original computed it into a second local, `left = frame - total; left -= charged; if (left <= 0 ...)`. `frame -= total;` reuses `frame`'s register, and one expression gives other allocations. Example: `fn_3_1EFE4` in `rep_8C8.c`.
- **A comparison used as an index allocated differently** (`subfic r3,r4,1; subi r0,r4,1; or r4,r3,r0` with the operand registers swapped): assign it to a local first, `late = early == 1 ? 0 : 1;`, then index with `late`. Writing `table[early != 1]` in place gives the same instructions in other registers. Example: `fn_3_1EAA8` in `rep_8C8.c`.
- **Float values loaded into swapped registers for stores that copy and offset them** (`lfs f3,32(r5)` against `lfs f2,32(r5)` before `stfs` to one struct and `fadds` into another): compute the second store from the field just stored, `b.pos.x = b.pos2.x + offset;` after `b.pos2.x = ai.box;`, not from the source global again. Example: `fn_3_1F998` in `rep_8C8.c`.
- **Operands swapped in an `fmadds`** (`fmadds f0,f2,f1,f0` against `f0,f1,f2,f0`): swapping or regrouping the C operands changes nothing. Compute the multiplicand into a local first: `t = min + range * rand() / 32767.0f; x = t * (n - i) + i;`. Example: `fn_3_15BAA0`.
- **The products of a two-term blend computed in the other order** (`fmuls` of one product, then `fmadds` folding in the other): MWCC computes the right-hand product of `a * b + c * d` with `fmuls` and folds the left one into the `fmadds`, so swap the terms. `fn_3_E5CBC` (`sta_c6.c`) matched as `(1.0f - t) * to->r + t * from->r`, with `to` and `from` read into locals before the clamp of `t`.
- **Operands swapped in an `fmuls` by a constant, product in a new register** (`fmuls f1,f2,f1` with the constant in `f1`, against `fmuls f1,f1,f2`): MWCC puts the literal first in both `s = s * K` and `s = K * s`, while `s *= K` keeps the order but writes the product back into `s`'s register. Passing both through `math.h`'s inline `scaleValue` keeps the order and gives a new register: `scale = scaleValue(a / 512.0f, 0.27208483f);`. Example: `fn_3_6CD88`; in `fn_3_15C3F8` (`rep_3B70.c`) `half *= 0.5f` also merged the stack slots of two int-to-float conversions, shrinking the frame by 0x10. For an `int` variable, `dx = a - b; dx *= 0.2f;` keeps the constant second (`fmuls f1,f1,f31`) and converts back to `int`, where `dx = (int)(a - b) * 0.2f;` puts it first: `fn_3_E9D30` (`rep_2BF8.c`). A negated operand behaves the same: `angle = -obj->_B0; angle = 0.017453292f * angle;` put the negation and the constant in the target's registers where `angle = 0.017453292f * -obj->_B0;` swapped them (`fn_3_E2F4C` in `rep_2998.c`).
- **Two loads in swapped registers feeding two stores** that already come out in the target's order: swap the two assignment statements. The scheduler keeps the store order, but allocation follows statement order. Example: the `_00` and `_10` stores before `fn_8002CE4C` in `fn_3_15BAA0`.
- **Operands swapped in a branchless `or`/`or.` chain** (`cntlzw; srwi; or; or.` tests): reorder the operands of `|` in the condition; each order gives a different pairing. Example: `fn_3_16E1EC` matches only as `lbl_3_bss_D6EC | !lbl_8036E548._3088 | !lbl_3_bss_D6E4`.
- **A loop with more counters in the target than the source has variables** (a register counting 16 to 22 that the loop test compares, `cmplwi r19,23`, beside one counting from 0 for an index, `addi r0,r17,16; mulli`, and a copy of a running count, `mr r18,r29` before the loop, incremented beside it): MWCC does not derive such counters from `i + 16` or from `n`, so each was its own variable, `for (k = n, j = 16, i = 0; j < 23; j++, i++, k++) { entry->_C0 = k; entry->type = j; ... models[i + 16] ... n++; }`. Example: the third loop of `fn_3_E7B20` (`sta_c6.c`, 99.50% to 99.98%).
- **A loop counter in the register that held a parameter before a call** (`mr r31,r3` at entry, later `li r31,0` for the loop): the loop reuses the parameter, `for (idx = 0; idx < 2; idx++)`; a new `i` gets a volatile register. Example: `fn_3_C0C4C`.
- **Two local arrays at swapped stack offsets, or their initial values loaded into different registers:** the array declared later gets the lower address, and the order of the statements that fill them decides the registers. Example: `fn_3_C095C` needs `u32 animIds[2]; UnkAnim1F58* anims[2];` filled as `animIds[0]`, `anims[0]`, `animIds[1]`, `anims[1]`.
- **A parameter and another long-lived value swap callee-saved registers** (`mr r28,r3` at entry against `mr r27,r3`, with every use renumbered) and declaration order changes nothing: the original took the parameter as `void*` and copied it into a typed local. Callbacks stored in a function pointer are written this way: `void fn(void* arg) { UnkDraw3CE0* draw = arg; ...`. Example: `fn_3_15FF28` in `rep_3CE0.c`. The same form also orders an inlined callee's entry: `fn_3_E6A48` (`sta_c6.c`), which nothing references, formed its pool base before the first call's stack argument (`addi r31` before `addi r3,r1,8`) until it took `void* arg` like the callback `fn_3_E6D90`, which inlines the same `fn_3_E5A84`.
- **A block that several functions repeat gets its loop's saved registers in another order** (the counter in r25 and its strength-reduced offsets in r26 and r27, where the target has the counter in r27): the block is an inline function with its own loop counter. Write it once as `static inline` and call it; a parameter can carry the one value that differs between copies. Example: `fn_3_24DBC(mode)` in `rep_A00.c`, inlined into six state machines (`fn_3_234BC` went from 97.2% to a match); it was a `static inline` until the `.text` split reached its standalone copy at 0x24DBC, and as a plain function `-inline auto` still inlines it.
- **Counters of a nested loop in swapped registers** (the target's outer counter in r27 and inner in r30, the base's the reverse) while the function's other loops already match: the variable those other loops use is the inner counter. `fn_3_169984` in `kinoko.c` matched with `for (j = 0; j < 148; j++) for (i = j + 1; i < 149; i++)` around loops over `i`, not with `i` outer. When declaration order changes nothing and the function reuses one counter across many loops, the outer counter of one nest had its own variable: `fn_3_16230C` (`rep_3DA8.c`) matched with `for (fielder = 0; fielder < 9; fielder++)` around `j`, where reusing `i` swapped r14 and r15; in the same nest `for (k = 0, flags = 0; k < 5; k++)` put `k` and `flags` in place.
- **Volatile registers of a nested loop differ, including the pointers MWCC strength-reduces** (a walking `slot` pointer in r11 where the target has r5): index the array in each statement, `lbl_80354720[t][i].slot = j;`, instead of advancing a pointer; MWCC then creates the induction pointers in the target's registers. Search declaration orders afterwards. Example: `maybeProcessTeamData` in `rep_0.c` (97.97% with a pointer, 98.57% indexed, matched with `order` declared before `i`, `j`, `t`). The same holds for saved registers: `fn_3_FA3C0` (`sta_c4.c`) went from 96.64% to 97.64% with `lbl_3_data_1BA98[j].group` in place of `prop->group` and `prop++`.
- **Block scope moves a volatile register too.** Declaring a loop-only variable inside the loop body changes its register: in `fn_3_15FB84`, `player` declared in the loop took r11 as in the target, though `n` and `marker` then swapped. The function matched through declaration order instead (above).
- **Float registers differ around `sin`/`cos` calls** (hoisted loop constants assigned to saved FPRs in a rotated order, or `frsp f1,f1` where the target has `frsp f0,f1`): the original called the `sinf`/`cosf` inlines, not `(f32)sin(x)`. Use `sinf_kludge`/`cosf_kludge` from `stl/math.h`; the permuter found nothing in 9000 iterations. Example: `fn_3_167178` and `fn_3_1674D0` in `rep_3E58.c`. The same fix applies when the base keeps a field in a saved FPR across `bl cos` and the target reloads it after the call (`lfs f3,180(r31)` after `bl cos`): `fn_3_E2F4C` and `fn_3_E3044` in `rep_2998.c`.
- **The inlined callee's argument shares a register with the variable it is loaded from** (`lwz r31,20(r31)` loading `task->_14` over `task`, while the base keeps `task` in r30): put the arguments in locals in the target's evaluation order, `id = table[rand() % n]; player = task->_14; fn_3_166C30(player, id);`. Example: `fn_3_166E04` and `fn_3_166FCC`.
- **An inlined callee's registers differ only where it is inlined** (the callee matches standalone): rewrite the callee in another form that compiles the same standalone and recheck its callers. Reusing the parameter (`idx *= 16;` instead of `s32 row = idx * 16;`) fixed the second of `fn_3_C0D10`'s two inlined copies in `fn_3_C1344` (`rep_1F58.c`) and left the first, and the copy in `fn_3_C1004`, unchanged.
- **A loop counter and a loaded pointer in swapped callee-saved registers** (`li r21,0` and `lwz r22,...` in the target, the reverse in the base) while declaration order, block scope and extra pointer locals change nothing: the original tested the array element before copying it, `if (lbl_8036E548._2C50[i] == NULL) continue; actor = lbl_8036E548._2C50[i];`, not `actor = ...; if (actor == NULL)`. The code is the same; the permuter found it. Example: `fn_3_6B144` in `rep_FE0.c`.
- **A limit copied with `mr` inside the branch in the base** (`lha r3,10(r31); cmpw r5,r3; ...; mr r4,r3`), where the target loads it straight into the variable's register and compares that (`lha r4,10(r31); cmpw r3,r4`): the variable was assigned inside the condition, `if (y <= (py = lim[5])) { ... } else if (y >= (py = lim[7])) { ... } else { py = y; }`. Assigning it before the `if` or inside the branch both differ. Example: `fn_3_E9D30` in `rep_2BF8.c`.
- **A chain of masks and remainders kept in the loaded value's register in the target** (`clrlwi r0,r0,17; ... subf r0,r3,r0; clrlwi r0,r0,16`), where the base moves the masked value to a new register: the original reassigned one `u16` variable, `code &= 0x7FFF; code %= 2116;`, instead of computing into a second local (`idx = code % 2116;`). In the same block the target scaled a column through a scratch register before its home (`extsh r0,r0; mulli r0,r0,22; extsh r30,r0`): `u = u * 22;` matched where `u *= 22;` scaled in `u`'s own register. Example: `fn_3_3904` in `rep_1C0.c` (93.1% to 100%).
- **A decrement of a global field allocates differently from its spelled-out form** (`mulli r6,r5,-1` and the values derived from it one register off): `x--` and `x -= 1` matched where `x = x - 1` did not, with identical instructions. Example: `lbl_3_common_bss_32A94._23--` in `fn_3_795A8` (`rep_12D0.c`). The reverse happens with a local: a `u8` difference masked into a new register in the target (`clrlwi r6,r0,24` then `or r0,r0,r6`) matched only as `first = first - fade; colors[0] |= first;`; `first -= fade;` put the mask in `first`'s own register, and `colors[0] |= (u8)(first - fade);` in `r0` (`fn_3_67EF0` in `rep_EA0.c`, 99.91% to a match).
- **Saved registers rotated among a function's long-lived locals and its CSE'd global bases** (`fielder` in r26 where the target has r30, every global base one register off): declaration order includes the declarations with initializers. Moving `s32 pitcher = g_GameLogic...;` above `s16 result = 0;` fixed `fn_3_77914` (`rep_12D0.c`); permuting the three plain locals did not. The permuter found it. In `fn_3_6E24C` (`rep_1188.c`) the two pointers declared with initializers had to come above every plain local; no order of the plain locals changed anything.
- **`mr rX,r28` only in the target right after each pointer advance** (`addi r28,r28,232; mr r4,r28` before a loop and at its latch, and the next block's first few stores going through r4 while the rest use r28): the original wrote those stores through a second pointer that it re-took after every advance, `entry = ++draw;`, with `entry = draw;` before the loop. A copy made at the top of each block (`entry = draw;`), an inline taking the pointer, or a cast to another struct type is propagated away. Example: `fn_3_C9DB4` in `sta_c0.c` (the kind fields at 0xA1 to 0xA4 of each 0xE8-byte entry).
- **A strength-reduced loop offset initialized from the counter** (`li r24,0; mr r21,r24` where the base has `li r21,0`, or `li r25,2; mulli r24,r25,144` where the base folds it to `li r24,288`): the counter's start value was not a fresh constant. Reuse one counter variable across the function's loops (`for (i = 0; ...)` again and again) for the `mr` form, and reach the start value by increments (`j = 0; ...; j++; ...; j++;`) for the `mulli` form. In the same function, scripting every declaration order of five locals then took it from 98.4% to 98.7%. Example: `fn_3_C9DB4`. In `fn_3_E763C` (`sta_c6.c`) the copies came from `i` because `i` also held the allocation size before the loops, `i = count * ...; _OSAllocFromHeap(4, i); memset(buf, 0, i); for (i = 0; ...)` (98.4% to 99.5%); a separate `size` local, or reusing `n`, `j` or `start`, did not give them. In `fn_3_162D54` (`rep_3DA8.c`) the offsets `mr r9,r11; mr r10,r11` of a player loop over `k` appeared once the preceding mission loop also counted with `k` (98.5% to 99.4%).`fn_3_FA3C0` (`sta_c4.c`) is the same case: its outer loop's three offsets for `count` start as `mr` copies of `i`'s `li 0` once `i` holds the allocation size first, `i = n * 2 + ...; _OSAllocFromHeap(4, i); memset(p, 0, i); for (i = 0; ...)` (97.64% to 99.65%, found by the permuter).
- **Two counters initialized to 0 in swapped registers** (`li r7,0` for the sum and `li r6,0` for the index, the base the reverse) when declaration and statement orders do not help: initialize them in one chained assignment, `i = sum = 0;`, then search declaration orders again. Example: `fn_3_113A48` in `rep_3290.c` (found by the permuter).
- **A loop counter given its own `li` in the base, while the target counts in the register of the same constant stored just before the loop** (`li r5,1; stb r5,6(r6)`, then `addi r5,r5,1; cmpwi r5,60`): the counter was assigned inside that store, `p[6] = i = 1;`. A separate `i = 1;` in any position, and `p[6] = i;`, load 1 twice. In the same function a later copy loop's counter and destination swapped saved registers (r28/r30) until that loop got its own counter, `j = 120; while (j--)`, with `dst` declared before `src`. Example: `fn_3_67620` in `rep_EA0.c` (97.72% to 98.78%).
- **Two volatile address registers swapped before a loop** (`addi r3,r3,lbl@l` for a float constant and `lis r4,g_Minigame@ha`, the base the reverse) where a float local is computed before the loop and tested inside it: write the expression in the loop's condition instead of the local, `if (wall->_28 == 3 && g_Ball.pos.z - g_Ball.ground - k[1] <= wall->_0.z && ...)`; MWCC still hoists it. Example: `fn_3_113F14` in `rep_3290.c` (found by the permuter).
- **A float multiply by a variable with the operands swapped** (`fmuls f6,f6,f0` with the scale in `f0`, against `fmuls f6,f0,f4`): MWCC put the scale first in `dx = (a - b) * t;` and in `t * (a - b)`. Split the statement, `dx = a - b; dx *= t;`. Example: `fn_3_114A88` in `rep_3290.c`.
- **Float registers rotated in a clamp** (the field loaded into `f3` and the bound computed in `f0` in the target, `f0` and `f1` in the base, before `fcmpo` and the store): the original repeated the bound instead of keeping it in a local (`min = 0.01f * mins[1]; if (f->_0F4 < min) f->_0F4 = min;`), `if (f->_0F4 < 0.01f * mins[1]) f->_0F4 = 0.01f * mins[1];`. In `fn_3_6E24C` (`rep_1188.c`) each of five clamps rewritten this way raised the score; the permuter found it.
- **A multiply by a global float that is loaded once, with the operands swapped** (`fmuls f7,f2,f6` with the multiplier in `f2`, against `fmuls f7,f6,f0`): the original read the global in each statement, `0.01f * sizes[c][k] * charSizeMultipliers[c][0]`. ## `...rodata.0` in the base, constants one by one in the target

The base shows `lis rX,...rodata.0@ha; addi` and then `lfs f0,100(rX)`, while the target names each constant (`lfs f0,lbl_3_rodata_418C@l(r4)`). MWCC pools a function's `.rodata` references once it touches enough of them (three float constants alone stayed separate in `fn_3_16D810`; adding a `GXColor` initializer pooled all four).

- **Cause: the original's `.rodata` began with weak objects, which turns pooling off for that section** (observed: with weak objects first nothing in `.rodata` is pooled, while `.bss` statics still are). `game/UnknownHomes_Game.h` defines `SQRT2_LINKAGE extern` before including `math.h`, so `dolsqrtf2` becomes an `extern inline` whose static locals are emitted as weak `_half$localstatic` and `_three$localstatic` even when unused; plain `#include "math.h"` emits nothing. The target's `.rodata` does not show them, presumably because the linker kept one weak copy for the whole module.
- **Fix, only when the base shows `...rodata.0`:** include `game/UnknownHomes_Game.h` above `header_rep_data.h`, as `game_batter.c` does. The `.rodata` section score loses those 0x10 bytes; the code matches. Example: `rep_4138.c`, where this matched `fn_3_16D810` and `fn_3_16DB6C`. `-pool off` also matches such functions but breaks pooled `.bss`, and GC/1.3.2 to 2.7 behave identically, so the include order is the explanation, not the flags.
- The same include matched `fn_3_16B5B4` in `kinoko.c`, which pooled once an inlined callee added string literals.
- **When nothing needs unpooled constants, include `header_rep_data.h` first.** That puts `repHeaderData` at offset 0 as in the target and scores `.rodata` higher (92% against 86% in `rep_F80.c`); every function matched with either order.

- **Literal constants in the reverse of the target's order:** the source lists functions in address order. With `-inline deferred` MWCC generates functions last to first (objdiff's `reverse_fn_order` hides this for `.text`) and creates each function's constants as it goes, so REL source lists functions from the highest address down; `tools/reverse_functions.py` converts a file. Example: rep_940 `.rodata` 83% to 93%.
- **The weak `dolsqrtf2` constants** (0x10 bytes, from `game/UnknownHomes_Game.h`) stay as a difference; the linker keeps one copy for the whole module. The explanation above is incomplete: in `rep_10E8`'s target, `_half` and `_three` are local objects in the middle of `.rodata` (0x1140, 0x1148), yet its constants are unpooled and the include order still matched.

## `.data` or `.bss` below 100% with every object defined

- **An all-zero object in the target's `.data`:** define it with an explicit initializer, `static T x = { 0 };`, which MWCC keeps in `.data`; without one it goes to `.bss`. Example: `lbl_3_data_28928` in `kinoko.c`.
- **A trailing `gap_..._data` symbol, or a last object larger than its type:** the linker padded the section up to the next unit's alignment (8 for `.data`, 32 for kinoko's `.bss`). Leave it; no source object belongs there. To confirm, `objdump -s -j .data` of both objects differs only in trailing zeros the base lacks. Examples: `rep_3F60.c` scores `.data` 99.78% (4 bytes at 0x28924); `rep_3E58.c` scores `.data` 98.73% (4-byte `gap_04_000285A4_data` after the jump table) and `.bss` 50% (`lbl_3_bss_B9E0` is an `s8` with size 0x20 in `symbols.txt`). A `switch` jump table needs no definition: MWCC emits it as `@NNN` and objdiff pairs it with `jumptable_...`.
- **Jump tables scored unmatched though their entries name the same labels** (`objdump -r -j .data` shows identical `fn+0xNN` relocations in both objects): objdiff 3.4 evidently compares a data relocation's target by address, so every table after a function whose size differs counts as unmatched, its own function's table included. Compare the functions' sizes in `objdump -t` of both objects; `.data` rises only when every function up to the last `switch` has the target's size. Example: `rep_36D8.c` `.data` stays at 2.38% (only `lbl_3_data_265F0`) because `fn_3_13C7BC` and `fn_3_140CE0` are each 4 bytes longer than the target, though `fn_3_141A30`'s table is identical.
- **A `gap_*` symbol between two objects** (3 bytes after a `u8`, before a 4-aligned object): alignment padding inside the file; objdiff counts it as unmatched, so the section stays below 100%. Leave it. Example: `rep_4138.c` `.bss` 88.46% from `gap_05_0000D6E1_bss` and `gap_05_0000D6ED_bss`.
- **An object larger than everything the code touches, ending at the unit's end on no alignment boundary:** the tail is a separate unreferenced object, not padding. Check a `memset` or loop bound for the real size, split the `symbols.txt` entry, and declare the tail too (MWCC keeps unreferenced statics). Example: `lbl_3_bss_D6F0` was 0x24, but `memset` clears 0x18; the last 0xC became `lbl_3_bss_D708` (`rep_4138.c`, `.bss` 66.67% to 88.46%). Likewise the 8 bytes `3, 0` after `rep_2308`'s four 0x28-byte draw entries became `lbl_3_data_17DB8`.
- **A pooled static landing one byte off its target offset after an unreferenced gap:** MWCC aligns a `u8` array of four or more bytes to 4, so a gap that starts at an odd offset cannot be one array. Declare a `u8` for the odd byte and the array after it. Example: `lbl_3_bss_AE53` and `lbl_3_bss_AE54[0x27]` in `sta_c6.c`, which put `lbl_3_bss_AE7B` at 0x2B for `fn_3_E7424`.

## Before committing

- Run `tools/match.py` on every function that uses a type, prototype or symbol you changed, not only the one you were fixing.
- Run `python3 tools/regress.py`; it fails on any dropped objdiff score or lost strict match. Its summary goes in the pull request.

## Tool pitfalls

- Install m2c from https://github.com/matt-kempster/m2c. The PyPI package named `m2c` is an unrelated project.
- `match.py --m2c` prepares the unit's context for m2c (preprocesses it and strips inline asm); the draft is typed only for globals the source's includes declare, so a placeholder file including only `header_rep_data.h` gives `?` types until you add `game/UnknownHomes_Game.h` and the like.
- `match.py` reports a function you have written as `missing` when objdiff cannot pair it, for example after a callee's empty stub was inlined into it; give the callee a body first.
- decomp-permuter's own `import.py` breaks on this project; `tools/permute.py` explains why in its header and replaces it.
- `tools/permute.py` fails to compile its view when the source has `sizeof(T) + (x)`: pycparser reads it as `sizeof((T) +(x))`, a cast. Parenthesize the product, `(20 * sizeof(T)) + (...)`, which compiles the same.
- The same happens with `sizeof(T) * 2` (read as `sizeof((T)(*2))`). Put the constant first, `(count - k) * (2 * sizeof(Vec))`; check the score afterwards, since `(count - k) * 2 * sizeof(Vec)` does not fold to one `mulli` (`fn_3_67EF0` in `rep_EA0.c`).
- A permuter output can beat the base with the target function's body unchanged: the output drops the file's other functions, and inlining and allocation then differ. Diff only the target function's body before trusting a score (`fn_3_67620` in `rep_EA0.c`: 245 against 390, same body).
- `tools/permute.py` fails with a syntax error on `va_arg(args, s32)`, because pycparser cannot parse MWCC's `_var_arg_typeof`. For the permuter run only, write `*(s32*)__va_arg(args, 1)` (the same code), and restore `va_arg` afterwards.
