# Matching notes

Lessons from matched functions, indexed by the **symptom** `tools/match.py` shows. Find the symptom, try its causes in order, and add a lesson here when a function teaches you something new (symptom, cause, fix, example).

## `reloc`: a reference points somewhere else

objdiff's report scores these 100% because it ignores relocation targets; the unit cannot link until they are fixed.

- **Placeholder shadows a named symbol.** The source declares its own `extern ... lbl_3_data_XXXX` for an address that `symbols.txt` already names. Look the address up in `config/GYQE01/**/symbols.txt`, use the existing header declaration, delete the placeholder. Example: `calculateHorizontalPower` read `hitTrajOptions` through `lbl_3_data_5B34`.
- **Source is ahead of `symbols.txt`.** The source uses a good name that `symbols.txt` still calls `lbl_...`. Rename it in `symbols.txt` after checking the source type's size equals the symbol's `size:`, then fix every other use of the old name (`tools/check_symbols.py` lists them). Example: `gameInitOptions` and `aILevel` for `setInMemBatterConstants`.
- **Wrong callee or global.** The call or load goes to a different symbol with the same shape. Treat it as a source bug, not a naming issue.
- **`sym+0xNNNN@ha` / `sym+0xNNNN@l` in the target.** MWCC never folds a constant offset into a relocation: `&arr[k]`, `arr + k` and struct members all compile to `addi rX,rX,sym@l; addi rX,rX,k`. So the original referenced a separate object that `symbols.txt` lacks. Declare an `extern` named by its address with the size the code implies, and escalate the split; the function then reports `reloc` until `symbols.txt` gets the symbol. Example: rep_1330's `lbl_8034E9A0+0x4C28` and `+0x4E44`, main-DOL objects at 0x803535C8 and 0x803537E4.
- **`...bss.0` or `...data.0` with offsets in the base.** MWCC addresses a file's statics from one base symbol plus literal offsets (`addi r4,r5,160`, `lwz r3,8(r31)`), so the target's offsets give the layout, and `symbols.txt` often lumps several statics into one symbol. Declare one static per object, in reverse address order (MWCC lays them out in reverse declaration order), including statics nothing in the file reads, and split the symbol in `symbols.txt` to match. One static struct does not reproduce this: it recomputes its base in each branch, while the pool base is computed once. Example: kinoko's `lbl_3_bss_BA00` to `BAA0`.
- **One data symbol plus offsets past its size in the target** (`addi r31,r5,lbl_3_data_285A8@l` then `addi r6,r31,0x360`, while the base loads each symbol with its own `lis`/`addi`): the target reaches several objects from one pool base, so they are statics of this file. Initialized `.data` statics are laid out in declaration order (unlike `.bss` above), so declare them in address order. An offset folded into one `addi` means a separate static; `arr[1]` compiles to `addi` of the array start, then the element offset. Extern declarations cannot reproduce this: if the data lies outside the unit's `splits.txt` ranges, keep externs under the `symbols.txt` names and escalate the `.data` range, with a scratch copy that defines the statics as evidence. MWCC pooled a function's accesses when it touched three of these statics and named each when it touched two. A zero-filled static needs an explicit initializer (`static u8 flags[9] = { 0 };`) to stay in `.data`; without one MWCC moves it to `.bss`. Objects the code names on their own can keep their global binding between pooled statics: the layout still follows declaration order (`lbl_3_data_18180` in `rep_2390.c`). Examples: `fn_3_168704` and `fn_3_168DFC` in `rep_3F60.c` (matched once its `.data` was defined there), `fn_3_15BAA0` in `rep_3AE8.c` (matched once its five statics were defined there), `fn_3_C11CC` and `fn_3_C1770` in `rep_1F58.c`.

## Registers only: same instructions, different register numbers

- **Shared across functions.** When several functions show the same unexplained allocation while identically written ones match, look at what they share before tweaking each: a prototype's parameter or return type changes the compiler's internal conversions and so its allocation, with identical instructions. Example: `minigame_checkIfAIInputIs_Algorithmic_Or_ControllerBased(u8)` should take `s8` (callers pass `s8 characterIndex[]`); that fixed three functions.
- **`int` against `s32` in a prototype.** `s32` is `long`, so MWCC converts between it and `int` even though the code is the same, and the conversion moves allocation. `fn_3_28E4` (`rep_140.c`) had `count` and a saved address swapped (r29/r30) until the callee `fn_3_1B24` took `int count`; the permuter pointed there with casts on that one argument. Recheck the callee: its second loop then tested `cmpwi r8,1; ble` against the target's `li r12,1; cmpw r12,r8; bge` until its counter became `s32 i`, and `fn_3_155C` needed `int` for both.
- **Declaration order.** The order locals are declared in affects which register each gets, volatile or callee-saved; try moving the variable that lands in the wrong register above its neighbour. Example: `inputs` declared before the `BOOL` flag. Search the orders again after any other fix: `fn_3_15FB84`'s `n` and `player` (r9 and r11 swapped) matched only once declared `n`, `marker`, `offset`, `player`, though an earlier search over the same four, made on an earlier version of the function, found nothing.
- **Statement order of independent loads.** Which register a shared base (`addi r10,r3,sym@l`) gets depends on where its first use sits among the statements that read through it. Example: `fn_3_CABF0` in `rep_2308.c` matched once `model = &bss._010->_C4;` moved above the six local-array fills, written as `ids[i]`, `anims[i]` pairs in the target's store order.
- **Volatile registers differ in a function's setup code** (`lbz r0,30(r27)` against `lbz r4,30(r27)` for the same field): the statement order of independent setup assignments decides them. Script every order of the first few assignments, crossed with a few declaration orders; that is a dozen runs. Example: `fn_3_168A6C` matched only as `model`, then `anim`, then `animData` assigned, with `animData` declared first. The same order decides how the whole entry block is scheduled: `fn_3_15FB84` went from 86% to 97.7% when a float local was computed after the first of three stores instead of before them.
- **A value loaded once.** Holding a repeated load in its own local (with the type of the expression, usually `int`, not the field's `u8`) changes allocation. Example: `slapContactSize` in `calculateBuntHorizontalAngle`; `u8 status = g_GameLogic.gameStatus;` tested by an `if` and a later `switch` in `fn_3_E1478`.
- **Operands swapped in an add** (`add r31,r31,r0` versus `add r31,r0,r3`): split the expression, e.g. `value = tex[i]; value += step * 2;`. Example: `fn_3_16943C`.
- **An `add` of a float-to-int conversion and a table value with the conversion second** (`lwz r0,12(r1); add r0,r10,r0` where the target has `add r0,r0,r10`): MWCC puts the loaded value first for both `(int)(d * t) + lo` and `lo + (int)(d * t)`. Hold the converted value in an `int` local, and the difference before it too: `range = hi - lo; offset = range * t; z = offset + lo;`. The `range` local also fixed where the index of `t` was loaded. Example: `fn_3_20224` in `rep_8C8.c` (`range` found by the permuter).
- **A derived value written to a new register** (`subf r3,r4,r6; subf. r3,r0,r3` where the base reuses the variable's register, `subf r6,r4,r6`): the original computed it into a second local, `left = frame - total; left -= charged; if (left <= 0 ...)`. `frame -= total;` reuses `frame`'s register, and one expression gives other allocations. Example: `fn_3_1EFE4` in `rep_8C8.c`.
- **A comparison used as an index allocated differently** (`subfic r3,r4,1; subi r0,r4,1; or r4,r3,r0` with the operand registers swapped): assign it to a local first, `late = early == 1 ? 0 : 1;`, then index with `late`. Writing `table[early != 1]` in place gives the same instructions in other registers. Example: `fn_3_1EAA8` in `rep_8C8.c`.
- **Float values loaded into swapped registers for stores that copy and offset them** (`lfs f3,32(r5)` against `lfs f2,32(r5)` before `stfs` to one struct and `fadds` into another): compute the second store from the field just stored, `b.pos.x = b.pos2.x + offset;` after `b.pos2.x = ai.box;`, not from the source global again. Example: `fn_3_1F998` in `rep_8C8.c`.
- **Operands swapped in an `fmadds`** (`fmadds f0,f2,f1,f0` against `f0,f1,f2,f0`): swapping or regrouping the C operands changes nothing. Compute the multiplicand into a local first: `t = min + range * rand() / 32767.0f; x = t * (n - i) + i;`. Example: `fn_3_15BAA0`.
- **Operands swapped in an `fmuls` by a constant, product in a new register** (`fmuls f1,f2,f1` with the constant in `f1`, against `fmuls f1,f1,f2`): MWCC puts the literal first in both `s = s * K` and `s = K * s`, while `s *= K` keeps the order but writes the product back into `s`'s register. Passing both through `math.h`'s inline `scaleValue` keeps the order and gives a new register: `scale = scaleValue(a / 512.0f, 0.27208483f);`. Example: `fn_3_6CD88`; in `fn_3_15C3F8` (`rep_3B70.c`) `half *= 0.5f` also merged the stack slots of two int-to-float conversions, shrinking the frame by 0x10. For an `int` variable, `dx = a - b; dx *= 0.2f;` keeps the constant second (`fmuls f1,f1,f31`) and converts back to `int`, where `dx = (int)(a - b) * 0.2f;` puts it first: `fn_3_E9D30` (`rep_2BF8.c`).
- **Two loads in swapped registers feeding two stores** that already come out in the target's order: swap the two assignment statements. The scheduler keeps the store order, but allocation follows statement order. Example: the `_00` and `_10` stores before `fn_8002CE4C` in `fn_3_15BAA0`.
- **Operands swapped in a branchless `or`/`or.` chain** (`cntlzw; srwi; or; or.` tests): reorder the operands of `|` in the condition; each order gives a different pairing. Example: `fn_3_16E1EC` matches only as `lbl_3_bss_D6EC | !lbl_8036E548._3088 | !lbl_3_bss_D6E4`.
- **A loop counter in the register that held a parameter before a call** (`mr r31,r3` at entry, later `li r31,0` for the loop): the loop reuses the parameter, `for (idx = 0; idx < 2; idx++)`; a new `i` gets a volatile register. Example: `fn_3_C0C4C`.
- **Two local arrays at swapped stack offsets, or their initial values loaded into different registers:** the array declared later gets the lower address, and the order of the statements that fill them decides the registers. Example: `fn_3_C095C` needs `u32 animIds[2]; UnkAnim1F58* anims[2];` filled as `animIds[0]`, `anims[0]`, `animIds[1]`, `anims[1]`.
- **A parameter and another long-lived value swap callee-saved registers** (`mr r28,r3` at entry against `mr r27,r3`, with every use renumbered) and declaration order changes nothing: the original took the parameter as `void*` and copied it into a typed local. Callbacks stored in a function pointer are written this way: `void fn(void* arg) { UnkDraw3CE0* draw = arg; ...`. Example: `fn_3_15FF28` in `rep_3CE0.c`.
- **Counters of a nested loop in swapped registers** (the target's outer counter in r27 and inner in r30, the base's the reverse) while the function's other loops already match: the variable those other loops use is the inner counter. `fn_3_169984` in `kinoko.c` matched with `for (j = 0; j < 148; j++) for (i = j + 1; i < 149; i++)` around loops over `i`, not with `i` outer.
- **Volatile registers of a nested loop differ, including the pointers MWCC strength-reduces** (a walking `slot` pointer in r11 where the target has r5): index the array in each statement, `lbl_80354720[t][i].slot = j;`, instead of advancing a pointer; MWCC then creates the induction pointers in the target's registers. Search declaration orders afterwards. Example: `maybeProcessTeamData` in `rep_0.c` (97.97% with a pointer, 98.57% indexed, matched with `order` declared before `i`, `j`, `t`).
- **Block scope moves a volatile register too.** Declaring a loop-only variable inside the loop body changes its register: in `fn_3_15FB84`, `player` declared in the loop took r11 as in the target, though `n` and `marker` then swapped. The function matched through declaration order instead (above).
- **Float registers differ around `sin`/`cos` calls** (hoisted loop constants assigned to saved FPRs in a rotated order, or `frsp f1,f1` where the target has `frsp f0,f1`): the original called the `sinf`/`cosf` inlines, not `(f32)sin(x)`. Use `sinf_kludge`/`cosf_kludge` from `stl/math.h`; the permuter found nothing in 9000 iterations. Example: `fn_3_167178` and `fn_3_1674D0` in `rep_3E58.c`.
- **The inlined callee's argument shares a register with the variable it is loaded from** (`lwz r31,20(r31)` loading `task->_14` over `task`, while the base keeps `task` in r30): put the arguments in locals in the target's evaluation order, `id = table[rand() % n]; player = task->_14; fn_3_166C30(player, id);`. Example: `fn_3_166E04` and `fn_3_166FCC`.
- **An inlined callee's registers differ only where it is inlined** (the callee matches standalone): rewrite the callee in another form that compiles the same standalone and recheck its callers. Reusing the parameter (`idx *= 16;` instead of `s32 row = idx * 16;`) fixed the second of `fn_3_C0D10`'s two inlined copies in `fn_3_C1344` (`rep_1F58.c`) and left the first, and the copy in `fn_3_C1004`, unchanged.
- **A loop counter and a loaded pointer in swapped callee-saved registers** (`li r21,0` and `lwz r22,...` in the target, the reverse in the base) while declaration order, block scope and extra pointer locals change nothing: the original tested the array element before copying it, `if (lbl_8036E548._2C50[i] == NULL) continue; actor = lbl_8036E548._2C50[i];`, not `actor = ...; if (actor == NULL)`. The code is the same; the permuter found it. Example: `fn_3_6B144` in `rep_FE0.c`.
- **A limit copied with `mr` inside the branch in the base** (`lha r3,10(r31); cmpw r5,r3; ...; mr r4,r3`), where the target loads it straight into the variable's register and compares that (`lha r4,10(r31); cmpw r3,r4`): the variable was assigned inside the condition, `if (y <= (py = lim[5])) { ... } else if (y >= (py = lim[7])) { ... } else { py = y; }`. Assigning it before the `if` or inside the branch both differ. Example: `fn_3_E9D30` in `rep_2BF8.c`.
- **A decrement of a global field allocates differently from its spelled-out form** (`mulli r6,r5,-1` and the values derived from it one register off): `x--` and `x -= 1` matched where `x = x - 1` did not, with identical instructions. Example: `lbl_3_common_bss_32A94._23--` in `fn_3_795A8` (`rep_12D0.c`).
- **Saved registers rotated among a function's long-lived locals and its CSE'd global bases** (`fielder` in r26 where the target has r30, every global base one register off): declaration order includes the declarations with initializers. Moving `s32 pitcher = g_GameLogic...;` above `s16 result = 0;` fixed `fn_3_77914` (`rep_12D0.c`); permuting the three plain locals did not. The permuter found it. In `fn_3_6E24C` (`rep_1188.c`) the two pointers declared with initializers had to come above every plain local; no order of the plain locals changed anything.
- **`mr rX,r28` only in the target right after each pointer advance** (`addi r28,r28,232; mr r4,r28` before a loop and at its latch, and the next block's first few stores going through r4 while the rest use r28): the original wrote those stores through a second pointer that it re-took after every advance, `entry = ++draw;`, with `entry = draw;` before the loop. A copy made at the top of each block (`entry = draw;`), an inline taking the pointer, or a cast to another struct type is propagated away. Example: `fn_3_C9DB4` in `sta_c0.c` (the kind fields at 0xA1 to 0xA4 of each 0xE8-byte entry).
- **A strength-reduced loop offset initialized from the counter** (`li r24,0; mr r21,r24` where the base has `li r21,0`, or `li r25,2; mulli r24,r25,144` where the base folds it to `li r24,288`): the counter's start value was not a fresh constant. Reuse one counter variable across the function's loops (`for (i = 0; ...)` again and again) for the `mr` form, and reach the start value by increments (`j = 0; ...; j++; ...; j++;`) for the `mulli` form. In the same function, scripting every declaration order of five locals then took it from 98.4% to 98.7%. Example: `fn_3_C9DB4`.
- **Two counters initialized to 0 in swapped registers** (`li r7,0` for the sum and `li r6,0` for the index, the base the reverse) when declaration and statement orders do not help: initialize them in one chained assignment, `i = sum = 0;`, then search declaration orders again. Example: `fn_3_113A48` in `rep_3290.c` (found by the permuter).
- **Two volatile address registers swapped before a loop** (`addi r3,r3,lbl@l` for a float constant and `lis r4,g_Minigame@ha`, the base the reverse) where a float local is computed before the loop and tested inside it: write the expression in the loop's condition instead of the local, `if (wall->_28 == 3 && g_Ball.pos.z - g_Ball.ground - k[1] <= wall->_0.z && ...)`; MWCC still hoists it. Example: `fn_3_113F14` in `rep_3290.c` (found by the permuter).
- **A float multiply by a variable with the operands swapped** (`fmuls f6,f6,f0` with the scale in `f0`, against `fmuls f6,f0,f4`): MWCC put the scale first in `dx = (a - b) * t;` and in `t * (a - b)`. Split the statement, `dx = a - b; dx *= t;`. Example: `fn_3_114A88` in `rep_3290.c`.
- **Float registers rotated in a clamp** (the field loaded into `f3` and the bound computed in `f0` in the target, `f0` and `f1` in the base, before `fcmpo` and the store): the original repeated the bound instead of keeping it in a local (`min = 0.01f * mins[1]; if (f->_0F4 < min) f->_0F4 = min;`), `if (f->_0F4 < 0.01f * mins[1]) f->_0F4 = 0.01f * mins[1];`. In `fn_3_6E24C` (`rep_1188.c`) each of five clamps rewritten this way raised the score; the permuter found it.
- **A multiply by a global float that is loaded once, with the operands swapped** (`fmuls f7,f2,f6` with the multiplier in `f2`, against `fmuls f7,f6,f0`): the original read the global in each statement, `0.01f * sizes[c][k] * charSizeMultipliers[c][0]`. MWCC still loads it once, but a local copy (`mult = charSizeMultipliers[c][0];`) goes first in every product. Likewise `stats.Speed *= k[8];` keeps a `u8` field first where `stats.Speed = stats.Speed * k[8];` does not. Examples: `fn_3_6E24C` and `fn_3_6EF1C` in `rep_1188.c`.
- **A table value and a constant stored beside it in swapped volatile registers** (`lbz r0; slwi r0; lwzx r0` with the `li r6,0` for two zero stores, the base the reverse), with every store already in the target's order: the original took the table row as a pointer and read the element later, `times = table[task->_14]; task->_15 = 0; task->_16 = times[0];`. A local for the element, its type, and a named zero changed nothing. Example: `fn_3_160814` in `rep_3D50.c`.
- **Callee-saved parameters one register off, with one parameter dropped to the bottom** (`mr r15,r4` where the target has `mr r24,r4`, the later parameters each one lower): a local initialized from a parameter in a separate statement changed the allocation order. `u8 alpha = color & 0xFF;` as a declaration put every parameter in the target's register; `alpha = color;` after `colors[0] = color;` did not. Example: `fn_3_67EF0` in `rep_EA0.c` (97.65% to 98.16%).
- **An FPR sum built in another register order** (`fadds f5,f5,f1; fadds f5,f5,f0` accumulating in the first operand's register, where the base computes `a + b + c` into fresh registers): the original accumulated, `offset = h[1]; for (i = 2; i < 4; i++) { offset.x += h[i].x; ... }`, which MWCC unrolls. Example: the held-ball offset in `fn_3_697CC` (`rep_EA0.c`).
- **Stalled after a few tries:** run `python3 tools/permute.py <unit> <function>` and the command it prints. Take the permuter's idea, not its literal code (it reuses unrelated variables and adds casts like `(long long)`), then rewrite it plausibly and recheck.

## Instruction differences that reveal types

- **A global pointer loaded as `lis; addi rX,rX,sym@l; lwz rX,0(rX)` into the argument register, then `mr r31,r3`,** where the target loads it straight into the saved register (`lwz r31,sym@l(r4); mr r3,r31`): the global is a `void*` and the local takes it through a conversion, `UnkTask* task = lbl_803CC1B8;` with `extern void* lbl_803CC1B8;`. A typed global lets MWCC copy-propagate the load into the call's argument; it showed only once a loop with a call kept `task` live. Example: `fn_3_912B4` in `rep_1610.c`.
- **`lha` followed by `extsh.` on the loaded value** (`lha r4,7016(r30); extsh. r0,r4`, where the base has `lha r0; cmpwi r0,0`): the field was read into an `s16` local and tested, `s16 hangtime = g_Ball.pitchHangtimeCounter; if (hangtime <= 0)`, and the local is reused later. Example: `fn_3_1EFE4` in `rep_8C8.c`.
- **Signedness of an int-to-float conversion.** Signed: `xoris rX,rX,0x8000` with the double constant `0x4330000080000000`. Unsigned: no `xoris`, constant `0x4330000000000000`. Fix the element or variable type to match.
- **A `u8` field converted with the signed constant** (`lbz` then `xoris`): the value went through an `int` local first. `alpha = p->color[3]; alpha -= 255.0f / n;` converts signed; `alpha = p->color[3] - 255.0f / n;` converts the `u8` as unsigned. Example: `fn_3_16C548` in `rep_4090.c`.
- **A local loaded from a `u8` field, compared with `cmplwi` and used as an index with a plain `slwi`:** the local is `u32`. An `s32` local compares with `cmpwi`; a `u8` local masks the index with `rlwinm`. Example: `stadium` in `fn_3_16C410` (`rep_4090.c`).
- **`neg; andc; srwi rX,rX,31; subf` on an `s32`:** a decrement that stops at zero and leaves negative values alone, `x -= x > 0;`. `if (x > 0) x--;` branches. Example: the hold timer in `fn_3_67A48` (`rep_EA0.c`).
- **`neg; or; rlwinm rX,rX,2,30,30` turning a 0/1 flag into a halfword-array offset** (where the base shifts the flag with `rlwinm rX,rY,1,...`): the index was converted to a boolean again, `tbl[flag ? 1 : 0]` (`tbl[flag != 0]` compiles the same). Example: `lbl_3_common_bss_35154._47A` in `fn_3_697CC` (`rep_EA0.c`).
- **`fmuls` then `fadds` in the target, `fmadds` in the base:** the multiply was its own statement, `height *= 0.003f; rot.y = fn(rot + height);`. Example: `fn_3_692E0` (`rep_EA0.c`).
- **Array shape from index arithmetic.** `subfic r0,e,3; slwi; lwzx` from a struct's start is one 4-element array indexed `[3 - e]`, not two 2-element fields. Example: `trajOptions_s._0` must stay `s32[4]`.
- **`extsb` before a call only in the target:** the callee takes `int`, and the caller sign-extends its `s8` argument; with an `s8` parameter the callee extends instead. Example: `fn_8001B728(s32, s32, Vec*)`.
- **A flag parameter tested with `clrlwi. r0,r4,24`** is a `u8`; a `BOOL` (`int`) compiles to `cmpwi`.
- **`cmpwi r3,0` after a call where the base has `clrlwi. r0,r3,24`:** the callee returns `BOOL`, not `bool` (`u8`). Its own result local must be `BOOL` too, or `return ret;` gains a `clrlwi r3,rX,24`. Example: `checkTriangleCollisions` in `rep_D0.c`.
- **A parameter the callee compares, switches on or scales as an index with no `clrlwi` or `extsb`** is int-width: MWCC extends a `u8` or `s8` parameter before each such use. A caller that passes a variable to it with a plain `mr` holds that variable in an int-width local too, even if the local is only loaded with `lbz` and stored with `stb`; a `u8` local and an `s32` parameter add `clrlwi`. Use this to type a callee from an unmatched unit, where the caller's constant arguments say nothing. Examples: `streak` in `fn_3_16230C` and `fn_3_76D08` (an `s32` local in `fn_3_77914`), `fn_3_B9BB4`'s `stadium`, `fn_3_8BBC4`'s fourth argument.
- **`extsb` before `cmpwi rX,-1` but none before `cmpwi rX,1` on the same field:** the field is `s8`; MWCC drops the sign extension when testing equality with a non-negative constant. Example: `AIStruct.aiPitchDirectionInput` in `fn_3_20CEC`.
- **`cmplw` between two computed element addresses:** the source compares two arrays, which decay to pointers. Keep the original's bug. Example: `g_Scores._04[batting] > g_Scores._04[fielding]` in `fn_3_212A0`.
- **`extsh rX,r3` right after a call that returns `s16`, where the base has `mr rX,r3`:** the result went into an `int` local, `int cur = radToShortAngle(x);`. The `int` local also keeps later `cur -= 0x280;` in its own register and extends it once at the call that takes it back as `s16`. Example: `fn_3_6AF9C` in `rep_FE0.c`.
- **`extsb` right after the `lbz` of an `s8` field, before an early test:** the field is read into an `int` local (`s32 idx = player->_254;`). An `s8` local delays the sign extension to its first use. Example: `fn_3_168CD8` and `fn_3_16892C`.
- **An `s8` tested with `extsb. r0,rX`, then extended again into a saved register** (`extsb r19,r5` scheduled into the next load) that indexes arrays and is passed to a call: an `s8` local copied into an `int` local after its guard, `idx = g_Minigame.minigameFielderIndex[i]; if (idx < 0) return; f = idx;`. Example: `fn_3_E1478` in `rep_2940.c`.
- **A loop pointer advanced by a stride no field explains** (`addi r8,r8,9` with fixed offsets such as `0x19EA(r8)` and `0x19EF(r8)` into a global): the header's flat fields there are an array of structs of that size. Check that no source uses the flat names, restructure the header, and run `match.py` on every user. Example: `MiniGameStruct._19E8[4]` (9-byte elements) and `MiniGameControlStruct` (`[4]` arrays up to 0x18F8, not two 0x16-byte structs) for `rep_2940.c`.
- **`extsh` of a converted value right before its halfword store, only in the target** (`fctiwz; stfd; lwz r0; extsh r0,r0; sth r0`), while an earlier value of the same variable is tested with `extsh.`: the local is an `int` assigned through an `s16` cast, `int magnitude = (s16)(64.0f * m / 56.0f);`. An `s16` local drops the extension before the store. Example: `fn_3_6CD88`.
- **`andi.` with a mask where the base has `rlwinm`** (`andi. r0,r3,0xffbf` against `rlwinm r0,r3,0,26,24`): the source clears the bit with a literal of the field's width, `x &= 0xFFBF;` for a `u16`, `x &= 0xFD;` for a `u8`; `x &= ~0x40` compiles to `rlwinm` for both. Examples: `fn_3_6D304`, `fn_3_1690C0`.
- **`rlwinm rX,rX,16,8,15` where the base has `slwi rX,rX,16`, then `rlwimi` inserts** (bytes packed into one word): the source masks each byte before shifting, as a color-packing macro does: `((r & 0xFF) << 24) | ((g & 0xFF) << 16) | ((b & 0xFF) << 8)`. Plain shifts, `(u32)` casts and a `GXColor` local filled field by field all differ. Example: `PACK_RGB` in `fn_3_15F648` (`rep_3C80.c`).
- **`extsh` of an `s16` local right before a call only in the target** (`extsh r4,r31` where the base has `mr r4,r31`): the callee's parameter is `int`, as with `extsb` above. Example: `fn_3_76D08` and `fn_3_16230C`, called from `fn_3_77914` (`rep_12D0.c`).
- **`addi r0,rX,1; cmplwi r0,1` with no `clrlwi` in the target** (`state == -1 || state == 0` merged into a range check): the local is `s32`, even though it is loaded with `lha`; an `s16` local adds `clrlwi r0,r0,16`. Example: `state` in `fn_3_78AC4` (`rep_12D0.c`).
- **A `u8` copy of a value.** `clrlwi rX,rY,24` before comparisons can mean the code compares a `u8` variable assigned from a cast (e.g. `u8 starType = (s8)field`), not the field directly.
- **A `u8` field's value masked where the base uses a constant** (`li r27,1` kept in a saved register, then `clrlslwi r24,r27,24,2` to index a table with the field after an inlined call reads it back, while the base has `li; slwi`): the field was assigned from an `int` variable with a post-increment, `ribbon->colorFrom = color++; ribbon->colorTo = color;`. Assigning constants, or `color++` as its own statement, lets MWCC propagate the constant. Example: `fn_3_16B884` in `kinoko.c`.
- **`extrwi. r0,r0,1,24` testing one bit where the base has `rlwinm. r0,r0,0,24,24`:** the source shifted, `(stats >> 7) & 1`, instead of masking with `stats & 0x80`. One function can mix both forms: `fn_3_6E24C` (`rep_1188.c`) tests bits 7 and 1 by shifting and bits 0, 2 and 6 by masking.
- **`neg` before `cntlzw` only in the base:** a pointer tested with `p == NULL` inside a `|` chain. Write `!p`, which compiles to plain `cntlzw; srwi`. Example: `fn_3_16E1EC`.
- **A call's float result as the second operand** (`fmul f0,f0,f1` or `fcmpu cr0,f0,f1` in the base, `f1,f0` in the target): swapping the C operands changes nothing. The source used another operation: `acos(x) / 2.0f` becomes `fmul` by the double 0.5 with the call result first, and `if (PSVECMag(v))` or `if (!PSVECMag(v))` compares the result first against 0.0, where `== 0.0f` puts the constant first. Examples: `fn_3_CAF9C`, `fn_3_169E70` in `kinoko.c`. The same holds for a float variable: `if (dir)` gives `fcmpu cr0,f31,f0` with the variable first, while `if (dir != 0.0f)` puts the constant first (`fn_3_15C024`).
- **`mulhwu` by `0xB21642C9` and `mulli 23` on a `rand()` result:** an unsigned modulo, `rand() % (sizeof(table) - 1)` for a 24-byte table of 23 entries plus a terminator. Example: `lbl_3_data_28558` in `rep_3E58.c`.
- **A word loaded from `.rodata`, stored to the stack, reloaded after a call and written to the FIFO** (`lwz r0,lbl@l; stw r0,8(r1)` ... `lwz r0,8(r1); stw r0,-0x8000(r3)`): a local `GXColor color = { 0xFF, 0xFF, 0xFF, 0xFF };` sent with `GXColor1u32(*(u32*)&color)`. Example: `fn_3_16D810`.

## Structure differences

- **A `Vec` initializer copied from `.rodata` only inside a branch, and the locals around it at the wrong offsets:** it is declared with its initializer in that block (`Vec offset = { 0.0f, 0.0f, 0.0f };`), and the locals at lower offsets are declared after it in the same block. Example: `fn_3_1674D0`.
- **Float constants loaded into saved registers before straight-line code, and a global's address formed with `addi` and loaded with `lwz r0,0(rX)`:** the body is a one-pass loop, `for (i = 0; i < 1; i++)`; loop-invariant code motion runs before the loop is unrolled away. Statements whose loads use the hoisted address go inside the loop. An `fmadd` with a 0.0f addend there is `angle = 0.0f; angle += 45.0 * r;`, since `0.0f + 45.0 * r` folds. Example: `fn_3_1678A8`.
- **Stack offsets swapped between two locals** (`addi r3,r1,72` against `addi r3,r1,24`, or array stores at `8(r1)` against `16(r1)`): MWCC gives later-declared locals lower offsets; swap their declarations. Example: `m` declared before `tmp` in `fn_3_168414`.
- **Int-to-float conversion temporaries at other stack offsets** (`stw r6,0x44(r1)` against `0x34`) in otherwise identical code: MWCC gives each conversion its slot in statement order, even where the scheduler interleaves the instructions, so the slots give the statements' source order. In `fn_3_6E24C` (`rep_1188.c`) the slots matched once `width = 0.01f * sizes[c][2] * m;` moved below the `_104` and `_108` stores.
- **Global loads hoisted before a loop in the target but repeated inside it in the base** (flags `lbz`'d into r24 to r31 and floats into f0 to f5 before `mtctr`): the loop wrote through a pointer it advanced (`stats++`), which MWCC assumes can alias any global. Index the global array in each statement, `inMemRoster[team][i].stats.Speed *= k[8];`; MWCC still strength-reduces it to a walking pointer. Example: `fn_3_6EF1C` in `rep_1188.c`.
- **A float-to-int conversion of a loop-invariant value done once before the loop in the base** (`fctiwz; stfd; lwz` ahead of `mtctr`) **but in every iteration in the target**: the cast is to the field's own type, `stats.CurveBallSpeed += (u8)k[4];`; `(int)k[4]` is hoisted. Example: `fn_3_6EF1C` (85.7% to 96.2%).
- **The same selection repeated before each use** (`lwz r4,8(r30); beq; li r4,0` ahead of every `mulli rX,r4,0x5A0`): an inline helper called once per test, `team = g_GameLogic.teamFielding; if (g_d_GameSettings.minigamesEnabled) team = 0; return inMemRoster[team][id].stats.FieldingStats;`. A ternary in its place gives `beq; li; b`, and a local computed once gives one selection. Example: `getFieldingStats` in `rep_1188.c`.
- **A `switch` compare tree with another pivot** (`cmpwi r0,2; beq; bge default; cmpwi r0,0; beq; bge case1; b default; b default` against a tree pivoting on 1): an explicit `case` label sharing the default's body adds its value to the tree. Write `case 3: default:`. Example: the offset table choice in `fn_3_15FB84`.
- **A `switch` whose listed cases branch forward past the default's code to a shared block** (`li r0,0` placed after the default's computation, which ends in `b` over it): the default comes first and falls into the cases when its guard fails, `default: if (!g_Stats.replayInd) { ...; flag = ...; break; } case 3: case 11: ... flag = FALSE; break;`. Cases first with an `if`/`else` in the default gives two copies of the zero block. Example: `fn_3_C9878` in `sta_c0.c`.
- **`cmpwi r,5; bge skip; cmpwi r,1; bge body; b skip`** is a `switch` with cases 1 to 4 sharing one body, not an `if` (which gives `blt skip` for the second test). Example: the bone loop in `fn_3_168414`.
- **`mr rS,r3` and a store through `r3` swapped right after a call** (`stb r31,41(r3); mr r30,r3` in the target): the stored field's type is wrong even though a byte store looks the same for `s8` and `u8`. Find a function that loads the field: plain `lbz` before indexing means `u8`. Example: `UnkTask3F60._29` in `fn_3_168CD8`.
- **A shared `mr r3,rN` before the epilogue in the target, but its own `mr r3,rN` before the branch in the base** (`bl processStadiumObjectFunction; b <end>`, where `<end>` is `lwz r0,68(r1); mr r3,r30`): the early exit jumps to the function's final `return ret;`, and the call's result is discarded. A second `return ret;` gets its own copy; `goto end;` with `end: return ret;` shares it. Example: `checkCollision` in `rep_D0.c`.
- **A different stored value** (`li r3,0` versus a register holding data) is a logic error in the source, not allocation. Example: in `calculateHitVariables` the original stores 0 into `inAirOrBefore2ndBounceOrLowBallEnergy`, not the star type.
- **Code shared with a `*_unused` static function.** Upstream's `_unused` means the standalone copy has no callers in the binary. The caller may hold its own written-out copy, possibly with statements in a different order, or call the function and have it inlined (units build with `-inline auto` and `-inline deferred`). Try both and keep whichever matches while the standalone function still matches. Example: `calculateHitVariables` matches with written-out copies of `starHitSetting_unused` and `calculateBuntVerticalAngle_unused`; calling them allocates registers differently.
- **Inlined same-file functions.** A call in the source with no `bl` in the object was inlined; small non-static functions from the same file inline too (`calculateBuntHorizontalPower`).
- **A function that matches standalone but not where it is inlined:** check every inlined copy before choosing between forms. `return (a >= b | c >= d) != 0;` and `if (a >= b | c >= d) return TRUE; return FALSE;` both give `neg; or; srwi` standalone, but only the second gives the target's `or.; beq; li r0,1; b; li r0,0` in the caller. Example: `fn_3_16D4D8`, inlined into `fn_3_16D5E4`.
- **A function outside the unit's `.text` range is inlined into one of its functions** (no callers, its body repeated in the unit; `match.py` warns "functions in the source but not in the target" once you write it as a plain function): look just outside the unit's `.text` range in `splits.txt` for an uncalled function with the same body. It belongs to the unit, so escalate the split. Meanwhile define it `static inline` under its `symbols.txt` name; a plain `static` function is still emitted even when every call inlines it. Examples: `fn_3_16C410` inlined into `fn_3_16CC2C` (`rep_4090.c`), `fn_3_15F874` inlined twice into `fn_3_15FF28` (`rep_3CE0.c`). The function may still have `bl` callers in the neighbouring unit: `fn_3_6C454`, inlined three times into `fn_3_6C4D0` (`rep_1090.c`), is called from `rep_1038`, whose `bl`s to the empty `fn_3_6C428` show those callers sit in another file. Once the split moves, make it a plain function with a header prototype: `-inline auto` still inlines it, and the object also gets the standalone copy the target has.
- **A `bl` only in the target, to an empty stub in the same file:** the stub gets inlined away, and `#pragma dont_inline` does not stop it. The caller matches once the stub has a real body; to check the rest now, delete the stub's definition temporarily and keep its prototype. Example: `fn_3_16C394` calls `fn_3_16B884`.
- **The base inlines a same-file function that the target calls with `bl`:** `-inline auto` inlines a callee whose statement count is under a threshold, so the original callee had more statements than yours, though they compiled to the same code. Measured on `fn_3_6A83C`: each expression statement, call, `if` and `return` counts about one; declarations with initializers count like assignments; empty statements and folded constants count nothing. Rewrite the callee in a plausible longer form (early `return`s instead of one nested `if`, a local for a value read twice) until the caller's size matches, and recheck the callee. To learn how far off you are, add `x = 0;` lines to a scratch copy until the inlining stops. Example: `fn_3_6A83C` stays a call in `fn_3_6AB58` only with its early returns and its `state` and `order` locals.
- **The size limit also counts expression size, not only statements.** Using a local `g_Stats_s* stats = &g_Stats;` as `stats->field` in about a dozen places raised fn_3_7C4E4's count by about three dummy statements, and a pointer that shortened `g_ReplayLogic[g_Stats.playFrameCounter][i].field` lowered it. `m -= 16.0f;` split from `m = sqrt(...) - 16.0f`, and `m = 64.0f * m; m /= 56.0f;` split from one expression, each added one with identical code (`m *= 64.0f` swaps the `fmuls` operands). Example: `fn_3_7C4E4`, called from `fn_3_7C9D8`.
- **One field loaded twice, once through a register set at function entry** (`addi r31,r7,g_Stats@l` before the calls, then `lbz r0,60(r3)` from a fresh `lis/addi` and `lbz r0,60(r31)`): the source mixes a local pointer and the global, `stats->x` for the early stores and one test, `g_Stats.x` for the other. Example: `fn_3_7C1FC` matches with `g_Stats._3C != 2 && stats->_3C != 13`. The reverse shows too: one block re-forms the address with `lis/addi r6` in the base where the target uses the saved register (`add r4,r30,r4; lwz r4,244(r4)`, `lbz r4,341(r30)`). `fn_3_6E24C` (`rep_1188.c`) matched with `GameControlsStruct* logic = &g_GameLogic;` used in the first statement and in `logic->Team_CaptainRosterLoc[logic->teamFielding]` and `++logic->rosterLoc_skippingCap`, and `g_GameLogic` everywhere else.
- **A global's address kept in a saved register for some fields, while a loop over the same global starts its strength-reduced pointer as a copy of it** (`mr r4,r31`) and other fields reload the address with `lis/addi`: a local `MiniGameStruct* mg = &g_Minigame;` is used for the fields read through the saved register, and the loops index `g_Minigame` directly. Writing the loops through `mg` too drops the strength reduction (`lbzx` from `mg` plus the index instead of `lbz 0x1a82(r4)` with `addi r4,r4,1`). Example: `fn_3_1136FC` and `fn_3_1133C4` in `rep_3290.c` (`mg->_1DCF` for a state machine, `g_Minigame.wallIndexTracker[i]` in the loops).
- **A comparison argument computed in a different place** (`cror; mfcr; rlwinm` or `srawi; subfc; adde` before the float loads in one listing, after them in the other): MWCC evaluates arguments left to right, and since ints and floats go in separate registers, register use does not show where a mixed prototype puts its `int` parameter. Move the flag in the prototype until the evaluation order matches. Example: `fn_3_C1344(s32, f32, f32, BOOL)` and `fn_3_BD504(f32, f32, f32, BOOL)` in `rep_F80.c`.
- **An index added before it is scaled** (`lhz r7,20(r31); addi r0,r7,1; slwi r0,r0,3; lwzx`) where the base folds the constant into the displacement (`slwi; add; lwz r4,8(r4)`): the accesses come from an unrolled loop, and `arr[x + i]` keeps the add once `i` becomes a constant. Example: `fn_3_912B4` in `rep_1610.c`, `for (i = 1; i < 3; i++) { lbl_80371C30[task->_14 + i]._00->_5C = (i - 1) << 16; }`.
- **A constant index scaled at run time** (`li r0,3; slwi r0,r0,2; add r5,r6,r0`), **or a register holding 0 compared with 0** (`li r29,0` before calls, `cmpwi r29,0` after them): the value is a counter that fully unrolled loops left behind, from generic code written for a count that is 1 here. Constant propagation after unrolling does not fold the arithmetic or the test. `fn_3_166448` in `rep_3E00.c` reads a file's offset table with `i = 0; for (j = 0; j < 1; j++) { for (k = 0; k < 3; k++) { models[j][k] = file + file[i++]; } }`, then tests `if (i == 0)` inside `for (i = 0; i < 1; i++)`. Two loads from that address, `lwz r0,0(r5)` and `lwz r0,4(r5)`, need a pointer local (`entry = &file[i];` then `entry[0]`, `entry[1]`); `file[i]` and `file[i + 1]` load the first with `lwzx`.
- **Stores in a different order with the same values,** such as `[2]` before `[0]`: chained assignments store right to left, so `a[0] = a[2] = 255;`. Example: `fn_3_169600`.
- **Stores in a different order with the same values,** such as `[2]` before `[0]`: chained assignments store right to left, so `a[0] = a[2] = 255;`. Example: `fn_3_169600`. The scheduler can still move a store, so script the orders of a longer chain: `fn_3_CB538` (`rep_2390.c`) stores `[2]`, `[1]`, `spark`, `[0]` and matches only as `t[0] = t[1] = t[2] = spark = v;`.
- **`addi rX,rX,-K` before the `add` in the base, after it in the target** (`add r3,r3,r0; addi r0,r3,-4`): MWCC reassociates `x = x + n - 4` into `x + (n - 4)`, while `x += n - 4` compiles as `(n + x) - 4`. Example: `frameToStartSwing` in `fn_3_1EAA8` (`rep_8C8.c`).
- **`addi rX,rX,1` after the `add` in the base, before it in the target:** MWCC reassociates `min + (rand() % range + 1)` into `(min + rand() % range) + 1`; parentheses and operand order do not stop it, and a `(u8)` cast adds a `clrlwi`. Hold the inner sum in a local: `shade = rand() % range + 1; color = min + shade;`. Example: `fn_3_16C878` in `rep_4090.c`.
- **A float argument of an inlined call computed late** (the base adds the constant after the callee's first `bl` into a scratch FPR; the target adds it into the saved FPR before): update the variable before the call, `x += 1.8f; draw(d, x, y);`, instead of passing `x + 1.8f`. Example: `fn_3_16DB6C` inlining `fn_3_16D810`.
- **A saved pointer moved into its argument register before a branch that computes a later argument** (`mr r4,r27` before the `beq` of `ch = 0x18; if (i != 0) ch = 0x17;`, while the base moves it after the branch, at the call): the arguments were locals assigned before the branch, and this one was a copy into another pointer type, `const VecXYZ* from = pos;`. MWCC propagates a copy of the same type (`VecXYZ* from = pos;`) into the call, which puts the move at the call. The order of those locals' declarations then decides the scheduling around them. Example: `fn_3_C1344` (`to`, `params`, `from`, `scale`).
- **A table load before a call in the target, after it in the base** (`lbzx r31,...; bl RandomInt_Game; cmpw r3,r31`): MWCC evaluates a call in an expression before the other operands, whichever side it is on, so the original read the value in its own statement first: `chance = table[i][j]; if (RandomInt_Game(100) < chance)`. Example: `fn_3_212A0`.
- **A retry counter that only increments when the loop repeats** (`cmpwi r30,2; bge exit; addi r30,r30,1; b top`, where `while (... && tries++ < 2)` gives `cmpwi; addi; blt top`): `for (;;) { ...; if (done || tries >= 2) break; tries++; }`. Example: `fn_3_20FB0`.
- **Float loads in another order, and a different constant addressed through `addi rX,rY,sym@l; lfs f,0(rX)`:** how the arithmetic is split into statements decides the scheduling. Try splitting a compound expression and moving neighbouring stores. Example: `fn_3_20EEC` matched only as `index` stored first, then `width = max - min; width /= 5.0f; x = min + width * index;`. In `fn_3_6CD88` the `addi`/`lfs 0(rX)` form for two constants appeared only with the scale in its own statement, not as one expression inside `x += x * (...)`.
- **A float test as `bge <next>; b <epilogue>` in the target** where the base has `blt <epilogue>` or `cror; beq <next>; b <epilogue>`: the test is the last term of an `||` guard, which branches past the return when false and falls through to it: `if (!fn(i) || data->_50 < 0.1f) return;`. A separate `if (data->_50 < 0.1f) return;` gives `blt`, and `!(data->_50 >= 0.1f)` gives the `cror` form. Example: `fn_3_16D5E4` in `rep_4090.c`.
- **An early-return guard ending in `bne <next>; b <epilogue>`** where the target has a single `beq <epilogue>`: MWCC does not invert the last test of `if (A && (B || C)) return;`. Put the body under the negated condition, `if (!A || (!B && !C)) { ... }`, and fold a following `if` into it with `&&` when the target exits with `bnelr`. Example: `fn_3_CB234`, `fn_3_CB1B0`, `fn_3_CB284`. In a leaf function the same shows as `bgt <next>; blr` against the target's `blelr`: `if (state == 6 || state <= 1) return;` matched as `if (state != 6 && state > 1) { ... }` (`fn_3_6C000` in `rep_1038.c`).
- **A load scheduled before the first test of an `&&`** (`lwz r0,arr(r3)` between `cmplwi` and `bne` of the first operand): the original read it into a local before the `if`. Example: `player = lbl_8036E548._2C50[task->_33]; if (task->_34 == 0 && player != NULL)` in `fn_3_CAE00`.
- **A list walk with no entry branch** (the body runs before the first `cmplwi; bne top`): the source is a `do { } while ((p = p->next) != NULL);`. A `for` loop adds `b <test>`, even right after an `if (dead != NULL)` that proves the first test. Example: both loops of `fn_3_16C548` in `rep_4090.c`.
- **A countdown loop with the test at the bottom and no entry branch** (`cmpwi r25,0; subi r25,r25,1; bne top`): `i = 2; do { ... } while (i--);`. `i = 3; while (i--)` adds an entry branch and `for (i = 2; i >= 0; i--)` gives `addic.; bge`. Example: `fn_3_CABF0`.
- **A short constant-count loop kept as a loop in the target** (`addi r5,r5,1; stb r3,0x1dc4(r4); ...; cmpwi r0,4; blt`, or `cmplwi r5,7; blt` with no `mtctr`) where the base unrolls it fully or counts with `bdnz`: the original is a `do`/`while`, `i = 0; do { counts[i] = 0; } while (++i < 3);`. MWCC unrolls and `ctr`-converts `for` loops with constant bounds, not `do`/`while` loops. The same form explains a search loop whose found path increments the index on its way out (`mr r27,r5; addi r5,r5,1; b after`): `i = 0; do { ...; if (found) { idx = i++; break; } i++; } while (i < 7);`. `rep_3290.c` uses it for eleven loops, in `fn_3_1133C4`, `fn_3_1136FC`, `fn_3_113A48` and `fn_3_114384`.
- **An array filled at a counter's index through an advancing pointer** (`addi r7,r1,28` before the loop, then `stw r8,0(r7); addi r7,r7,4` beside `addi r26,r26,1`) where the base stores with `stwx r8,r4,r3` and an offset register: the store and the increment were separate statements, `candidates[m] = i; m++;`, not `candidates[m++] = i;`. Example: `fn_3_114384` in `rep_3290.c`.
- **A store of 0 and a loop counter sharing one `li rX,0`:** a chained assignment, `task->_34 = i = 0; for (; i < 2; i++)`. Separate statements load 0 twice. Example: `fn_3_CAF9C`.
- **A range test over different values** (`addi r0,r4,-49; clrlwi r0,r0,24; cmplwi r0,1; ble` against the base's `addi r0,r3,-48; ... cmplwi r0,2`): MWCC merges consecutive `==` tests in an `||` chain into unsigned range checks, and the grouping depends on the operand. With an `s8` local, `id == 0x30 || id == 0x31 || id == 0x32 || id == 0x33` gives a 0x30 to 0x32 range; reading the field in each test (`p->_252 == 0x30 || p->_252 == 0x31 || ...`) gives `== 0x30`, a 0x31 to 0x32 range, then `== 0x33`. Example: `fn_3_E1478`.
- **Consecutive values tested one by one** (`cmplwi r0,9; beq; cmplwi r0,10; beq`) where the base merges them (`addi r0,r3,-9; clrlwi; cmplwi r0,1; ble`): the original negated an `&&` chain of `!=`, which MWCC does not merge. `if (!(type != 1 && type != 6 && type != 9 && type != 10 && type != 0x32)) return FALSE; return TRUE;` matched; the `||` chain of `==`, a `switch` (a compare tree) and `if (type != 1 && ...) return TRUE;` (blocks in the other order) did not. `cmplwi` on a value masked with `clrlwi r0,r3,25` means a `u8` local, `u8 type = checkCollision(...) & 0x7F;`. Example: `fn_3_B7CDC` and `fn_3_B7C2C` in `rep_1CB8.c`.
- **`li rX,K; beq; li rX,K-1` in the target, `cntlzw; srwi; addi` or `neg; or; srawi` in the base:** MWCC turns `i == 0 ? K : K-1`, and an `if`/`else` that assigns one constant in each branch, into branchless code. Assigning the default first keeps the branch: `ch = 0x18; if (i != 0) { ch = 0x17; }`. Example: `fn_3_C11CC` and `fn_3_C1770` in rep_1F58.
- **An array element indexed by `i - K` addressed through its own induction pointer in the base** (`addi rN,rN,0x154` at the loop's end) **but recomputed in the target** (`subi r0,r6,9; mulli r10,r0,0x154; add`): the original took a block-scoped pointer, `InMemRunnerType* runner = &g_Runners[i - 9];`, at the top of the branch. `g_Runners[i - 9].x` is strength-reduced, and an `int` index local stops that but allocates differently. Example: `fn_3_6BEA4` in `rep_1038.c`.
- **A copy loop unrolled by 4 with an unsigned trip count** (`cmpwi rN,0; beq <exit>; srwi. r0,rN,2; mtctr r0`, remainder `andi. rN,rN,3`, and the source pointer advanced in its register) where the base unrolls by 8 (`ble`, `cmpwi rN,8`, a `cmpw` remainder test): the loop counts its parameter down, `while (count--) { dst[k++] = *src++; }`, not `for (i = 0; i < count; i++)`. Example: `fn_3_15FA58` in `rep_3CE0.c`.
- **A countdown loop that tests before it decrements** (`cmpwi r5,0; subi r5,r5,1; ...; bne top`, leaving -1 when nothing was found): `i = 1; do { if (found) break; } while (i-- != 0);`. `for (i = 1; i >= 0; i--)` is unrolled when inlined, or compiles to `addic.; bge`. Example: `fn_3_C1930` (inlined across rep_1F58) and `fn_3_C095C`.
- **A search loop whose bottom test loads through its own offset register** (`addi r3,r3,4; addi r5,r5,4; lhzx r0,r4,r3` with the body testing `lhz r0,0(r5)`) where the base merges both into one `lhzu r0,4(r3)`: the test pre-increments its index, `do { ... } while (table[++i][0] != 0xFFFF);`. `i++;` as a statement before `while (table[i][0] ...)` and `for` loops differ. Example: `fn_3_CB3AC` in `rep_2390.c`.
- **Byte stores indexed from `buf+K`** (`addi r31,r5,1; stbx r4,r31,r30`) **next to copies addressed with displacements:** MWCC compiles `buf[x + K] = v` as `(buf + K)[x]`, but folds `&buf[x + K]` into `(buf + x) + K`. When the target indexes some accesses through a separately computed `x + 0x20` and folds others into `(buf + x) + 0x22`, the source had a second index variable for the former only: `row2 = row + 0x20; buf[row2] = g; *(u16*)&buf[row + 0x22] = *(u16*)&buf[row2];`. Example: `fn_3_C0D10`.
- **Word stores through `addi rX,rI,68; stwx` in the base where the target adds the index to the row first** (`slwi r3,r0,3; add r10,r9,r3; stw r4,68(r10); stw r3,72(r10)`) for `arr[team][e->slot + 1][k]`: the original read the index into an `int` local before testing it, `slot = e->slot; if (slot == 9) ... else { arr[team][slot + 1][0] = ...; arr[team][slot + 1][1] = ...; }`. Reading the field in each subscript gives the `stwx` form, and pointer locals (`entry = arr[team] + slot`) share the `+60` base hoisted for other stores. - **`bl memcpy` in the target where the base copies a struct with `lwz`/`stw` pairs:** the original called `memcpy(&a[i], &a[i - 1], sizeof(a[i]))`; MWCC copied the same struct inline when it was assigned. Example: `fn_3_16B884` and `fn_3_16A07C` in `kinoko.c` (0x2C-byte structs).
- **The same statements repeated for each array element:** MWCC did not unroll a 6-iteration loop, even one holding only a `memcpy` and a store, so the original wrote the copies out. Example: the six ribbons in `kinoko.c`.
- **An `else if` chain where a failing inner test jumps to the last `else if`'s test, which reloads its operands, while the middle tests reuse values loaded once** (the base repeats the outer conditions or falls through to another `else`): the middle branches are nested under one outer condition and leave with `goto` when they assign. `} else { if (a >= 3 && n) { f = ...; b = ...; if (f < b && f + n >= b) { x = 3; goto done; } if (f == b) { x = 2; goto done; } } if (... + 5 < ...) x = 0; } done:`. Repeating the outer condition in a second `else if` keeps both tests. Example: `fn_3_1DEB8` in `rep_868.c`.
- **Two `blr` in a row at the end of an `if` branch in the target** (`bltlr; li; stb; blr; blr`), where the base has one: the branch ends with an explicit `return;` after its nested `if`s, before the `else`. Example: `fn_3_78730` (`rep_12D0.c`).
- **Shifting a history array** (`a[4] = a[3]; ... a[1] = a[0];`): if the target interleaves each load with its store (`lbz r0,57(r6); stb r0,58(r6); lbz r0,56(r6); ...`) while the base loads all four first, the original is a loop, `for (i = 4; i > 0; i--) a[i] = a[i - 1];`. The change also moved a later reload of an unrelated global into place. Example: `lbl_3_common_bss_32A94._36` in `fn_3_77914` (`rep_12D0.c`).
- **A saturating increment that re-forms the address with `lbzu` and reloads the byte** (`lbzu r5,22(r10); cmplwi r5,254; bge; lbz r5,0(r10); addi; stb`) where the base loads with a displacement and reuses the value: the original indexes the array in each statement, `if (tbl[t][k]._16 < 0xFE) tbl[t][k]._16++; else tbl[t][k]._16 = 0xFF;`, instead of going through a pointer local. Example: `lbl_803537E4` in `fn_3_77914` (`rep_12D0.c`).
- **A loop whose result nothing uses, right before an identical loop** (two copies of an inlined binary search in a row, the first one's index dead): the source called an inlined function and used only part of its output. MWCC deletes the dead arithmetic but keeps loops. `fn_3_2D6C`, `fn_3_310C` and `fn_3_28E4` in `rep_140.c` evaluate a 2D spline into `VecXZ xz` and keep only `xz.z`.
- **An inlined function's result stored through the output pointer later in the target than in the base** (`stfs f7,0(r3)` scheduled after the next computation's loads, where the base stores right away): the function wrote into a local struct and the caller copied it out, `fn_3_19B0(t, &xy, ...); out[i].x = xy.x; out[i].y = xy.z;`. MWCC keeps the local in registers, and a store through `out` no longer orders the later loads from local arrays. Passing `(VecXZ*)&out[i]` stores at once. Example: `fn_3_2D6C` in `rep_140.c`.
- **Float fields reloaded after every store** (`stfs f0,56(r1)` then `lfs` of the same source fields again, where the base loads each source once), **with the locals at consecutive stack offsets:** the written locals and the read ones are elements of one array, so MWCC assumes the stores may alias the reads. `fn_3_67EF0` (`rep_EA0.c`) keeps two ring points and the projected pair in `Vec pts[4]` (`pts[idx]`, `pts[!idx]`, `pts[2]`, `pts[3]`) and two direction vectors in `Vec dir2[2]`; separate locals, or pointers to them, gave 88% to 91%, the arrays 97.65%. - **A flag computed right after a call and tested at the end** (`addi r0,r3,1; srawi. r12,r0,1` right after `bl`, its `beq` after a run of stores): the original assigned it to a local before the stores, `side = fn(...); side = (side + 1) >> 1; ... if (side)`. Testing `if ((dir + 1) >> 1)` at the end moves the shift down. Example: `fn_3_678B8` (`rep_EA0.c`).

## `...rodata.0` in the base, constants one by one in the target

The base shows `lis rX,...rodata.0@ha; addi` and then `lfs f0,100(rX)`, while the target names each constant (`lfs f0,lbl_3_rodata_418C@l(r4)`). MWCC pools a function's `.rodata` references once it touches enough of them (three float constants alone stayed separate in `fn_3_16D810`; adding a `GXColor` initializer pooled all four).

- **Cause: the original's `.rodata` began with weak objects, which turns pooling off for that section** (observed: with weak objects first nothing in `.rodata` is pooled, while `.bss` statics still are). `game/UnknownHomes_Game.h` defines `SQRT2_LINKAGE extern` before including `math.h`, so `dolsqrtf2` becomes an `extern inline` whose static locals are emitted as weak `_half$localstatic` and `_three$localstatic` even when unused; plain `#include "math.h"` emits nothing. The target's `.rodata` does not show them, presumably because the linker kept one weak copy for the whole module.
- **Fix, only when the base shows `...rodata.0`:** include `game/UnknownHomes_Game.h` above `header_rep_data.h`, as `game_batter.c` does. The `.rodata` section score loses those 0x10 bytes; the code matches. Example: `rep_4138.c`, where this matched `fn_3_16D810` and `fn_3_16DB6C`. `-pool off` also matches such functions but breaks pooled `.bss`, and GC/1.3.2 to 2.7 behave identically, so the include order is the explanation, not the flags.
- The same include matched `fn_3_16B5B4` in `kinoko.c`, which pooled once an inlined callee added string literals.
- **When nothing needs unpooled constants, include `header_rep_data.h` first.** That puts `repHeaderData` at offset 0 as in the target and scores `.rodata` higher (92% against 86% in `rep_F80.c`); every function matched with either order.

## `.rodata` below 100% with every function matched

- **Literal constants in the reverse of the target's order:** the source lists functions in address order. With `-inline deferred` MWCC generates functions last to first (objdiff's `reverse_fn_order` hides this for `.text`) and creates each function's constants as it goes, so REL source lists functions from the highest address down; `tools/reverse_functions.py` converts a file. Example: rep_940 `.rodata` 83% to 93%.
- **The weak `dolsqrtf2` constants** (0x10 bytes, from `game/UnknownHomes_Game.h`) stay as a difference; the linker keeps one copy for the whole module. The explanation above is incomplete: in `rep_10E8`'s target, `_half` and `_three` are local objects in the middle of `.rodata` (0x1140, 0x1148), yet its constants are unpooled and the include order still matched.
- **Avoid them when the unit needs nothing from `game/UnknownHomes_Game.h`:** include only what it uses (`Dolphin/vec.h`, `static/UnknownHomes_Static.h`); `.rodata` then scores 100%. Example: `rep_3C80.c`, 92.31% to 100%.
- **The weak `dolsqrtf2` constants** (0x10 bytes, from `game/UnknownHomes_Game.h`) stay as a difference; the linker keeps one copy for the whole module, rep_0's: that target's `.rodata` begins with `_half` and `_three`, so `rep_0.c` includes `game/UnknownHomes_Game.h` above `header_rep_data.h` and scores 100%. The explanation above is incomplete: in `rep_10E8`'s target, `_half` and `_three` are local objects in the middle of `.rodata` (0x1140, 0x1148), yet its constants are unpooled and the include order still matched.

## `.data` or `.bss` below 100% with every object defined

- **An all-zero object in the target's `.data`:** define it with an explicit initializer, `static T x = { 0 };`, which MWCC keeps in `.data`; without one it goes to `.bss`. Example: `lbl_3_data_28928` in `kinoko.c`.
- **A trailing `gap_..._data` symbol, or a last object larger than its type:** the linker padded the section up to the next unit's alignment (8 for `.data`, 32 for kinoko's `.bss`). Leave it; no source object belongs there. To confirm, `objdump -s -j .data` of both objects differs only in trailing zeros the base lacks. Examples: `rep_3F60.c` scores `.data` 99.78% (4 bytes at 0x28924); `rep_3E58.c` scores `.data` 98.73% (4-byte `gap_04_000285A4_data` after the jump table) and `.bss` 50% (`lbl_3_bss_B9E0` is an `s8` with size 0x20 in `symbols.txt`). A `switch` jump table needs no definition: MWCC emits it as `@NNN` and objdiff pairs it with `jumptable_...`.
- **A `gap_*` symbol between two objects** (3 bytes after a `u8`, before a 4-aligned object): alignment padding inside the file; objdiff counts it as unmatched, so the section stays below 100%. Leave it. Example: `rep_4138.c` `.bss` 88.46% from `gap_05_0000D6E1_bss` and `gap_05_0000D6ED_bss`.
- **An object larger than everything the code touches, ending at the unit's end on no alignment boundary:** the tail is a separate unreferenced object, not padding. Check a `memset` or loop bound for the real size, split the `symbols.txt` entry, and declare the tail too (MWCC keeps unreferenced statics). Example: `lbl_3_bss_D6F0` was 0x24, but `memset` clears 0x18; the last 0xC became `lbl_3_bss_D708` (`rep_4138.c`, `.bss` 66.67% to 88.46%). Likewise the 8 bytes `3, 0` after `rep_2308`'s four 0x28-byte draw entries became `lbl_3_data_17DB8`.

## Before committing

- Run `tools/match.py` on every function that uses a type, prototype or symbol you changed, not only the one you were fixing.
- Run `python3 tools/regress.py`; it fails on any dropped objdiff score or lost strict match. Its summary goes in the pull request.

## Tool pitfalls

- Install m2c from https://github.com/matt-kempster/m2c. The PyPI package named `m2c` is an unrelated project.
- `match.py --m2c` prepares the unit's context for m2c (preprocesses it and strips inline asm); the draft is typed only for globals the source's includes declare, so a placeholder file including only `header_rep_data.h` gives `?` types until you add `game/UnknownHomes_Game.h` and the like.
- `match.py` reports a function you have written as `missing` when objdiff cannot pair it, for example after a callee's empty stub was inlined into it; give the callee a body first.
- decomp-permuter's own `import.py` breaks on this project; `tools/permute.py` explains why in its header and replaces it.
- `tools/permute.py` fails to compile its view when the source has `sizeof(T) + (x)`: pycparser reads it as `sizeof((T) +(x))`, a cast. Parenthesize the product, `(20 * sizeof(T)) + (...)`, which compiles the same.
- `tools/permute.py` fails with a syntax error on `va_arg(args, s32)`, because pycparser cannot parse MWCC's `_var_arg_typeof`. For the permuter run only, write `*(s32*)__va_arg(args, 1)` (the same code), and restore `va_arg` afterwards.
