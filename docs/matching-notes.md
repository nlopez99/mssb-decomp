# Matching notes

Lessons from matched functions, indexed by the **symptom** `tools/match.py` shows. Find the symptom, try its causes in order, and add a lesson here when a function teaches you something new (symptom, cause, fix, example).

## `reloc`: a reference points somewhere else

objdiff's report scores these 100% because it ignores relocation targets; the unit cannot link until they are fixed.

- **Placeholder shadows a named symbol.** The source declares its own `extern ... lbl_3_data_XXXX` for an address that `symbols.txt` already names. Look the address up in `config/GYQE01/**/symbols.txt`, use the existing header declaration, delete the placeholder. Example: `calculateHorizontalPower` read `hitTrajOptions` through `lbl_3_data_5B34`.
- **Source is ahead of `symbols.txt`.** The source uses a good name that `symbols.txt` still calls `lbl_...`. Rename it in `symbols.txt` after checking the source type's size equals the symbol's `size:`, then fix every other use of the old name (`tools/check_symbols.py` lists them). Example: `gameInitOptions` and `aILevel` for `setInMemBatterConstants`.
- **Wrong callee or global.** The call or load goes to a different symbol with the same shape. Treat it as a source bug, not a naming issue.
- **`sym+0xNNNN@ha` / `sym+0xNNNN@l` in the target.** MWCC never folds a constant offset into a relocation: `&arr[k]`, `arr + k` and struct members all compile to `addi rX,rX,sym@l; addi rX,rX,k`. So the original referenced a separate object that `symbols.txt` lacks. Declare an `extern` named by its address with the size the code implies, and escalate the split; the function then reports `reloc` until `symbols.txt` gets the symbol. Example: rep_1330's `lbl_8034E9A0+0x4C28` and `+0x4E44`, main-DOL objects at 0x803535C8 and 0x803537E4.
- **`...bss.0` or `...data.0` with offsets in the base.** MWCC addresses a file's statics from one base symbol plus literal offsets (`addi r4,r5,160`, `lwz r3,8(r31)`), so the target's offsets give the layout, and `symbols.txt` often lumps several statics into one symbol. Declare one static per object, in reverse address order (MWCC lays them out in reverse declaration order), including statics nothing in the file reads, and split the symbol in `symbols.txt` to match. One static struct does not reproduce this: it recomputes its base in each branch, while the pool base is computed once. Example: kinoko's `lbl_3_bss_BA00` to `BAA0`.
- **One data symbol plus offsets past its size in the target** (`addi r31,r5,lbl_3_data_285A8@l` then `addi r6,r31,0x360`, while the base loads each symbol with its own `lis`/`addi`): the target reaches several objects from one pool base, so they are statics of this file. Initialized `.data` statics are laid out in declaration order (unlike `.bss` above), so declare them in address order. An offset folded into one `addi` means a separate static; `arr[1]` compiles to `addi` of the array start, then the element offset. Extern declarations cannot reproduce this: if the data lies outside the unit's `splits.txt` ranges, keep externs under the `symbols.txt` names and escalate the `.data` range, with a scratch copy that defines the statics as evidence. MWCC pooled a function's accesses when it touched three of these statics and named each when it touched two. Examples: `fn_3_168704` and `fn_3_168DFC` in `rep_3F60.c`, `fn_3_15BAA0` in `rep_3AE8.c`, `fn_3_C11CC` and `fn_3_C1770` in `rep_1F58.c`.

## Registers only: same instructions, different register numbers

- **Shared across functions.** When several functions show the same unexplained allocation while identically written ones match, look at what they share before tweaking each: a prototype's parameter or return type changes the compiler's internal conversions and so its allocation, with identical instructions. Example: `minigame_checkIfAIInputIs_Algorithmic_Or_ControllerBased(u8)` should take `s8` (callers pass `s8 characterIndex[]`); that fixed three functions.
- **Declaration order.** The order locals are declared in affects which callee-saved register each gets; try moving the variable that lands in the wrong register above its neighbour. Example: `inputs` declared before the `BOOL` flag.
- **Statement order of independent loads.** Which register a shared base (`addi r10,r3,sym@l`) gets depends on where its first use sits among the statements that read through it. Example: `fn_3_CABF0` in `rep_2308.c` matched once `model = &bss._010->_C4;` moved above the six local-array fills, written as `ids[i]`, `anims[i]` pairs in the target's store order.
- **Volatile registers differ in a function's setup code** (`lbz r0,30(r27)` against `lbz r4,30(r27)` for the same field): the statement order of independent setup assignments decides them. Script every order of the first few assignments, crossed with a few declaration orders; that is a dozen runs. Example: `fn_3_168A6C` matched only as `model`, then `anim`, then `animData` assigned, with `animData` declared first. The same order decides how the whole entry block is scheduled: `fn_3_15FB84` went from 86% to 97.7% when a float local was computed after the first of three stores instead of before them.
- **A value loaded once.** Holding a repeated load in its own local (with the type of the expression, usually `int`, not the field's `u8`) changes allocation. Example: `slapContactSize` in `calculateBuntHorizontalAngle`; `u8 status = g_GameLogic.gameStatus;` tested by an `if` and a later `switch` in `fn_3_E1478`.
- **Operands swapped in an add** (`add r31,r31,r0` versus `add r31,r0,r3`): split the expression, e.g. `value = tex[i]; value += step * 2;`. Example: `fn_3_16943C`.
- **Operands swapped in an `fmadds`** (`fmadds f0,f2,f1,f0` against `f0,f1,f2,f0`): swapping or regrouping the C operands changes nothing. Compute the multiplicand into a local first: `t = min + range * rand() / 32767.0f; x = t * (n - i) + i;`. Example: `fn_3_15BAA0`.
- **Operands swapped in an `fmuls` by a constant, product in a new register** (`fmuls f1,f2,f1` with the constant in `f1`, against `fmuls f1,f1,f2`): MWCC puts the literal first in both `s = s * K` and `s = K * s`, while `s *= K` keeps the order but writes the product back into `s`'s register. Passing both through `math.h`'s inline `scaleValue` keeps the order and gives a new register: `scale = scaleValue(a / 512.0f, 0.27208483f);`. Example: `fn_3_6CD88`.
- **Two loads in swapped registers feeding two stores** that already come out in the target's order: swap the two assignment statements. The scheduler keeps the store order, but allocation follows statement order. Example: the `_00` and `_10` stores before `fn_8002CE4C` in `fn_3_15BAA0`.
- **Operands swapped in a branchless `or`/`or.` chain** (`cntlzw; srwi; or; or.` tests): reorder the operands of `|` in the condition; each order gives a different pairing. Example: `fn_3_16E1EC` matches only as `lbl_3_bss_D6EC | !lbl_8036E548._3088 | !lbl_3_bss_D6E4`.
- **A loop counter in the register that held a parameter before a call** (`mr r31,r3` at entry, later `li r31,0` for the loop): the loop reuses the parameter, `for (idx = 0; idx < 2; idx++)`; a new `i` gets a volatile register. Example: `fn_3_C0C4C`.
- **Two local arrays at swapped stack offsets, or their initial values loaded into different registers:** the array declared later gets the lower address, and the order of the statements that fill them decides the registers. Example: `fn_3_C095C` needs `u32 animIds[2]; UnkAnim1F58* anims[2];` filled as `animIds[0]`, `anims[0]`, `animIds[1]`, `anims[1]`.
- **A parameter and another long-lived value swap callee-saved registers** (`mr r28,r3` at entry against `mr r27,r3`, with every use renumbered) and declaration order changes nothing: the original took the parameter as `void*` and copied it into a typed local. Callbacks stored in a function pointer are written this way: `void fn(void* arg) { UnkDraw3CE0* draw = arg; ...`. Example: `fn_3_15FF28` in `rep_3CE0.c`.
- **Block scope moves a volatile register when declaration order does not.** In `fn_3_15FB84` no order of the function-scope declarations changed which of `n`, `marker` and `player` got r9 to r11, but declaring `player` inside the loop body did (it then took r11, as in the target, though `n` and `marker` swapped). Try moving a loop-only variable into the loop's block.
- **Float registers differ around `sin`/`cos` calls** (hoisted loop constants assigned to saved FPRs in a rotated order, or `frsp f1,f1` where the target has `frsp f0,f1`): the original called the `sinf`/`cosf` inlines, not `(f32)sin(x)`. Use `sinf_kludge`/`cosf_kludge` from `stl/math.h`; the permuter found nothing in 9000 iterations. Example: `fn_3_167178` and `fn_3_1674D0` in `rep_3E58.c`.
- **The inlined callee's argument shares a register with the variable it is loaded from** (`lwz r31,20(r31)` loading `task->_14` over `task`, while the base keeps `task` in r30): put the arguments in locals in the target's evaluation order, `id = table[rand() % n]; player = task->_14; fn_3_166C30(player, id);`. Example: `fn_3_166E04` and `fn_3_166FCC`.
- **Stalled after a few tries:** run `python3 tools/permute.py <unit> <function>` and the command it prints. Take the permuter's idea, not its literal code (it reuses unrelated variables and adds casts like `(long long)`), then rewrite it plausibly and recheck.

## Instruction differences that reveal types

- **Signedness of an int-to-float conversion.** Signed: `xoris rX,rX,0x8000` with the double constant `0x4330000080000000`. Unsigned: no `xoris`, constant `0x4330000000000000`. Fix the element or variable type to match.
- **A `u8` field converted with the signed constant** (`lbz` then `xoris`): the value went through an `int` local first. `alpha = p->color[3]; alpha -= 255.0f / n;` converts signed; `alpha = p->color[3] - 255.0f / n;` converts the `u8` as unsigned. Example: `fn_3_16C548` in `rep_4090.c`.
- **A local loaded from a `u8` field, compared with `cmplwi` and used as an index with a plain `slwi`:** the local is `u32`. An `s32` local compares with `cmpwi`; a `u8` local masks the index with `rlwinm`. Example: `stadium` in `fn_3_16C410` (`rep_4090.c`).
- **Array shape from index arithmetic.** `subfic r0,e,3; slwi; lwzx` from a struct's start is one 4-element array indexed `[3 - e]`, not two 2-element fields. Example: `trajOptions_s._0` must stay `s32[4]`.
- **`extsb` before a call only in the target:** the callee takes `int`, and the caller sign-extends its `s8` argument; with an `s8` parameter the callee extends instead. Example: `fn_8001B728(s32, s32, Vec*)`.
- **A flag parameter tested with `clrlwi. r0,r4,24`** is a `u8`; a `BOOL` (`int`) compiles to `cmpwi`.
- **`extsb` before `cmpwi rX,-1` but none before `cmpwi rX,1` on the same field:** the field is `s8`; MWCC drops the sign extension when testing equality with a non-negative constant. Example: `AIStruct.aiPitchDirectionInput` in `fn_3_20CEC`.
- **`cmplw` between two computed element addresses:** the source compares two arrays, which decay to pointers. Keep the original's bug. Example: `g_Scores._04[batting] > g_Scores._04[fielding]` in `fn_3_212A0`.
- **`extsb` right after the `lbz` of an `s8` field, before an early test:** the field is read into an `int` local (`s32 idx = player->_254;`). An `s8` local delays the sign extension to its first use. Example: `fn_3_168CD8` and `fn_3_16892C`.
- **An `s8` tested with `extsb. r0,rX`, then extended again into a saved register** (`extsb r19,r5` scheduled into the next load) that indexes arrays and is passed to a call: an `s8` local copied into an `int` local after its guard, `idx = g_Minigame.minigameFielderIndex[i]; if (idx < 0) return; f = idx;`. Example: `fn_3_E1478` in `rep_2940.c`.
- **A loop pointer advanced by a stride no field explains** (`addi r8,r8,9` with fixed offsets such as `0x19EA(r8)` and `0x19EF(r8)` into a global): the header's flat fields there are an array of structs of that size. Check that no source uses the flat names, restructure the header, and run `match.py` on every user. Example: `MiniGameStruct._19E8[4]` (9-byte elements) and `MiniGameControlStruct` (`[4]` arrays up to 0x18F8, not two 0x16-byte structs) for `rep_2940.c`.
- **`extsh` of a converted value right before its halfword store, only in the target** (`fctiwz; stfd; lwz r0; extsh r0,r0; sth r0`), while an earlier value of the same variable is tested with `extsh.`: the local is an `int` assigned through an `s16` cast, `int magnitude = (s16)(64.0f * m / 56.0f);`. An `s16` local drops the extension before the store. Example: `fn_3_6CD88`.
- **`andi.` with a 16-bit mask where the base has `rlwinm`** (`andi. r0,r3,0xffbf` against `rlwinm r0,r3,0,26,24`): the source clears the bit with a 16-bit literal, `x &= 0xFFBF;`; `x &= ~0x40` compiles to `rlwinm` even for a `u16`. Example: `fn_3_6D304`.
- **A `u8` copy of a value.** `clrlwi rX,rY,24` before comparisons can mean the code compares a `u8` variable assigned from a cast (e.g. `u8 starType = (s8)field`), not the field directly.
- **`neg` before `cntlzw` only in the base:** a pointer tested with `p == NULL` inside a `|` chain. Write `!p`, which compiles to plain `cntlzw; srwi`. Example: `fn_3_16E1EC`.
- **A call's float result as the second operand** (`fmul f0,f0,f1` or `fcmpu cr0,f0,f1` in the base, `f1,f0` in the target): swapping the C operands changes nothing. The source used another operation: `acos(x) / 2.0f` becomes `fmul` by the double 0.5 with the call result first, and `if (PSVECMag(v))` compares the result first against 0.0. Example: `fn_3_CAF9C`. The same holds for a float variable: `if (dir)` gives `fcmpu cr0,f31,f0` with the variable first, while `if (dir != 0.0f)` puts the constant first (`fn_3_15C024`).
- **`mulhwu` by `0xB21642C9` and `mulli 23` on a `rand()` result:** an unsigned modulo, `rand() % (sizeof(table) - 1)` for a 24-byte table of 23 entries plus a terminator. Example: `lbl_3_data_28558` in `rep_3E58.c`.
- **A word loaded from `.rodata`, stored to the stack, reloaded after a call and written to the FIFO** (`lwz r0,lbl@l; stw r0,8(r1)` ... `lwz r0,8(r1); stw r0,-0x8000(r3)`): a local `GXColor color = { 0xFF, 0xFF, 0xFF, 0xFF };` sent with `GXColor1u32(*(u32*)&color)`. Example: `fn_3_16D810`.

## Structure differences

- **A `Vec` initializer copied from `.rodata` only inside a branch, and the locals around it at the wrong offsets:** it is declared with its initializer in that block (`Vec offset = { 0.0f, 0.0f, 0.0f };`), and the locals at lower offsets are declared after it in the same block. Example: `fn_3_1674D0`.
- **Float constants loaded into saved registers before straight-line code, and a global's address formed with `addi` and loaded with `lwz r0,0(rX)`:** the body is a one-pass loop, `for (i = 0; i < 1; i++)`; loop-invariant code motion runs before the loop is unrolled away. Statements whose loads use the hoisted address go inside the loop. An `fmadd` with a 0.0f addend there is `angle = 0.0f; angle += 45.0 * r;`, since `0.0f + 45.0 * r` folds. Example: `fn_3_1678A8`.
- **Stack offsets swapped between two locals** (`addi r3,r1,72` against `addi r3,r1,24`, or array stores at `8(r1)` against `16(r1)`): MWCC gives later-declared locals lower offsets; swap their declarations. Example: `m` declared before `tmp` in `fn_3_168414`.
- **A `switch` compare tree with another pivot** (`cmpwi r0,2; beq; bge default; cmpwi r0,0; beq; bge case1; b default; b default` against a tree pivoting on 1): an explicit `case` label sharing the default's body adds its value to the tree. Write `case 3: default:`. Example: the offset table choice in `fn_3_15FB84`.
- **`cmpwi r,5; bge skip; cmpwi r,1; bge body; b skip`** is a `switch` with cases 1 to 4 sharing one body, not an `if` (which gives `blt skip` for the second test). Example: the bone loop in `fn_3_168414`.
- **`mr rS,r3` and a store through `r3` swapped right after a call** (`stb r31,41(r3); mr r30,r3` in the target): the stored field's type is wrong even though a byte store looks the same for `s8` and `u8`. Find a function that loads the field: plain `lbz` before indexing means `u8`. Example: `UnkTask3F60._29` in `fn_3_168CD8`.
- **A different stored value** (`li r3,0` versus a register holding data) is a logic error in the source, not allocation. Example: in `calculateHitVariables` the original stores 0 into `inAirOrBefore2ndBounceOrLowBallEnergy`, not the star type.
- **Code shared with a `*_unused` static function.** Upstream's `_unused` means the standalone copy has no callers in the binary. The caller may hold its own written-out copy, possibly with statements in a different order, or call the function and have it inlined (units build with `-inline auto` and `-inline deferred`). Try both and keep whichever matches while the standalone function still matches. Example: `calculateHitVariables` matches with written-out copies of `starHitSetting_unused` and `calculateBuntVerticalAngle_unused`; calling them allocates registers differently.
- **Inlined same-file functions.** A call in the source with no `bl` in the object was inlined; small non-static functions from the same file inline too (`calculateBuntHorizontalPower`).
- **A function that matches standalone but not where it is inlined:** check every inlined copy before choosing between forms. `return (a >= b | c >= d) != 0;` and `if (a >= b | c >= d) return TRUE; return FALSE;` both give `neg; or; srwi` standalone, but only the second gives the target's `or.; beq; li r0,1; b; li r0,0` in the caller. Example: `fn_3_16D4D8`, inlined into `fn_3_16D5E4`.
- **A function outside the unit's `.text` range is inlined into one of its functions** (no callers, its body repeated in the unit; `match.py` warns "functions in the source but not in the target" once you write it as a plain function): look just outside the unit's `.text` range in `splits.txt` for an uncalled function with the same body. It belongs to the unit, so escalate the split. Meanwhile define it `static inline` under its `symbols.txt` name; a plain `static` function is still emitted even when every call inlines it. Examples: `fn_3_16C410` inlined into `fn_3_16CC2C` (`rep_4090.c`), `fn_3_15F874` inlined twice into `fn_3_15FF28` (`rep_3CE0.c`).
- **A `bl` only in the target, to an empty stub in the same file:** the stub gets inlined away, and `#pragma dont_inline` does not stop it. The caller matches once the stub has a real body; to check the rest now, delete the stub's definition temporarily and keep its prototype. Example: `fn_3_16C394` calls `fn_3_16B884`.
- **The base inlines a same-file function that the target calls with `bl`:** `-inline auto` inlines a callee whose statement count is under a threshold, so the original callee had more statements than yours, though they compiled to the same code. Measured on `fn_3_6A83C`: each expression statement, call, `if` and `return` counts about one; declarations with initializers count like assignments; empty statements and folded constants count nothing. Rewrite the callee in a plausible longer form (early `return`s instead of one nested `if`, a local for a value read twice) until the caller's size matches, and recheck the callee. To learn how far off you are, add `x = 0;` lines to a scratch copy until the inlining stops. Example: `fn_3_6A83C` stays a call in `fn_3_6AB58` only with its early returns and its `state` and `order` locals.
- **The size limit also counts expression size, not only statements.** Using a local `g_Stats_s* stats = &g_Stats;` as `stats->field` in about a dozen places raised fn_3_7C4E4's count by about three dummy statements, and a pointer that shortened `g_ReplayLogic[g_Stats.playFrameCounter][i].field` lowered it. `m -= 16.0f;` split from `m = sqrt(...) - 16.0f`, and `m = 64.0f * m; m /= 56.0f;` split from one expression, each added one with identical code (`m *= 64.0f` swaps the `fmuls` operands). Example: `fn_3_7C4E4`, called from `fn_3_7C9D8`.
- **One field loaded twice, once through a register set at function entry** (`addi r31,r7,g_Stats@l` before the calls, then `lbz r0,60(r3)` from a fresh `lis/addi` and `lbz r0,60(r31)`): the source mixes a local pointer and the global, `stats->x` for the early stores and one test, `g_Stats.x` for the other. Example: `fn_3_7C1FC` matches with `g_Stats._3C != 2 && stats->_3C != 13`.
- **A comparison argument computed in a different place** (`cror; mfcr; rlwinm` or `srawi; subfc; adde` before the float loads in one listing, after them in the other): MWCC evaluates arguments left to right, and since ints and floats go in separate registers, register use does not show where a mixed prototype puts its `int` parameter. Move the flag in the prototype until the evaluation order matches. Example: `fn_3_C1344(s32, f32, f32, BOOL)` and `fn_3_BD504(f32, f32, f32, BOOL)` in `rep_F80.c`.
- **Stores in a different order with the same values,** such as `[2]` before `[0]`: chained assignments store right to left, so `a[0] = a[2] = 255;`. Example: `fn_3_169600`.
- **`addi rX,rX,1` after the `add` in the base, before it in the target:** MWCC reassociates `min + (rand() % range + 1)` into `(min + rand() % range) + 1`; parentheses and operand order do not stop it, and a `(u8)` cast adds a `clrlwi`. Hold the inner sum in a local: `shade = rand() % range + 1; color = min + shade;`. Example: `fn_3_16C878` in `rep_4090.c`.
- **A float argument of an inlined call computed late** (the base adds the constant after the callee's first `bl` into a scratch FPR; the target adds it into the saved FPR before): update the variable before the call, `x += 1.8f; draw(d, x, y);`, instead of passing `x + 1.8f`. Example: `fn_3_16DB6C` inlining `fn_3_16D810`.
- **A table load before a call in the target, after it in the base** (`lbzx r31,...; bl RandomInt_Game; cmpw r3,r31`): MWCC evaluates a call in an expression before the other operands, whichever side it is on, so the original read the value in its own statement first: `chance = table[i][j]; if (RandomInt_Game(100) < chance)`. Example: `fn_3_212A0`.
- **A retry counter that only increments when the loop repeats** (`cmpwi r30,2; bge exit; addi r30,r30,1; b top`, where `while (... && tries++ < 2)` gives `cmpwi; addi; blt top`): `for (;;) { ...; if (done || tries >= 2) break; tries++; }`. Example: `fn_3_20FB0`.
- **Float loads in another order, and a different constant addressed through `addi rX,rY,sym@l; lfs f,0(rX)`:** how the arithmetic is split into statements decides the scheduling. Try splitting a compound expression and moving neighbouring stores. Example: `fn_3_20EEC` matched only as `index` stored first, then `width = max - min; width /= 5.0f; x = min + width * index;`. In `fn_3_6CD88` the `addi`/`lfs 0(rX)` form for two constants appeared only with the scale in its own statement, not as one expression inside `x += x * (...)`.
- **A float test as `bge <next>; b <epilogue>` in the target** where the base has `blt <epilogue>` or `cror; beq <next>; b <epilogue>`: the test is the last term of an `||` guard, which branches past the return when false and falls through to it: `if (!fn(i) || data->_50 < 0.1f) return;`. A separate `if (data->_50 < 0.1f) return;` gives `blt`, and `!(data->_50 >= 0.1f)` gives the `cror` form. Example: `fn_3_16D5E4` in `rep_4090.c`.
- **An early-return guard ending in `bne <next>; b <epilogue>`** where the target has a single `beq <epilogue>`: MWCC does not invert the last test of `if (A && (B || C)) return;`. Put the body under the negated condition, `if (!A || (!B && !C)) { ... }`, and fold a following `if` into it with `&&` when the target exits with `bnelr`. Example: `fn_3_CB234`, `fn_3_CB1B0`, `fn_3_CB284`.
- **A load scheduled before the first test of an `&&`** (`lwz r0,arr(r3)` between `cmplwi` and `bne` of the first operand): the original read it into a local before the `if`. Example: `player = lbl_8036E548._2C50[task->_33]; if (task->_34 == 0 && player != NULL)` in `fn_3_CAE00`.
- **A list walk with no entry branch** (the body runs before the first `cmplwi; bne top`): the source is a `do { } while ((p = p->next) != NULL);`. A `for` loop adds `b <test>`, even right after an `if (dead != NULL)` that proves the first test. Example: both loops of `fn_3_16C548` in `rep_4090.c`.
- **A countdown loop with the test at the bottom and no entry branch** (`cmpwi r25,0; subi r25,r25,1; bne top`): `i = 2; do { ... } while (i--);`. `i = 3; while (i--)` adds an entry branch and `for (i = 2; i >= 0; i--)` gives `addic.; bge`. Example: `fn_3_CABF0`.
- **A store of 0 and a loop counter sharing one `li rX,0`:** a chained assignment, `task->_34 = i = 0; for (; i < 2; i++)`. Separate statements load 0 twice. Example: `fn_3_CAF9C`.
- **A range test over different values** (`addi r0,r4,-49; clrlwi r0,r0,24; cmplwi r0,1; ble` against the base's `addi r0,r3,-48; ... cmplwi r0,2`): MWCC merges consecutive `==` tests in an `||` chain into unsigned range checks, and the grouping depends on the operand. With an `s8` local, `id == 0x30 || id == 0x31 || id == 0x32 || id == 0x33` gives a 0x30 to 0x32 range; reading the field in each test (`p->_252 == 0x30 || p->_252 == 0x31 || ...`) gives `== 0x30`, a 0x31 to 0x32 range, then `== 0x33`. Example: `fn_3_E1478`.
- **`li rX,K; beq; li rX,K-1` in the target, `cntlzw; srwi; addi` or `neg; or; srawi` in the base:** MWCC turns `i == 0 ? K : K-1`, and an `if`/`else` that assigns one constant in each branch, into branchless code. Assigning the default first keeps the branch: `ch = 0x18; if (i != 0) { ch = 0x17; }`. Example: `fn_3_C11CC` and `fn_3_C1770` in rep_1F58.
- **A countdown loop that tests before it decrements** (`cmpwi r5,0; subi r5,r5,1; ...; bne top`, leaving -1 when nothing was found): `i = 1; do { if (found) break; } while (i-- != 0);`. `for (i = 1; i >= 0; i--)` is unrolled when inlined, or compiles to `addic.; bge`. Example: `fn_3_C1930` (inlined across rep_1F58) and `fn_3_C095C`.
- **Byte stores indexed from `buf+K`** (`addi r31,r5,1; stbx r4,r31,r30`) **next to copies addressed with displacements:** MWCC compiles `buf[x + K] = v` as `(buf + K)[x]`, but folds `&buf[x + K]` into `(buf + x) + K`. When the target indexes some accesses through a separately computed `x + 0x20` and folds others into `(buf + x) + 0x22`, the source had a second index variable for the former only: `row2 = row + 0x20; buf[row2] = g; *(u16*)&buf[row + 0x22] = *(u16*)&buf[row2];`. Example: `fn_3_C0D10`.
- **Assertion panics:** `OSErrorLine(line, "message")` produces `OSPanic(__FILE__, line, ...)`, and `__FILE__` is the bare file name (`"kinoko.c"`).

## `...rodata.0` in the base, constants one by one in the target

The base shows `lis rX,...rodata.0@ha; addi` and then `lfs f0,100(rX)`, while the target names each constant (`lfs f0,lbl_3_rodata_418C@l(r4)`). MWCC pools a function's `.rodata` references once it touches enough of them (three float constants alone stayed separate in `fn_3_16D810`; adding a `GXColor` initializer pooled all four).

- **Cause: the original's `.rodata` began with weak objects, which turns pooling off for that section** (observed: with weak objects first nothing in `.rodata` is pooled, while `.bss` statics still are). `game/UnknownHomes_Game.h` defines `SQRT2_LINKAGE extern` before including `math.h`, so `dolsqrtf2` becomes an `extern inline` whose static locals are emitted as weak `_half$localstatic` and `_three$localstatic` even when unused; plain `#include "math.h"` emits nothing. The target's `.rodata` does not show them, presumably because the linker kept one weak copy for the whole module.
- **Fix, only when the base shows `...rodata.0`:** include `game/UnknownHomes_Game.h` above `header_rep_data.h`, as `game_batter.c` does. The `.rodata` section score loses those 0x10 bytes; the code matches. Example: `rep_4138.c`, where this matched `fn_3_16D810` and `fn_3_16DB6C`. `-pool off` also matches such functions but breaks pooled `.bss`, and GC/1.3.2 to 2.7 behave identically, so the include order is the explanation, not the flags.
- The same include matched `fn_3_16B5B4` in `kinoko.c`, which pooled once an inlined callee added string literals.
- **When nothing needs unpooled constants, include `header_rep_data.h` first.** That puts `repHeaderData` at offset 0 as in the target and scores `.rodata` higher (92% against 86% in `rep_F80.c`); every function matched with either order.

## `.rodata` below 100% with every function matched

- **Literal constants in the reverse of the target's order:** the source lists functions in address order. With `-inline deferred` MWCC generates functions last to first (objdiff's `reverse_fn_order` hides this for `.text`) and creates each function's constants as it goes, so REL source lists functions from the highest address down; `tools/reverse_functions.py` converts a file. Example: rep_940 `.rodata` 83% to 93%.
- **The weak `dolsqrtf2` constants** (0x10 bytes, from `game/UnknownHomes_Game.h`) stay as a difference; the linker keeps one copy for the whole module. The explanation above is incomplete: in `rep_10E8`'s target, `_half` and `_three` are local objects in the middle of `.rodata` (0x1140, 0x1148), yet its constants are unpooled and the include order still matched.

## `.data` or `.bss` below 100% with every object defined

- **A trailing `gap_..._data` symbol, or a last object larger than its type:** the linker padded the section up to the next unit's alignment (8 for `.data`, 32 for kinoko's `.bss`). Leave it; no source object belongs there. Example: `rep_3E58.c` scores `.data` 98.73% (4-byte `gap_04_000285A4_data` after the jump table) and `.bss` 50% (`lbl_3_bss_B9E0` is an `s8` with size 0x20 in `symbols.txt`). A `switch` jump table needs no definition: MWCC emits it as `@NNN` and objdiff pairs it with `jumptable_...`.

## Before committing

- Run `tools/match.py` on every function that uses a type, prototype or symbol you changed, not only the one you were fixing.
- Run `python3 tools/regress.py`; it fails on any dropped objdiff score or lost strict match. Its summary goes in the pull request.

## Tool pitfalls

- Install m2c from https://github.com/matt-kempster/m2c. The PyPI package named `m2c` is an unrelated project.
- `match.py --m2c` prepares the unit's context for m2c (preprocesses it and strips inline asm); the draft is typed only for globals the source's includes declare, so a placeholder file including only `header_rep_data.h` gives `?` types until you add `game/UnknownHomes_Game.h` and the like.
- `match.py` reports a function you have written as `missing` when objdiff cannot pair it, for example after a callee's empty stub was inlined into it; give the callee a body first.
- decomp-permuter's own `import.py` breaks on this project; `tools/permute.py` explains why in its header and replaces it.
- `tools/permute.py` fails with a syntax error on `va_arg(args, s32)`, because pycparser cannot parse MWCC's `_var_arg_typeof`. For the permuter run only, write `*(s32*)__va_arg(args, 1)` (the same code), and restore `va_arg` afterwards.
