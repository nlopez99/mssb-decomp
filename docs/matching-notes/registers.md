# Registers only: same instructions, different register numbers

Part of the [matching notes](../matching-notes.md). Add a lesson here when a function with this symptom teaches you something new: symptom, cause, fix, example.


- **The task local in r31 in the base, r30 in the target, with a CSE'd global base in r31 there** (`addi r31,r3,4` for `&lbl_803C77B8[0]._04`, used by several `lhzx`): the global the task comes from is `void*`, so the local takes it through a conversion, `MenuTask0840* task = lbl_803CC1B8;` with `extern void* lbl_803CC1B8;` (later reads cast it, `((MenuTask0840*)lbl_803CC1B8)->_0C`). Declared `MenuTask0840*`, every other function of the unit still matched, which hid the cause. Examples: `fn_2_3A8FC` and `fn_2_3AF08` in menus `rep_0840.c`; see also the `void*` entry in [`types.md`](types.md). A pointer local to another global, live from the entry, takes r31 the same way: `GameInitVariables* settings = &g_d_GameSettings;` declared after `task` and used in one `case` (`addi r31,r3,g_d_GameSettings@l` before the switch in the target; `fn_2_399C0`, same file). Even a global read once deep in a loop can come from such a local: in `fn_2_4358C` (menus `rep_08E8.c`) only the `lis` registers of `lbl_800E8558` and `g_d_GameSettings` were swapped at entry until `player = g_d_GameSettings._36;` read through `settings`.
- **Shared across functions.** When several functions show the same unexplained allocation while identically written ones match, look at what they share before tweaking each: a prototype's parameter or return type changes the compiler's internal conversions and so its allocation, with identical instructions. Example: `minigame_checkIfAIInputIs_Algorithmic_Or_ControllerBased(u8)` should take `s8` (callers pass `s8 characterIndex[]`); that fixed three functions.
- **`int` against `s32` in a prototype.** `s32` is `long`, so MWCC converts between it and `int` even though the code is the same, and the conversion moves allocation. `fn_3_28E4` (`rep_140.c`) had `count` and a saved address swapped (r29/r30) until the callee `fn_3_1B24` took `int count`; the permuter pointed there with casts on that one argument. Recheck the callee: its second loop then tested `cmpwi r8,1; ble` against the target's `li r12,1; cmpw r12,r8; bge` until its counter became `s32 i`, and `fn_3_155C` needed `int` for both. An inlined callee's parameter type counts too: `fn_3_4EFC8` (`rep_AC8.c`) shares one fielder pointer with the inlined `fn_3_52560(int fielder, ...)` only when its own parameter is `int` (93.70% to 99.87%), and its caller `fn_3_3EB6C` moves with that prototype (99.69% with both `s32`, 97.61% with both `int`). `rep_13B8`'s callers of `fn_3_52560` lose two matches with `s32`, so run `regress.py` after any such change to a shared prototype.
- **Declaration order.** The order locals are declared in affects which register each gets, volatile or callee-saved; try moving the variable that lands in the wrong register above its neighbour. Example: `inputs` declared before the `BOOL` flag. Search the orders again after any other fix: `fn_3_15FB84`'s `n` and `player` (r9 and r11 swapped) matched only once declared `n`, `marker`, `offset`, `player`, though an earlier search over the same four, made on an earlier version of the function, found nothing. Moving one declaration at a time can stall where swapping two distant ones still helps: `fn_3_FA58C` (`sta_c4.c`) gained nothing from any single move at 99.49% but reached 99.59% with `slot` and `indices` exchanged, so script every pairwise swap too. The permuter finds such orders when a manual search over statement forms does not: `fn_3_46ABC` and `fn_3_3BE50` (`rep_AC8.c`, 97.8% to 100%) matched once `x` was declared after `z` and `dx`.
- **Two counters zeroed into swapped registers before a loop** (`li r8,0; li r9,0` against `li r9,0; li r8,0`, with the counted index `n` in the other register): initialize both in the `for` header, `for (k = 0, n = 0; k < 9; k++)`. `n = 0;` before the loop stayed swapped over all 120 declaration orders. Example: `fn_2_8A008` in menus `rep_0DE0.c`.
- **Initializers count as part of the order.** A batch that permutes declarations keeps each one's form, all initialized at the declaration or all assigned in statements, so it misses mixed forms. `fn_3_60D80` (`rep_E08.c`) stayed at 99.26% over 576 orders and matched, as the permuter showed, with only `anim` initialized at its declaration and `player`, `state` and `timer` assigned in statements after it. Vary which locals are initialized where, as well as their order.
- **A whole function's registers rotated, with one more saved register in the target** (`stw r29` only in the target, the loop counter and hoisted globals each one register off): look for a value the target re-reads where the source reuses a local. In `fn_3_3C594` (`rep_AC8.c`) the condition `(other = g_FieldingLogic._0D8) != -1 && (... || f->_0B8 + 3.0f < g_Fielders[g_FieldingLogic._0D8]._0B8)` indexes with the global again, not `other`; that took it from 97.40% to 99.67%, and a declaration batch did the rest. The permuter found it.
- **A float and `0.0f` loaded into swapped FPRs for an equality test** (`lfs f1,80(r31); lfs f0,zero` then `fcmpu cr0,f1,f0` in the target, the reverse loads in the base): `x != 0.0f` and `0.0f != x` both put the constant first; the source tested the float's truth, `if (outs >= 3 && f->_050 && ...)` or `if (len)`. Examples: `fn_3_54B58` and `fn_3_2BB04` in `rep_AC8.c`.
- **Statement order of independent loads.** Which register a shared base (`addi r10,r3,sym@l`) gets depends on where its first use sits among the statements that read through it. Example: `fn_3_CABF0` in `rep_2308.c` matched once `model = &bss._010->_C4;` moved above the six local-array fills, written as `ids[i]`, `anims[i]` pairs in the target's store order.
- **Two tables' bases hoisted out of a loop in swapped registers** (`lis r7,lbl_80109AE8@ha` before `lis r6,lbl_8010A768@ha` in the target, the reverse in the base, every load in the loop otherwise identical): the table whose base the target forms first was read first in the loop body, even though the scheduled loads still take the other table's field first. Move that read to the top of its block of reads. Example: five functions in menus `rep_08E8.c` (`fn_2_42708`, `42BE8`, `42EB0`, `42FC8`, `432EC`) matched once `goal = lbl_80109AE8[...][j]._0;` came before the `lbl_8010A768` fields.
- **Two locals in one branch of an `if`/`else` in other registers, while the other branch matches with the same code shape:** each branch had its own locals. `fn_2_4917C` (menus `rep_08E8.c`) formats a number in hex or decimal; with one `i` and one value copy shared by both branches only the decimal branch differed (99.58%), and a separate `j` and `n` there matched it.
- **Volatile registers differ in a function's setup code** (`lbz r0,30(r27)` against `lbz r4,30(r27)` for the same field): the statement order of independent setup assignments decides them. Script every order of the first few assignments, crossed with a few declaration orders; that is a dozen runs. Example: `fn_3_168A6C` matched only as `model`, then `anim`, then `animData` assigned, with `animData` declared first. The same order decides how the whole entry block is scheduled: `fn_3_15FB84` went from 86% to 97.7% when a float local was computed after the first of three stores instead of before them.
- **A value loaded once.** Holding a repeated load in its own local (with the type of the expression, usually `int`, not the field's `u8`) changes allocation. Example: `slapContactSize` in `calculateBuntHorizontalAngle`; `u8 status = g_GameLogic.gameStatus;` tested by an `if` and a later `switch` in `fn_3_E1478`.
- **The same digit values in other saved registers in each `switch` case** (thousands in r28 in one case and r26 in another, tens the reverse): the original reused three generic locals in a different role per case, not one local per meaning. `fn_2_5F458` in menus `rep_0AB0.c` matched with `d2, d1, d0` for thousands, hundreds, tens in case 0, `d0, d1` for hundreds, tens in case 3 and `d0, d1, d2` in case 4.
- **An array index loaded before the pointer to the array in the target** (`lbz r7,0(r4)` of `table[i]`, then `lwz r6,0(r3)` of the global pointer, where the base loads the pointer first): the index went into a local first, `id = lbl_800E869C[i]; p->_00[id] = (p->_00[id] + 1) % 2;`. Example: the last loop of `fn_2_587F8` in menus `rep_0AB0.c` (98.23% to a match).
- **A helper's two bases in swapped registers** (`lis r5,lbl_3_data_21A48@ha` against the base's `r6`), **and where it is inlined the caller reads the same fields through a saved register** (`lfs f5,32(r19)` for `g_Minigame._1DEC`, with `r19` holding `&g_Minigame._1DCC`): the helper read the fields through a pointer to the struct that begins earlier, `Unk3520Ai* ai = (Unk3520Ai*)&g_Minigame._1DCC; ... x * ai->cos - z * ai->sin`. The caller's own `ai` pointer then serves the inlined copy too. Example: `fn_3_135600` in `rep_3520.c`, which matched together with `fn_3_13493C` and the stores of `ai->sin` in `fn_3_13334C`.
- **An indexed global's base in `r0` and the scaled index in the parameter's own register in the target** (`slwi r3,r3,6; addi r0,r5,g_Minigame@l; add r5,r0,r3`, where the base has `slwi r0,r3,6; addi r5,r5,...; add r5,r5,r0`): the function indexed a real member of the struct, `g_Minigame.starDashObjs[i]._0.x` (a union member added to `MiniGameStruct`); a local pointer, `Unk3520Minigame* mg = &MG; mg->objs[i]`, matches as well, but its inlined copies do not share the callers' walkers. A cast in place, `((Unk3520Obj*)((u8*)&g_Minigame + 0xBB0))[i]`, gives the base's allocation and `MG.objs[i]` other instructions. Example: `fn_3_1354BC` in `rep_3520.c`, which matched this way but is kept at 99.2% with its locals declared so that its copy inlined in `fn_3_1350BC` matches.
- **A loop that forms `g_Minigame`'s address anew (`lis/addi`) where the target copies the function's saved base (`mr r24,r27`)**: the loop reached the struct through a cast view of `g_Minigame` (a macro such as `#define MG (*(Unk3520Minigame*)&g_Minigame)`), which MWCC does not share with plain `g_Minigame.x` accesses. A union member in `MiniGameStruct` over the same bytes (`g_Minigame.starDashSpokes[j][0]`) shares the base. Example: `fn_3_135A64` in `rep_3520.c` (96.5% to 98.1%).
- **A loop's element walker in the lowest saved register where the target has a higher one** (`mr r17,r30` against `mr r21,r30` for `c = coins`): the loop indexed the array, `coins[i].valid`, and MWCC made the walker itself. In the same function, a fielder read once into a pointer local (`fielder = &g_Fielders[...]; dx = coord.x - fielder->pos.x;`) loaded its operands in the other order from the target, which indexed `g_Fielders[...]` in each expression. Example: `fn_3_1350BC` in `rep_3520.c` (98.9% to a match).
- **Operands swapped in an add** (`add r31,r31,r0` versus `add r31,r0,r3`): split the expression, e.g. `value = tex[i]; value += step * 2;`. Example: `fn_3_16943C`.
- **An `add` of a float-to-int conversion and a table value with the conversion second** (`lwz r0,12(r1); add r0,r10,r0` where the target has `add r0,r0,r10`): MWCC puts the loaded value first for both `(int)(d * t) + lo` and `lo + (int)(d * t)`. Hold the converted value in an `int` local, and the difference before it too: `range = hi - lo; offset = range * t; z = offset + lo;`. The `range` local also fixed where the index of `t` was loaded. Example: `fn_3_20224` in `rep_8C8.c` (`range` found by the permuter).
- **A table base and a scaled index added in the other order** (`addi r0,r3,g_hitShorts@l; slwi r3,r4,1; add r3,r0,r3` against the target's `addi r3,r3,...; slwi r0,r0,1; add r3,r3,r0`), **with the registers of nearby values rotated:** the source cast the struct to an element pointer, `((s16*)&g_hitShorts)[i]`; indexing from its first field, `(&g_hitShorts.frameChargeDownEnds)[i]`, adds in the target's order. Example: `fn_3_A970` in `rep_540.c` (99.77% to 99.83%).
- **A derived value written to a new register** (`subf r3,r4,r6; subf. r3,r0,r3` where the base reuses the variable's register, `subf r6,r4,r6`): the original computed it into a second local, `left = frame - total; left -= charged; if (left <= 0 ...)`. `frame -= total;` reuses `frame`'s register, and one expression gives other allocations. Example: `fn_3_1EFE4` in `rep_8C8.c`.
- **A comparison used as an index allocated differently** (`subfic r3,r4,1; subi r0,r4,1; or r4,r3,r0` with the operand registers swapped): assign it to a local first, `late = early == 1 ? 0 : 1;`, then index with `late`. Writing `table[early != 1]` in place gives the same instructions in other registers. Example: `fn_3_1EAA8` in `rep_8C8.c`.
- **Float values loaded into swapped registers for stores that copy and offset them** (`lfs f3,32(r5)` against `lfs f2,32(r5)` before `stfs` to one struct and `fadds` into another): compute the second store from the field just stored, `b.pos.x = b.pos2.x + offset;` after `b.pos2.x = ai.box;`, not from the source global again. Example: `fn_3_1F998` in `rep_8C8.c`.
- **A converted integer times a power-of-two reciprocal with the constant second** (`fmadds f0,f4,f1,f0` with `f1` = `0.00390625f`, where the base puts the constant first): the source divided, `camera->_38 += pad->_11 / 256.0f;`. MWCC turns the division into a multiply by the reciprocal and keeps the dividend first; `* 0.00390625f` puts the literal first. A negative divisor stays an `fdivs` (`/ -256.0f`). Examples: `fn_2_858A4` and `fn_2_85AC0` in menus `rep_0DE0.c`.
- **Operands swapped in an `fmadds`** (`fmadds f0,f2,f1,f0` against `f0,f1,f2,f0`): swapping or regrouping the C operands changes nothing. Compute the multiplicand into a local first: `t = min + range * rand() / 32767.0f; x = t * (n - i) + i;`. Example: `fn_3_15BAA0`.
- **The products of a two-term blend computed in the other order** (`fmuls` of one product, then `fmadds` folding in the other): MWCC computes the right-hand product of `a * b + c * d` with `fmuls` and folds the left one into the `fmadds`, so swap the terms. `fn_3_E5CBC` (`sta_c6.c`) matched as `(1.0f - t) * to->r + t * from->r`, with `to` and `from` read into locals before the clamp of `t`.
- **Operands swapped in an `fmuls` by a constant, product in a new register** (`fmuls f1,f2,f1` with the constant in `f1`, against `fmuls f1,f1,f2`): MWCC puts the literal first in both `s = s * K` and `s = K * s`, while `s *= K` keeps the order but writes the product back into `s`'s register. Passing both through `math.h`'s inline `scaleValue` keeps the order and gives a new register: `scale = scaleValue(a / 512.0f, 0.27208483f);`. Example: `fn_3_6CD88`; in `fn_3_15C3F8` (`rep_3B70.c`) `half *= 0.5f` also merged the stack slots of two int-to-float conversions, shrinking the frame by 0x10. For an `int` variable, `dx = a - b; dx *= 0.2f;` keeps the constant second (`fmuls f1,f1,f31`) and converts back to `int`, where `dx = (int)(a - b) * 0.2f;` puts it first: `fn_3_E9D30` (`rep_2BF8.c`). A negated operand behaves the same: `angle = -obj->_B0; angle = 0.017453292f * angle;` put the negation and the constant in the target's registers where `angle = 0.017453292f * -obj->_B0;` swapped them (`fn_3_E2F4C` in `rep_2998.c`). The same split fixed an angle and its sine or cosine swapped between saved FPRs where the function is inlined, though the standalone copy matched either way: `angle = rand() % 360; angle = 0.017453292f * angle;` (`fn_3_14B248`, inlined in `fn_3_14B53C`) and `angle = (rand() % 36000) / 100.0; angle = 0.017453292f * angle;` (`fn_3_150D84`, inlined in `fn_3_151204`); `fn_3_148FD0` needed `angle = scaleValue(0.017453292f, scaleValue(15.0f, ...));` (all `rep_3880.c`).
- **A product by 0.5 with the variable first** (`fmuls f3,f0,f2` with `0.5f` in `f2`, where `x * 0.5f` and `0.5f * x` put the literal first): the source divided by two, `p->_38 / 2`; MWCC turns the division into a multiply after it has ordered the operands. - **A pointer picked by a flag, set by default and overridden in one branch** (`addi r31,lbl_A@l; cmplwi; bne; addi r31,lbl_B@l`), where the base builds both in scratch registers and copies one: the source used a conditional expression, and MWCC stores its false operand first and the true one in the branch, `cfg = big ? lbl_3_data_26DC4 : lbl_3_data_26D88;` for a default of `26D88`; flip the condition (`!p->_4F ? ... : ...`) when the target's default is the other table. - **Two loads in swapped registers feeding two stores** that already come out in the target's order: swap the two assignment statements. - **Operands swapped in a branchless `or`/`or.` chain** (`cntlzw; srwi; or; or.` tests): reorder the operands of `|` in the condition; each order gives a different pairing. Example: `fn_3_16E1EC` matches only as `lbl_3_bss_D6EC | !lbl_8036E548._3088 | !lbl_3_bss_D6E4`.
