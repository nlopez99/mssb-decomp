# Structure differences

Part of the [matching notes](../matching-notes.md). Add a lesson here when a function with this symptom teaches you something new: symptom, cause, fix, example.


- **A `Vec` initializer copied from `.rodata` only inside a branch, and the locals around it at the wrong offsets:** it is declared with its initializer in that block (`Vec offset = { 0.0f, 0.0f, 0.0f };`), and the locals at lower offsets are declared after it in the same block. Example: `fn_3_1674D0`.
- **Float constants loaded into saved registers before straight-line code, and a global's address formed with `addi` and loaded with `lwz r0,0(rX)`:** the body is a one-pass loop, `for (i = 0; i < 1; i++)`; loop-invariant code motion runs before the loop is unrolled away. Statements whose loads use the hoisted address go inside the loop. An `fmadd` with a 0.0f addend there is `angle = 0.0f; angle += 45.0 * r;`, since `0.0f + 45.0 * r` folds. Example: `fn_3_1678A8`. When an index's offset is still computed after the first call while the constant is hoisted above it (`lfs f30,...` before `bl fn_800BDC88`, `mulli r21,r3,144` after), the one-pass loop's increment also steps that index, `for (i = 0; i < 1; j++, i++)`: `fn_3_E4FC4` in `rep_2998.c` (91.9% to 94.1%).
- **An argument's address hoisted out of a loop into a saved register in the target** (`addi r30,r24,8` before the loop, `mr r3,r30` at the call), where the base forms it at each call (`addi r3,r26,8`): the original copied the member's address into a local first, `MtxPtr world = task->_08;`. Order these locals with the others: `fn_3_3638` (`rep_1C0.c`) matched only with `world`, `camera`, `i`, `layout`, `disp`, `pal` declared in that order.
- **A float sum recomputed after a call in the target** (`extsh; xoris; ... fadds f0,f0,f31` again after `bl`), **while the base keeps it from the argument in a saved FPR** (`fadds f31,f1,f31` before the call): the original passed `x + dx` and then updated with a compound assignment, `x += dx;`; `x = x + dx;` is CSE'd with the argument. Example: `fn_3_3904` in `rep_1C0.c` (87.6% to 93.1%).
- **A float constant's address formed with `addi` and loaded with `lfs f,0(rX)` in each branch of an `if` chain (one instruction more per branch), the other factor loaded first with `lfs f,sym@l(rY)`:** every branch called an inline helper that took the constants as arguments and converted the integers into float locals, `placeInGrid(i, &pos, 5, 0.79f, 0.614f)` with `f32 x = i % columns; f32 z = i / columns; CTRLSetTranslation(..., pos->x + x * dx, pos->y, pos->z - z * dz);`. Written out in each branch, or with the conversions inside the expressions, the base loaded both constants directly. Example: `fn_2_86470` in menus `rep_0DE0.c` (90.55% to a match).
- **Digit quotients computed twice in the base** (`srawi; srwi; add` repeated before each `mulli r,q,100`), **once in the target, which multiplies the stored digit back**: the source took each remainder from the digit it had stored, `digits[0] = value / 100; digits[1] = (value - digits[0] * 100) / 10; digits[2] = (value - digits[0] * 100) - digits[1] * 10;`; `value % 100` recomputes the quotient. With `u8` digits the products use `clrlwi` copies of the stores. `fn_2_89038` stores `s8` digits (`extsb` before the call that passes one) yet multiplies `clrlwi` copies for the last digit, which only `(u8)digits[0] * 100` and `(u8)digits[1] * 10` there gave. Examples: `fn_2_887F8`, `fn_2_87998` and `fn_2_89038` in menus `rep_0DE0.c`.
- **A value computed into a saved register before the first of several calls in the target, while the base computes it right before the last call that uses it:** MWCC forwards a local's single assignment into its one use, across calls. A compound assignment stops it: `hundreds = value / 100; hundreds %= 10;` before `fn(..., value % 10); fn(..., (value / 10) % 10); fn(..., hundreds);`, where `hundreds = (value / 100) % 10;` and every type and statement order tried were forwarded. In the same file, digits followed by `if (value < 100) hundreds = 10;` stay put on their own. Example: `fn_2_62A38` in menus `rep_0AB0.c` (80.69% to 96.62%; the target still keeps `value / 100` in a scratch register).
- **Rows `K` and up of a two-dimensional array strength-reduced in the target** (a base advanced by the row size each iteration, `addi r25,r25,224`, plus `idx * 112 + 0x548`), **but multiplied in the base** (`addi r3,r23,6; mulli r4,r3,224`), when the second index is a variable: those rows are a separate struct member, `_548[i][idx]`, not `tasks[i + 6][idx]` of one array. Example: `g_UNK_StadiumDetails` for `fn_3_567C` (`rep_1C0.c`); `fn_3_5EC0`, whose second index is constant, matched either way.
- **A field address hoisted out of an inner loop in the base** (`addi r11,r6,2` before `mtctr`, then `lha r0,0(r11)`) **where the target folds the offset** (`lha r0,2(r6)` from the outer loop's walking pointer): take a pointer to the element in the outer loop body, `def = &m[i];`, and read `def->type` and `def->target` through it. `m[i].target` in the inner loop is hoisted, and advancing `m++` in the outer loop reorders the setup instead. Examples: `fn_3_162080` and `fn_3_16230C` in `rep_3DA8.c`.
- **Stack offsets swapped between two locals** (`addi r3,r1,72` against `addi r3,r1,24`, or array stores at `8(r1)` against `16(r1)`): MWCC gives later-declared locals lower offsets; swap their declarations. Example: `m` declared before `tmp` in `fn_3_168414`.
- **An inlined callee's stack locals in the reverse order of its standalone copy** (each case of a `switch` that inlines one function has its `Vec`s at swapped offsets): MWCC lays out an inlined function's locals in declaration order and a standalone function's last-declared lowest. When the callee needs its own order to match standalone, the original repeated its code: `fn_3_1536A8` (`rep_3880.c`) writes out `fn_3_1534C0`, `fn_3_1531A4` and `fn_3_152794` as its cases. An inline-only helper takes its declarations reversed instead: `Vec v; Vec base;` and `rz, ry, rx` in `fn_3_SpawnAtBall`, against `fn_3_155C28`'s written-out `base, v` and `rx, ry, rz`. The same holds for registers: `fn_3_62E70` (`rep_E08.c`) writes out `fn_3_62CA8`'s body with `kind` declared first, since no order of `fn_3_62CA8`'s own locals matches both standalone and inlined (99.77% to 99.94%; reading `_20D` through a `fielder` pointer declared at the loop top matched the rest).
- **An inlined callee recomputing a global array's address that the caller keeps in a saved register** (the target reads `lwzx r4,r27,r0` from the caller's `addi r27,r3,0x2c50`, the base rebuilds it with `lis; addi; lwz 0x2c50(r5)`): the callee's index had another type than the caller's, here `int player` against `s32 player`, and MWCC shares the address only between identical expressions. The callee compiled the same standalone with either type. Example: `fn_3_60D80` inlined into `fn_3_61B64` (`rep_E08.c`, 99.0% to 99.7%). The reverse also happens: menus `rep_0B08.c`'s byte setter `fn_2_68F08(int index, s8 value)` is inlined into `s32 index` callers, and only with `int` does `fn_2_71C6C` recompute `index * 0xD8` after a `memcpy` as its target does, while the other inlined setters share it.
- **A struct copied with a `mtctr` loop of `lwz`/`lwzu` pairs in the target, word by word in the base:** the copied type is larger than yours. A 0x3C-byte struct copy is unrolled; the target's loop (8 iterations of two words plus one) copies 0x44 bytes. Example: the `Control` copied in `fn_3_E4CB0` (`rep_2998.c`), which is 0x44 bytes in this game (below).
- **Two out-parameter addresses hoisted into saved registers before a loop** (`addi r26,r1,12; addi r27,r1,16`, read back with `lfs f0,0(r27)`) while the first is formed at each call: they are members of one local struct, `CTRLGetTranslation(&c, &pos.x, &pos.y, &pos.z)`. Example: `fn_3_E4CB0` in `rep_2998.c`.
- **Two stores through one pointer loaded after a call, with no reload between a float and a byte store, while the next call reloads the pointer from its owner:** the stores went through a local assigned right there, `speed = speeds[fn_3_B7F70(3)]; model = obj->_74; model->_54 = speed; model->_5A = 1; fn_800B4C04(obj->_74->_00, obj->_74->_54);`. Example: `fn_3_E29B4` in `rep_2998.c`.
- **A position stored to a global after a later call in the target** (`stfsu f30,g_Ball@l(r4)` after `bl cos`), the base storing the first component before it: the components went into locals first, `x = ...sin...; z = ...cos...; g.x = x; g.y = ...; g.z = z;`. Example: `fn_3_E3044` in `rep_2998.c`.
- **Int-to-float conversion temporaries at other stack offsets** (`stw r6,0x44(r1)` against `0x34`) in otherwise identical code: MWCC gives each conversion its slot in statement order, even where the scheduler interleaves the instructions, so the slots give the statements' source order. In `fn_3_6E24C` (`rep_1188.c`) the slots matched once `width = 0.01f * sizes[c][2] * m;` moved below the `_104` and `_108` stores.
- **`__fpclassifyf` temporaries of several inlined `dolsqrtf2` at other stack offsets** (`stfs f4,20(r1); lwz r4,20(r1)` against `16(r1)`, the slots in another order): a call written directly in the function gets its slot before the calls inside an inlined helper, whatever the code order. Put the lone call in a helper too, or the helper's calls in the function. In `fn_3_6C38` (`rep_540.c`) three speed checks went through `keepMinimumSpeed()` and the last one, written inline, took the first slot; moving it into `stopIfSlow()` gave the target's order.
- **Global loads hoisted before a loop in the target but repeated inside it in the base** (flags `lbz`'d into r24 to r31 and floats into f0 to f5 before `mtctr`): the loop wrote through a pointer it advanced (`stats++`), which MWCC assumes can alias any global. Index the global array in each statement, `inMemRoster[team][i].stats.Speed *= k[8];`; MWCC still strength-reduces it to a walking pointer. Example: `fn_3_6EF1C` in `rep_1188.c`. A pointer to one element does the same: `c = &tracker.characters[id]; c->inGameMissionTracker[i].starMissionStatus++` kept `g_Pitcher` fields from being hoisted out of an inner loop, while `starMissionCompletionTracker.characters[id].inGameMissionTracker[i]` in every statement (a macro in `rep_3DA8.c`) let them go (`fn_3_162080`). A field read through a pointer local to a global, `bss->_40` with `bss = &lbl_3_common_bss_37400`, likewise stayed in the loop with the index arithmetic built on it; reading `lbl_3_common_bss_37400._40` itself let MWCC hoist `inMemRoster[team]` and `lbl_803537E4[team]` (`fn_3_162D54` 93.6% to 95.8%, the last loop of `fn_3_16230C` 97.2% to 99.9%).
- **A float-to-int conversion of a loop-invariant value done once before the loop in the base** (`fctiwz; stfd; lwz` ahead of `mtctr`) **but in every iteration in the target**: the cast is to the field's own type, `stats.CurveBallSpeed += (u8)k[4];`; `(int)k[4]` is hoisted. Example: `fn_3_6EF1C` (85.7% to 96.2%).
- **The same selection repeated before each use** (`lwz r4,8(r30); beq; li r4,0` ahead of every `mulli rX,r4,0x5A0`): an inline helper called once per test, `team = g_GameLogic.teamFielding; if (g_d_GameSettings.minigamesEnabled) team = 0; return inMemRoster[team][id].stats.FieldingStats;`. A ternary in its place gives `beq; li; b`, and a local computed once gives one selection. Example: `getFieldingStats` in `rep_1188.c`.
- **A two-case `switch` whose tree ends in two `b default` in the target and one in the base** (`cmpwi r0,1; beq; bge default; cmpwi r0,0; bge case0; b default; b default`): the switch has a third, empty case, `case 2: break;`. `default: break;` in any position changes nothing. Example: `fn_3_21C90` and `fn_3_21DE4` in `rep_A00.c`.
- **A dead `b <default>` right after a switch's range test** (`cmpwi r0,2; bge <default>; cmpwi r0,0; bge <case>; b <default>; b <default>`): the source listed more cases that share the default block, `case 0: case 1: ...; break; case 2: case 3: case 4: default: ...`; MWCC threads their test into `default` but leaves its branch behind. Example: `fn_1_D300` in `rep_0610.c` (98.83% to 99.73%, and its inlined copy in `fn_1_107B8`).
- **`cmpwi r0,K; beq <body>; b <next>` testing one value inside a loop** (where `if (x == K)` gives `cmpwi; bne <next>`): a `switch` with a single case, `switch (m[i].type) { case 31: ...; break; }`. Example: every case of `fn_3_161588` in `rep_3DA8.c`.
- **The same doubled `b default` when the default has code:** a value that shares the default's body, `case 4: default:`, gives the second `b default` without adding a compare. Example: the participant-count switch in `fn_3_E7B20` (`sta_c6.c`).
- **A `switch` compare tree with another pivot** (`cmpwi r0,2; beq; bge default; cmpwi r0,0; beq; bge case1; b default; b default` against a tree pivoting on 1): an explicit `case` label sharing the default's body adds its value to the tree. Write `case 3: default:`. Example: the offset table choice in `fn_3_15FB84`. Empty labels count as well: the target's tree for cases 1 and 2 pivoted on 2 with an explicit `beq` to the end for 0 once the source listed `case 0: break;` and `case 3: break;` (`fn_1_1E90C` in `rep_7730.c`).
- **A field loaded once before a `switch` and compared in some cases, but reloaded after the call in others** (`lbz r0,33(r29)` before the tree, `cmpw r30,r0` in cases 0 and 3, `bl; lbz r0,33(r29)` in cases 1 and 2): the original copied the field into a local before the switch, `sel = task->_21;`, and compared the cases that make no call with `sel`, the others with the field. Examples: `fn_1_1F418` and `fn_1_1FD78` in `rep_7730.c`.
- **An inlined callee's copy rereads an array element after a call** (`lwz r3,0(r29)` for `GXLoadTexObj`, then `lwz r0,0(r29)` again for the `& 0x80000000` test), while the standalone callee, which matches, keeps the element in a saved register: the callers wrote the loop out in place and read `ids[j]` at each use. Example: `fn_1_1F900` in `rep_7730.c` (and `fn_1_1F618`, whose registers still differ), against `fn_1_20640`.
- **An index decremented before it is scaled, outside any loop** (`lbz r0,33(r31); addi r0,r0,-1; slwi r0,r0,6; add`, where the base folds the -1 into the displacements, `lfs f2,-52(r4)`): the original computed the index into a local first, `last = params->_21 - 1; lbl_1_bss_6FE0[last]._0C.x`. Example: `fn_1_21180` in `rep_7730.c`.
- **A countdown loop tested at the bottom with `addic. rN,rN,-1; bne` (or `cmpwi rN,0; addi rN,rN,-1; bne`), walking a pointer down by one element per pass:** the source decremented in the test, `i = n; while (--i != 0)` (or `while (i-- != 0)`). Written as `for (i = n - 1; i != 0; i--)` MWCC unrolled the loop (0x364 bytes against 0x170), and `match.py` then reported the function `missing` although it was in the source. Example: `fn_1_21298` in `rep_7730.c`.
- **A `switch` compare tree preceded by its own `cmplwi r0,0; beq <end>`** (then `cmpwi r0,3; beq; bge; cmpwi r0,1; ...` over cases 1 to 4), where the base folds 0 into the tree (`cmpwi r0,2` as pivot, `cmpwi r0,0; beq <end>` inside): the source left the switch before it on zero, `if (x == 0) continue;` (or `return;`), and listed only cases 1 to 4. `case 0: break;` adds 0 to the tree. Example: both menus of `fn_3_ACD38` in `rep_1A80.c` (97.5% to a match).
- **A `switch` whose listed cases branch forward past the default's code to a shared block** (`li r0,0` placed after the default's computation, which ends in `b` over it): the default comes first and falls into the cases when its guard fails, `default: if (!g_Stats.replayInd) { ...; flag = ...; break; } case 3: case 11: ... flag = FALSE; break;`. Cases first with an `if`/`else` in the default gives two copies of the zero block. Example: `fn_3_C9878` in `sta_c0.c`.
- **A jump-table `switch` whose case bodies sit in another order than their values** (case 5's body after case 10's, the table's entry 5 pointing past the others): MWCC lays out case bodies in source order, so write the cases in the target's layout order, `case 6: ... case 10: ...; break; case 5: ...`. m2c's draft lists them in that order too. Example: both switches of `fn_1_1B7DC` in challenge `rep_74A0.c` (82.70% to a match, 0xBF0 bytes).
- **A `switch` drafted by m2c whose compare tree or jump-table bound differs** (`cmplwi r0,37` against the base's `cmplwi r0,7`, or another pivot): m2c drops the empty cases whose target is the switch's exit, so their labels are missing from the source. A jump table's bound is its highest case (`case 0x25: break;`); in a tree, a constant followed by `beq`, or by a `bge` into a case body, is a case, while one followed by `bge <exit>` only bounds a range. When the tree still differs, compile sets of extra empty cases in a script: the menus item handlers needed `case 0x24: case 0x25:` (`fn_2_3735C`), and `fn_2_24800`'s closing `cmpwi r0,0; beq; blt <exit>; b <exit>` came from `case 0:` with empty `case 1: case 2:` (`rep_0788.c`).
- **Two `b <exit>` in a row after a compare tree** (`cmpwi r0,0; bge <case 1>; b <exit>; b <exit>`): the `switch` has an empty case one past its last, which also moves the pivot. `case 3: break;` after cases 0 to 2 (`fn_2_53408` in `rep_0A08.c`), `case 2: break;` after cases 0 and 1 (`fn_2_509A4` in `rep_09B8.c`). A lone `cmpwi r3,1; beq <a>; b <b>` with identical blocks at `<a>` and `<b>` is a `switch` with `case 1:` and `default:` (`fn_2_509A4`).
- **A case body that ends without `b <exit>` and runs into the next case's code** (its failed test branches straight into that code too): the case falls through, `case 3: if (...) { ...; state = 4; } case 4: ...`. Example: `fn_2_2E5C8` in `rep_0788.c`.
- **Argument registers set before a compare whose result only picks the last argument** (`mr r3,r30; lha r4; li r5; li r6` ahead of `lbz; cmpwi r0,2; beq`, then `mr r7,r9` and the call), where the base tests first and sets the arguments after: the value is a conditional expression inside the call, `fn_800363D8(task, item->_0E, 1, 0x65, list[i] != 2 ? i : 20);`. Example: `fn_2_306D8` in `rep_0788.c`. When the conditional in the call still sets the arguments after the test, they went through an inline helper's parameters, which are assigned before its body: `fn_1_2948C` in challenge `rep_7BF0.c` matched only as `menuControl(&menu, pad._00, pad._02, repeat)` around `fn_80048820(menu, held, pressed, repeat, (held & PAD_BUTTON_Y) ? 0x91 : ...)`.
- **Two calls made before a flag test in the target, one inside the condition in the base:** their results go into locals first, `done = fn_8006CDC0(id); kind = fn_2_44E2C(id); if (flag == 1 && done != kind)`. Example: `fn_2_28EA0` in `rep_0788.c` (90% to 99.8%).
- **A struct field's offset added to the index before an indexed load** (`mulli r3,r3,52; addi r3,r3,9; add r0,r3,r0; lbzx r0,r4,r0`), where the base folds it into the displacement (`add r3,r4,r3; lbz r0,9(r3)`): the source took a pointer to the inner array first, `missions = tracker->chars[id]._09; if (missions[i]._0 < 0)`. Found by the permuter as `(0, chars[id]._09)[i]`. Example: `fn_2_2B654`, `fn_2_2BB34` and `fn_2_2B884` in `rep_0788.c`.
- **A record field read with the record's offset in the displacement** (`mulli r0,r0,10; add r3,r4,r0; lbz r0,16630(r3)`), where the base adds the array's offset first (`addi r3,r3,16624; lbz r0,6(r3)`): index the array in each access, `p->slots[p->cur]._8`, instead of taking `slot = &p->slots[p->cur]`. Example: `fn_2_200E4` in `rep_0788.c`.
- **A failed equality test that branches past a later test of the same field** (`cmplwi r0,7; bne <after the == 8 block>`, where the base falls through to `cmplwi r0,8`): the later test is nested in the first one's block, `if (x == 7) { ...; if (x == 8 && ...) same = TRUE; }`. MWCC does not thread a jump past a test whose field the block may have changed. Example: `fn_3_D9A30` in `rep_28A8.c`.
- **A constant set on a counted loop's fall-through exit, then tested against a value no path sets** (`bdnz` back, `li r0,4`, then `cmpwi r0,-1` before using `r0`): the loop is an inline helper that returns from inside it, `for (i = 3; i >= 0; i--) { if (...) { ...; return 2; } } return 4;`, and the caller checks its result, `base = getBaseToCover(); if (base != -1)`. The same loop with a `base` local and `break` sets 4 before the loop. Example: `fn_3_480B8` in `rep_AC8.c`.
- **`cmpwi r,5; bge skip; cmpwi r,1; bge body; b skip`** is a `switch` with cases 1 to 4 sharing one body, not an `if` (which gives `blt skip` for the second test). Example: the bone loop in `fn_3_168414`.
- **`mr rS,r3` and a store through `r3` swapped right after a call** (`stb r31,41(r3); mr r30,r3` in the target): the stored field's type is wrong even though a byte store looks the same for `s8` and `u8`. Find a function that loads the field: plain `lbz` before indexing means `u8`. Example: `UnkTask3F60._29` in `fn_3_168CD8`.
- **A shared `mr r3,rN` before the epilogue in the target, but its own `mr r3,rN` before the branch in the base** (`bl processStadiumObjectFunction; b <end>`, where `<end>` is `lwz r0,68(r1); mr r3,r30`): the early exit jumps to the function's final `return ret;`, and the call's result is discarded. A second `return ret;` gets its own copy; `goto end;` with `end: return ret;` shares it. Example: `checkCollision` in `rep_D0.c`.
- **A task's teardown (`bl fn_80034CEC; bl fn_800B0A14_removeQueue`) once, at the end, reached by a `bne` from the first test and a `bge` from a later case** (the base repeats the calls inside the late case or puts them first): both paths `goto remove;`, with `return;` before the label. When only the first test reaches it, the body sits in `if (!cond) { ... } else { teardown }`. Examples: `fn_3_128A38` and `fn_3_125604` in `rep_3448.c`.
- **A different stored value** (`li r3,0` versus a register holding data) is a logic error in the source, not allocation. Example: in `calculateHitVariables` the original stores 0 into `inAirOrBefore2ndBounceOrLowBallEnergy`, not the star type.
- **Code shared with a `*_unused` static function.** Upstream's `_unused` means the standalone copy has no callers in the binary. The caller may hold its own written-out copy, possibly with statements in a different order, or call the function and have it inlined (units build with `-inline auto` and `-inline deferred`). Try both and keep whichever matches while the standalone function still matches. Example: `calculateHitVariables` matches with written-out copies of `starHitSetting_unused` and `calculateBuntVerticalAngle_unused`; calling them allocates registers differently.
- **Inlined same-file functions.** A call in the source with no `bl` in the object was inlined; small non-static functions from the same file inline too (`calculateBuntHorizontalPower`).
- **A call's stack-address arguments set out of order** (`addi r4,r1,32; addi r5,r1,44; addi r3,r1,20` with a temporary in `r3` before them, where the base sets `r3` first and uses `r7`), or **stack `Vec`s that keep the wrong offsets whatever their declaration order:** the `Vec`s were one array, `VecXYZ pts[4]; ... fn_3_9EFD0(&pts[0], &pts[1], &pts[2], &pts[3])`. A three-element array plus a separate output fixed the order but put the output at the bottom of the frame. Examples: `fn_3_2BB04` and `fn_3_2AD68` in `rep_AC8.c`.
- **An inlined callee's arguments copied into stack slots before its body** (nine `lwz`/`stw` pairs filling three `Vec` slots that the inlined `PSVECSubtract` then reads, or `lwz`/`stw` of a struct field into a local right before an inlined `PSMTX44MultVec` into it): the callee takes the struct by value, `Vec fn_3_FC2FC(Vec pos, Vec anchor, Vec target, ...)`. Its standalone code is the same as with pointer parameters, so only the callers show it.
