# Structure differences

Part of the [matching notes](../matching-notes.md). Add a lesson here when a function with this symptom teaches you something new: symptom, cause, fix, example.


- **A `Vec` initializer copied from `.rodata` only inside a branch, and the locals around it at the wrong offsets:** it is declared with its initializer in that block (`Vec offset = { 0.0f, 0.0f, 0.0f };`), and the locals at lower offsets are declared after it in the same block. Example: `fn_3_1674D0`.
- **Float constants loaded into saved registers before straight-line code, and a global's address formed with `addi` and loaded with `lwz r0,0(rX)`:** the body is a one-pass loop, `for (i = 0; i < 1; i++)`; loop-invariant code motion runs before the loop is unrolled away. Statements whose loads use the hoisted address go inside the loop. An `fmadd` with a 0.0f addend there is `angle = 0.0f; angle += 45.0 * r;`, since `0.0f + 45.0 * r` folds. Example: `fn_3_1678A8`. When an index's offset is still computed after the first call while the constant is hoisted above it (`lfs f30,...` before `bl fn_800BDC88`, `mulli r21,r3,144` after), the one-pass loop's increment also steps that index, `for (i = 0; i < 1; j++, i++)`: `fn_3_E4FC4` in `rep_2998.c` (91.9% to 94.1%).
- **An argument's address hoisted out of a loop into a saved register in the target** (`addi r30,r24,8` before the loop, `mr r3,r30` at the call), where the base forms it at each call (`addi r3,r26,8`): the original copied the member's address into a local first, `MtxPtr world = task->_08;`. Order these locals with the others: `fn_3_3638` (`rep_1C0.c`) matched only with `world`, `camera`, `i`, `layout`, `disp`, `pal` declared in that order.
- **A float sum recomputed after a call in the target** (`extsh; xoris; ... fadds f0,f0,f31` again after `bl`), **while the base keeps it from the argument in a saved FPR** (`fadds f31,f1,f31` before the call): the original passed `x + dx` and then updated with a compound assignment, `x += dx;`; `x = x + dx;` is CSE'd with the argument. Example: `fn_3_3904` in `rep_1C0.c` (87.6% to 93.1%).
- **Rows `K` and up of a two-dimensional array strength-reduced in the target** (a base advanced by the row size each iteration, `addi r25,r25,224`, plus `idx * 112 + 0x548`), **but multiplied in the base** (`addi r3,r23,6; mulli r4,r3,224`), when the second index is a variable: those rows are a separate struct member, `_548[i][idx]`, not `tasks[i + 6][idx]` of one array. Example: `g_UNK_StadiumDetails` for `fn_3_567C` (`rep_1C0.c`); `fn_3_5EC0`, whose second index is constant, matched either way.
- **A field address hoisted out of an inner loop in the base** (`addi r11,r6,2` before `mtctr`, then `lha r0,0(r11)`) **where the target folds the offset** (`lha r0,2(r6)` from the outer loop's walking pointer): take a pointer to the element in the outer loop body, `def = &m[i];`, and read `def->type` and `def->target` through it. `m[i].target` in the inner loop is hoisted, and advancing `m++` in the outer loop reorders the setup instead. Examples: `fn_3_162080` and `fn_3_16230C` in `rep_3DA8.c`.
- **Stack offsets swapped between two locals** (`addi r3,r1,72` against `addi r3,r1,24`, or array stores at `8(r1)` against `16(r1)`): MWCC gives later-declared locals lower offsets; swap their declarations. Example: `m` declared before `tmp` in `fn_3_168414`.
- **An inlined callee's stack locals in the reverse order of its standalone copy** (each case of a `switch` that inlines one function has its `Vec`s at swapped offsets): MWCC lays out an inlined function's locals in declaration order and a standalone function's last-declared lowest. When the callee needs its own order to match standalone, the original repeated its code: `fn_3_1536A8` (`rep_3880.c`) writes out `fn_3_1534C0`, `fn_3_1531A4` and `fn_3_152794` as its cases. An inline-only helper takes its declarations reversed instead: `Vec v; Vec base;` and `rz, ry, rx` in `fn_3_SpawnAtBall`, against `fn_3_155C28`'s written-out `base, v` and `rx, ry, rz`.
- **A struct copied with a `mtctr` loop of `lwz`/`lwzu` pairs in the target, word by word in the base:** the copied type is larger than yours. A 0x3C-byte struct copy is unrolled; the target's loop (8 iterations of two words plus one) copies 0x44 bytes. Example: the `Control` copied in `fn_3_E4CB0` (`rep_2998.c`), which is 0x44 bytes in this game (below).
- **Two out-parameter addresses hoisted into saved registers before a loop** (`addi r26,r1,12; addi r27,r1,16`, read back with `lfs f0,0(r27)`) while the first is formed at each call: they are members of one local struct, `CTRLGetTranslation(&c, &pos.x, &pos.y, &pos.z)`. Example: `fn_3_E4CB0` in `rep_2998.c`.
- **Two stores through one pointer loaded after a call, with no reload between a float and a byte store, while the next call reloads the pointer from its owner:** the stores went through a local assigned right there, `speed = speeds[fn_3_B7F70(3)]; model = obj->_74; model->_54 = speed; model->_5A = 1; fn_800B4C04(obj->_74->_00, obj->_74->_54);`. Example: `fn_3_E29B4` in `rep_2998.c`.
- **A position stored to a global after a later call in the target** (`stfsu f30,g_Ball@l(r4)` after `bl cos`), the base storing the first component before it: the components went into locals first, `x = ...sin...; z = ...cos...; g.x = x; g.y = ...; g.z = z;`. Example: `fn_3_E3044` in `rep_2998.c`.
- **Int-to-float conversion temporaries at other stack offsets** (`stw r6,0x44(r1)` against `0x34`) in otherwise identical code: MWCC gives each conversion its slot in statement order, even where the scheduler interleaves the instructions, so the slots give the statements' source order. In `fn_3_6E24C` (`rep_1188.c`) the slots matched once `width = 0.01f * sizes[c][2] * m;` moved below the `_104` and `_108` stores.
- **Global loads hoisted before a loop in the target but repeated inside it in the base** (flags `lbz`'d into r24 to r31 and floats into f0 to f5 before `mtctr`): the loop wrote through a pointer it advanced (`stats++`), which MWCC assumes can alias any global. Index the global array in each statement, `inMemRoster[team][i].stats.Speed *= k[8];`; MWCC still strength-reduces it to a walking pointer. Example: `fn_3_6EF1C` in `rep_1188.c`. A pointer to one element does the same: `c = &tracker.characters[id]; c->inGameMissionTracker[i].starMissionStatus++` kept `g_Pitcher` fields from being hoisted out of an inner loop, while `starMissionCompletionTracker.characters[id].inGameMissionTracker[i]` in every statement (a macro in `rep_3DA8.c`) let them go (`fn_3_162080`). A field read through a pointer local to a global, `bss->_40` with `bss = &lbl_3_common_bss_37400`, likewise stayed in the loop with the index arithmetic built on it; reading `lbl_3_common_bss_37400._40` itself let MWCC hoist `inMemRoster[team]` and `lbl_803537E4[team]` (`fn_3_162D54` 93.6% to 95.8%, the last loop of `fn_3_16230C` 97.2% to 99.9%).
- **A float-to-int conversion of a loop-invariant value done once before the loop in the base** (`fctiwz; stfd; lwz` ahead of `mtctr`) **but in every iteration in the target**: the cast is to the field's own type, `stats.CurveBallSpeed += (u8)k[4];`; `(int)k[4]` is hoisted. Example: `fn_3_6EF1C` (85.7% to 96.2%).
- **The same selection repeated before each use** (`lwz r4,8(r30); beq; li r4,0` ahead of every `mulli rX,r4,0x5A0`): an inline helper called once per test, `team = g_GameLogic.teamFielding; if (g_d_GameSettings.minigamesEnabled) team = 0; return inMemRoster[team][id].stats.FieldingStats;`. A ternary in its place gives `beq; li; b`, and a local computed once gives one selection. Example: `getFieldingStats` in `rep_1188.c`.
- **A two-case `switch` whose tree ends in two `b default` in the target and one in the base** (`cmpwi r0,1; beq; bge default; cmpwi r0,0; bge case0; b default; b default`): the switch has a third, empty case, `case 2: break;`. `default: break;` in any position changes nothing. Example: `fn_3_21C90` and `fn_3_21DE4` in `rep_A00.c`.
- **`cmpwi r0,K; beq <body>; b <next>` testing one value inside a loop** (where `if (x == K)` gives `cmpwi; bne <next>`): a `switch` with a single case, `switch (m[i].type) { case 31: ...; break; }`. Example: every case of `fn_3_161588` in `rep_3DA8.c`.
- **The same doubled `b default` when the default has code:** a value that shares the default's body, `case 4: default:`, gives the second `b default` without adding a compare. Example: the participant-count switch in `fn_3_E7B20` (`sta_c6.c`).
- **A `switch` compare tree with another pivot** (`cmpwi r0,2; beq; bge default; cmpwi r0,0; beq; bge case1; b default; b default` against a tree pivoting on 1): an explicit `case` label sharing the default's body adds its value to the tree. Write `case 3: default:`. Example: the offset table choice in `fn_3_15FB84`.
- **A `switch` whose listed cases branch forward past the default's code to a shared block** (`li r0,0` placed after the default's computation, which ends in `b` over it): the default comes first and falls into the cases when its guard fails, `default: if (!g_Stats.replayInd) { ...; flag = ...; break; } case 3: case 11: ... flag = FALSE; break;`. Cases first with an `if`/`else` in the default gives two copies of the zero block. Example: `fn_3_C9878` in `sta_c0.c`.
- **A failed equality test that branches past a later test of the same field** (`cmplwi r0,7; bne <after the == 8 block>`, where the base falls through to `cmplwi r0,8`): the later test is nested in the first one's block, `if (x == 7) { ...; if (x == 8 && ...) same = TRUE; }`. MWCC does not thread a jump past a test whose field the block may have changed. Example: `fn_3_D9A30` in `rep_28A8.c`.
- **`cmpwi r,5; bge skip; cmpwi r,1; bge body; b skip`** is a `switch` with cases 1 to 4 sharing one body, not an `if` (which gives `blt skip` for the second test). Example: the bone loop in `fn_3_168414`.
- **`mr rS,r3` and a store through `r3` swapped right after a call** (`stb r31,41(r3); mr r30,r3` in the target): the stored field's type is wrong even though a byte store looks the same for `s8` and `u8`. Find a function that loads the field: plain `lbz` before indexing means `u8`. Example: `UnkTask3F60._29` in `fn_3_168CD8`.
- **A shared `mr r3,rN` before the epilogue in the target, but its own `mr r3,rN` before the branch in the base** (`bl processStadiumObjectFunction; b <end>`, where `<end>` is `lwz r0,68(r1); mr r3,r30`): the early exit jumps to the function's final `return ret;`, and the call's result is discarded. A second `return ret;` gets its own copy; `goto end;` with `end: return ret;` shares it. Example: `checkCollision` in `rep_D0.c`.
- **A task's teardown (`bl fn_80034CEC; bl fn_800B0A14_removeQueue`) once, at the end, reached by a `bne` from the first test and a `bge` from a later case** (the base repeats the calls inside the late case or puts them first): both paths `goto remove;`, with `return;` before the label. When only the first test reaches it, the body sits in `if (!cond) { ... } else { teardown }`. Examples: `fn_3_128A38` and `fn_3_125604` in `rep_3448.c`.
- **A different stored value** (`li r3,0` versus a register holding data) is a logic error in the source, not allocation. Example: in `calculateHitVariables` the original stores 0 into `inAirOrBefore2ndBounceOrLowBallEnergy`, not the star type.
- **Code shared with a `*_unused` static function.** Upstream's `_unused` means the standalone copy has no callers in the binary. The caller may hold its own written-out copy, possibly with statements in a different order, or call the function and have it inlined (units build with `-inline auto` and `-inline deferred`). Try both and keep whichever matches while the standalone function still matches. Example: `calculateHitVariables` matches with written-out copies of `starHitSetting_unused` and `calculateBuntVerticalAngle_unused`; calling them allocates registers differently.
- **Inlined same-file functions.** A call in the source with no `bl` in the object was inlined; small non-static functions from the same file inline too (`calculateBuntHorizontalPower`).
- **An inlined callee's arguments copied into stack slots before its body** (nine `lwz`/`stw` pairs filling three `Vec` slots that the inlined `PSVECSubtract` then reads, or `lwz`/`stw` of a struct field into a local right before an inlined `PSMTX44MultVec` into it): the callee takes the struct by value, `Vec fn_3_FC2FC(Vec pos, Vec anchor, Vec target, ...)`. Its standalone code is the same as with pointer parameters, so only the callers show it. A by-value copy written to by the callee is discarded, which is how `fn_3_1048E0` (`rep_3090.c`) calls `fn_3_104A88(pose->_24, view._00)`. Examples: `fn_3_103C30` and `fn_3_103E7C` (inlining `fn_3_FC2FC`) and `fn_3_1048E0` in `rep_3090.c`.
- **A float constant loaded with `addi rX,sym@l; lfs fN,0(rX)` in one build and `lfs fN,sym@l(rY)` in the other, inside a run of independent float temporaries** (spline weights, matrix terms): reorder the statements until the constants are created in the target's `.rodata` order, which MWCC follows (first use creates the constant); the address form and the schedule follow. In `fn_3_FCF24` (`rep_3090.c`) computing the B-spline weights for p2, p0 and p1 in that order (`.rodata` 3.0f, -3.0f, -1.0f, 4.0f, 6.0f) matched that branch. The same function's int-to-float constant keeps its `addi` form only in the target, unexplained.
- **A function that matches standalone but not where it is inlined:** check every inlined copy before choosing between forms. `return (a >= b | c >= d) != 0;` and `if (a >= b | c >= d) return TRUE; return FALSE;` both give `neg; or; srwi` standalone, but only the second gives the target's `or.; beq; li r0,1; b; li r0,0` in the caller. Example: `fn_3_16D4D8`, inlined into `fn_3_16D5E4`. Likewise `ret = a >= b;` (and `ret = !ret;` for the inverse) is branchless in both places, while `if (a < b) return FALSE; return TRUE;` is branchless standalone and gives the caller's `bge; li r3,0; b; li r3,1`: `fn_3_22A20`, inlined into `fn_3_21F14` (`rep_A00.c`). The same held for `return !(x < 10.0f);` against `if (x < 10.0f) return FALSE; return TRUE;` in `fn_3_AABF8`, inlined into `fn_3_A25C4` (`rep_18E8.c`). Float allocation can differ the same way: `fn_3_A6ABC` matched with `if (speed == 0.0f) div = 1.0f; else div = speed;`, but its copy in `fn_3_A384C` matched only once that became `f32 div = speed == 0.0f ? 1.0f : speed;`, which matches standalone too.
- **A function outside the unit's `.text` range is inlined into one of its functions** (no callers, its body repeated in the unit; `match.py` warns "functions in the source but not in the target" once you write it as a plain function): look just outside the unit's `.text` range in `splits.txt` for an uncalled function with the same body. It belongs to the unit, so escalate the split. Meanwhile define it `static inline` under its `symbols.txt` name; a plain `static` function is still emitted even when every call inlines it. Examples: `fn_3_16C410` inlined into `fn_3_16CC2C` (`rep_4090.c`), `fn_3_15F874` inlined twice into `fn_3_15FF28` (`rep_3CE0.c`). The function may still have `bl` callers in the neighbouring unit: `fn_3_6C454`, inlined three times into `fn_3_6C4D0` (`rep_1090.c`), is called from `rep_1038`, whose `bl`s to the empty `fn_3_6C428` show those callers sit in another file. Once the split moves, make it a plain function with a header prototype: `-inline auto` still inlines it, and the object also gets the standalone copy the target has.
- **A `bl` only in the target, to an empty stub in the same file:** the stub gets inlined away, and `#pragma dont_inline` does not stop it. The caller matches once the stub has a real body; to check the rest now, delete the stub's definition temporarily and keep its prototype. Example: `fn_3_16C394` calls `fn_3_16B884`.
- **The base inlines a same-file function that the target calls with `bl`:** `-inline auto` inlines a callee whose statement count is under a threshold, so the original callee had more statements than yours, though they compiled to the same code. Measured on `fn_3_6A83C`: each expression statement, call, `if` and `return` counts about one; declarations with initializers count like assignments; empty statements and folded constants count nothing. Rewrite the callee in a plausible longer form (early `return`s instead of one nested `if`, a local for a value read twice) until the caller's size matches, and recheck the callee. Two statements were enough for `fn_3_1192B8` (`rep_3310.c`): an `id = i + 0x82;` local, which the target already keeps in a register, and a `scale` local for the computed size keep it a call in `fn_3_11AC6C` (84% to 99.85%). `fn_3_11D1B0` there stays unmatched: `fn_3_11CD00` and `fn_3_11C02C`, three or four `fn_3_11D2C8` calls each, need about 20 more statements (dummy stores in a scratch copy) before they stop being inlined. To learn how far off you are, add `x = 0;` lines to a scratch copy until the inlining stops. Example: `fn_3_6A83C` stays a call in `fn_3_6AB58` only with its early returns and its `state` and `order` locals. In `fn_3_E4CB0` (`rep_2998.c`) one statement was missing: `if (i != p._12 || p._10 == 2) continue; if (flag) { ... }` stops the inlining into `fn_3_E4EF4` where `if (i == p._12 && p._10 != 2 && flag)` does not. `fn_3_DD1A8` (`rep_28A8.c`) needed two more, which its draw loops gave without changing its code: `id = random_fn_3_9EE24(4); g_Minigame.rosterID = id; i++;` inside `do { } while (i < 100 && ...)`, instead of the call stored directly and `++i` in the condition; `fn_3_DFBAC` then calls it. `fn_3_82F80` (`rep_13B8.c`) stays a call in `fn_3_8307C` once each loop is `for (;;) { ...; dist -= v; if (dist < 0.0f) break; }` instead of `do { ...; dist -= v; } while (!(dist < 0.0f));`, which compiles the same. `fn_3_1360BC` (`rep_3520.c`) stays a call in `fn_3_135A64` with an early `if (count == 0) return;`, a separate `n++;` before its test and its random angle in a local; three dead `i = 0;` lines were the measured margin, and two plausible additions were not enough.
- **The size limit also counts expression size, not only statements.** Using a local `g_Stats_s* stats = &g_Stats;` as `stats->field` in about a dozen places raised fn_3_7C4E4's count by about three dummy statements, and a pointer that shortened `g_ReplayLogic[g_Stats.playFrameCounter][i].field` lowered it. `m -= 16.0f;` split from `m = sqrt(...) - 16.0f`, and `m = 64.0f * m; m /= 56.0f;` split from one expression, each added one with identical code (`m *= 64.0f` swaps the `fmuls` operands). Example: `fn_3_7C4E4`, called from `fn_3_7C9D8`.
- **The target inlines a same-file function that the base calls with `bl`** (the converse of the above): the original callee had fewer statements. A block it shares with another function was a `static inline` helper, which counts as one call. Example: `fn_3_155C28` (`rep_3880.c`) with its spawn block written out stays a call in `fn_3_155F08`; calling `fn_3_SpawnAtBall(p)`, the helper `fn_3_1552AC` uses twice, inlines it there and keeps its standalone copy (`fn_3_155F08` and `fn_3_156218` matched). Unsolved the other way: `fn_3_153F8C` inlines into `fn_3_1540E4` unless about 20 dummy `x = 0;` lines are added (16 are not enough), and writing out the `fn_3_153E8C` it inlines adds too few.
- **One field loaded twice, once through a register set at function entry** (`addi r31,r7,g_Stats@l` before the calls, then `lbz r0,60(r3)` from a fresh `lis/addi` and `lbz r0,60(r31)`): the source mixes a local pointer and the global, `stats->x` for the early stores and one test, `g_Stats.x` for the other. Example: `fn_3_7C1FC` matches with `g_Stats._3C != 2 && stats->_3C != 13`. The reverse shows too: one block re-forms the address with `lis/addi r6` in the base where the target uses the saved register (`add r4,r30,r4; lwz r4,244(r4)`, `lbz r4,341(r30)`). `fn_3_6E24C` (`rep_1188.c`) matched with `GameControlsStruct* logic = &g_GameLogic;` used in the first statement and in `logic->Team_CaptainRosterLoc[logic->teamFielding]` and `++logic->rosterLoc_skippingCap`, and `g_GameLogic` everywhere else.
- **A global's address kept in a saved register for some fields, while a loop over the same global starts its strength-reduced pointer as a copy of it** (`mr r4,r31`) and other fields reload the address with `lis/addi`: a local `MiniGameStruct* mg = &g_Minigame;` is used for the fields read through the saved register, and the loops index `g_Minigame` directly. Writing the loops through `mg` too drops the strength reduction (`lbzx` from `mg` plus the index instead of `lbz 0x1a82(r4)` with `addi r4,r4,1`). Example: `fn_3_1136FC` and `fn_3_1133C4` in `rep_3290.c` (`mg->_1DCF` for a state machine, `g_Minigame.wallIndexTracker[i]` in the loops).
- **A comparison argument computed in a different place** (`cror; mfcr; rlwinm` or `srawi; subfc; adde` before the float loads in one listing, after them in the other): MWCC evaluates arguments left to right, and since ints and floats go in separate registers, register use does not show where a mixed prototype puts its `int` parameter. Move the flag in the prototype until the evaluation order matches. Example: `fn_3_C1344(s32, f32, f32, BOOL)` and `fn_3_BD504(f32, f32, f32, BOOL)` in `rep_F80.c`. The same holds for pointer arguments: the target loading three floats before forming `addi r3,r1,10` meant `fn_800528C0(f32 x, f32 y, f32 z, s16* sx, s16* sy)`, not the pointers first (`fn_3_F9088` in `sta_c4.c`).
- **Argument registers set only in the target just before a `bl`** (`lfsx f1,...; lfs f2,...` before `bl fn_3_52560`, or `r3` computed before `bl fn_3_107988`), **or a whole function's float registers shifted around an inlined callee:** the local or header prototype has fewer parameters than the callee reads. Check the callee's entry for uses of `r3`-`r10` and `f1`-`f8`, give the owner's header and stub the real prototype, and pass the values the target loads. Where the target leaves them in `f1`/`f2` from an inlined call that used them first, keep them in locals that live until the second call. Examples: `fn_3_52560(fielder, x, z)` matched `fn_3_A41E8` and raised `fn_3_A63E4` from 95.5% to 99.8% in `rep_18E8.c`; `fn_3_107988(k)` matched `fn_3_11DECC` in `rep_3448.c`.
- **An index added before it is scaled** (`lhz r7,20(r31); addi r0,r7,1; slwi r0,r0,3; lwzx`) where the base folds the constant into the displacement (`slwi; add; lwz r4,8(r4)`): the accesses come from an unrolled loop, and `arr[x + i]` keeps the add once `i` becomes a constant. Example: `fn_3_912B4` in `rep_1610.c`, `for (i = 1; i < 3; i++) { lbl_80371C30[task->_14 + i]._00->_5C = (i - 1) << 16; }`.
- **A constant index scaled at run time** (`li r0,3; slwi r0,r0,2; add r5,r6,r0`), **or a register holding 0 compared with 0** (`li r29,0` before calls, `cmpwi r29,0` after them): the value is a counter that fully unrolled loops left behind, from generic code written for a count that is 1 here. Constant propagation after unrolling does not fold the arithmetic or the test. `fn_3_166448` in `rep_3E00.c` reads a file's offset table with `i = 0; for (j = 0; j < 1; j++) { for (k = 0; k < 3; k++) { models[j][k] = file + file[i++]; } }`, then tests `if (i == 0)` inside `for (i = 0; i < 1; i++)`. Two loads from that address, `lwz r0,0(r5)` and `lwz r0,4(r5)`, need a pointer local (`entry = &file[i];` then `entry[0]`, `entry[1]`); `file[i]` and `file[i + 1]` load the first with `lwzx`.
